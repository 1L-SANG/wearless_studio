# 계획 없는 빈 칸은 자리와 주변 사진을 보고 컷을 골라 채운다

상태: Accepted, 오너 승인 2026-10-11. 결정 네 가지(규칙만, 짝 칸은 비슷한 컷, 생성 중 한 줄 표시, 임시 버튼 없음)는 G6 세션이 전달한 오너 답이며 이 승인으로 확정했다.

## 배경

오너 원문(2026-10-11): "2가지 구분하자. 계획 없는 칸은, 현재의 위치나 위아래, 양옆 컷을 고려하며 어떤 컷을 넣으면 좋을지 종합적 판단하고 넣게끔 기능 만들어야할거같아."

에디터의 빈 사진 칸은 두 종류다. 콘티에서 계획된 칸은 저장된 콘티 설정으로 다시 만든다(ADR-0017). 계획 없는 칸은 지금 AI로 채울 길이 없다. 칸을 누르면 의류 탭만 열리고, AI 탭의 새 이미지는 칸이 아니라 의류 탭으로 간다. 색을 고르지 않은 요청은 `misc` 색으로 가서 서버가 실패시키고 예약을 풀어 준다.

조사에서 확인한 사실(origin/main 06805edd).

- 프레임과 템플릿은 넣는 순간 생성 컷으로 빈 칸을 돌려 채우고 그 컷의 `sourceBlockId`도 복사한다(`templates/autofill.js`). 셀러가 반복된 사진을 지우면 칸은 비지만 `sourceBlockId`가 남는다(`editorSelection.js` 칸 비우기). 그래서 `sourceBlockId`만으로는 계획된 칸을 가릴 수 없다.
- 셀러가 넣은 블록은 kind `styling`, contentRole `custom`으로 고정된다. 섹션을 알려 주지 않는다. 템플릿 칸에는 작성자가 정한 사진 목적 `roleHint`가 있다.
- 템플릿 한 벌 적용은 페이지의 생성 컷 블록을 걷어낸다. 그 뒤 페이지에는 섹션을 가진 블록이 남지 않는다.
- 에디터 새 이미지 경로는 장소 세트를 받지 않는다. 에디터에서 같은 장소의 다른 컷을 만드는 기존 수단은 비슷한 컷(ADR-0016)뿐이다.
- 발행된 고스트샷 예시는 상의 한 장뿐이다. 고스트샷은 예시 없이 만든다.
- 요청 접수 단계는 요청의 컷 종류가 착용컷일 때만 모델을 남긴다. 판단을 작업자 쪽으로 미루면 모델 없이 생성된다.

## 결정

### 1. 칸 가르기

- **계획된 칸**: 실패 표시(`genFailed`)가 있는 칸, 또는 `sourceBlockId`가 저장 콘티의 AI 블록을 가리키고 그 칸이 페이지 생성이 만든 블록에 있는 칸. 페이지 생성이 만든 블록은 `templateId`가 없고, kind가 사진 행(`twocol`, `threecol`, `grid2x2`, `colorcmp`)이거나 contentRole이 `custom`이 아닌 블록이다. 계획된 칸은 ADR-0017 다시 만들기로 간다.
- **계획 없는 칸**: 그 밖의 빈 사진 칸. 프레임과 템플릿의 칸, 붙여넣은 블록의 칸, 자동 채움 뒤 셀러가 지운 템플릿 칸이 여기에 든다. 이 ADR의 대상이다.
- **대상 밖**: 정보 블록(kind `info`)과 자동 블록(사이즈, 세탁, AI 안내)의 사진 칸, 생성 중인 칸(`genPending`), 숨긴 칸.
- 같은 판정을 화면과 서버가 함께 쓴다. 화면은 이 판정으로 다시 만들기와 AI로 채우기 중 하나를 연다. 서버는 받은 칸을 저장된 에디터와 콘티로 다시 판정한다.

### 2. 판단은 규칙으로, 서버가 요청을 받을 때 한 번 한다

- AI 판단 호출을 쓰지 않는다. 종합 판단은 규칙이 칸의 목적, 짝 사진, 위아래 사진, 페이지 전체, 상품 사실을 함께 보는 것으로 한다.
- 판단은 후보 만들기와 고르기로 나눈다. 후보 만들기는 이유가 붙은 순서 있는 후보 목록을 만들고, 고르기는 그중 하나를 정한다. 나중에 순위 판단을 바꿀 때 고르기만 바꾼다.
- 화면은 칸 위치만 보낸다. 레시피는 서버가 저장된 에디터, 콘티, 상품, 분석, 자산 기록에서 만든다. 클라이언트가 보낸 컷 설정은 읽지 않는다(ADR-0012의 원칙).
- 판단은 요청 접수 단계에서 끝내고 결과를 작업에 저장한다. 작업자는 다시 판단하지 않고, 재큐도 같은 결과로 만든다.

### 3. 칸의 목적

아래에서 처음 맞는 것을 쓴다.

1. 템플릿 칸의 `roleHint`.
2. 칸이 든 블록의 contentRole이 `custom`이 아니면 그 값(붙여넣은 페이지 생성 블록 포함).
3. 같은 블록 안에서 설정을 아는 다른 사진의 섹션.
4. 설정을 아는 사진이 있는 가장 가까운 위쪽 블록의 섹션, 없으면 가장 가까운 아래쪽 블록의 섹션. 정보 블록과 자동 블록은 건너뛴다.
5. 스타일링.

섹션의 기본 목적은 후킹 `hero`(그 칸이 페이지 첫 사진이 아니면 `benefit`), 스타일링 `coordination`, 스튜디오 `fit`, 의류 확인 `productOverview`다.

### 4. 짝 사진

- 같은 블록에서 세로 범위가 작은 쪽 높이의 절반 이상 겹치는 칸을 같은 줄로 본다. 가장 가까운 왼쪽, 그다음 가장 가까운 오른쪽이 짝이다. 같은 줄에 사진이 없으면 같은 블록에서 가로 범위가 절반 이상 겹치는 바로 위 칸이 짝이다.
- 짝과 페이지 사진의 설정은 서버가 사진 주소의 자산으로 찾는다. 칸에 남은 `sourceBlockId`는 자동 채움과 끌어 넣기 때문에 사진과 어긋날 수 있어 쓰지 않는다. 찾는 순서와 함수는 11절의 공용 함수를 따른다.
- 셀러가 직접 고르지 않은 사진은 자동으로 변형하지 않는다. 그래서 셀러가 직접 올린 사진은 짝으로 쓰지 않는다. 실제 모델 사진(`facemarket_real_derived`)도 짝으로 쓰지 않는다. 셀러가 그 사진을 골라 직접 비슷한 컷을 누르는 것은 G6가 허용한다.

### 5. 목적별 컷

**착용(hero, benefit, coordination)**

- 짝이 이 프로젝트에서 AI로 만든 착용 사진이고 서버가 컷 종류를 찾을 수 있으면, 그 사진의 비슷한 컷을 만든다(ADR-0016 경로). 같은 사람, 옷, 장소에서 동작만 바뀐다. 색 그룹은 짝을 따르고, 열림 정도도 짝 사진의 상태를 따른다(비슷한 컷 경로는 열림 값을 읽지 않는다).
- 짝이 없으면 새 컷을 만든다. 컷 종류는 목적의 기본값이다(hero와 coordination은 스타일링, benefit은 호리존 중간샷). 색은 기준색이다. 샷은 바로 위 블록부터 위로, 없으면 아래로 찾은 첫 착용 사진이 풀샷이면 중간샷, 아니면 풀샷이다. 예시는 공개 예시 중 이 페이지에 같은 색으로 쓰이지 않은 것이고, 정면을 먼저 보고 위아래 사진과 같은 방향은 뒤로 미룬다.

**스튜디오(fit)**

- 호리존이다. 짝은 설정을 아는 호리존 사진일 때만 쓴다. 색은 짝, 없으면 기준색이다.
- 짝이 있으면 그 줄에 없는 방향을 정면, 옆모습, 뒷모습 순으로 고르고 샷은 짝과 같게 한다.
- 짝이 없으면 그 색 호리존 사진에 페이지 전체에서 없는 방향을 고른다. 셋 다 있으면 다른 샷으로 정면부터 다시 본다.
- 예시는 그 방향과 샷의 공개 호리존 예시 중 페이지에 없는 것이다.

**고스트샷(productOverview)**

- 기준색 앞면, 기준색 뒷면, 추가 색 앞면(등록 순), 뒷면 사진이 있는 추가 색 뒷면 순서에서 페이지에 아직 없는 색과 면을 고른다.
- 짝이 고스트샷이면 짝 색의 다른 면을 맨 앞으로 올린다.

**디테일(detail)**

- 분석이 찾은 부위 중 고를 수 있는 것(단독, 잘 보임, 앞면이나 뒷면) 가운데 페이지에 없는 것을 순위대로 고른다. 같은 정보 묶음이 이미 있으면 건너뛴다. 색은 기준색이다.
- 남은 부위가 없으면 고스트샷 순서로 넘어간다. 사진에 없는 부위는 만들지 않는다(ADR-0012).

**색 비교 칸**

- 블록이 '컬러 비교' 프레임이거나 '컬러 비교 카드' 템플릿이면, 짝과 같은 컷을 그 줄에 아직 없는 색으로 만든다. 짝이 없거나 짝 설정을 모르면 고스트샷 앞면을 그 줄에 없는 색으로 만든다. 줄에 모든 색이 나오면 고스트샷 순서로 넘어간다.

### 6. 모든 칸에 함께

- 상품 사실: 디테일은 분석 부위만, 제품컷의 면은 그 색에 그 면 사진이 있을 때만, 추가 색은 정면 사진이 있는 색만 쓴다.
- 열림 정도(아우터 새 착용컷): 짝의 값, 없으면 페이지 착용컷에 가장 많은 값, 없으면 열림. 칸 수 범위를 넘는 값은 서버가 맞춘다(ADR-0018). 여밈 없는 옷은 값을 넣지 않는다.
- 모델은 프로젝트에서 고른 모델이다. 매칭 의류는 짝의 값, 없으면 같은 색 착용 콘티 블록의 값이다.
- 반복을 피한다. 같은 예시와 같은 색, 같은 고스트 색과 면, 같은 디테일 부위를 다시 고르지 않는다. 같은 칸에서 전에 AI로 채운 결과의 설정도 다시 고르지 않는다.
- 같은 순위의 후보가 여럿이면 프로젝트, 칸, 시도 횟수로 정해지는 값으로 하나를 뽑는다(`cut_generator`의 결정적 뽑기 재사용). 같은 상황이면 같은 답이 나오고, 같은 칸에서 다시 누르면 다음 후보가 나온다. 시도 횟수는 그 칸에서 완료된 AI로 채우기 작업 수다.

### 7. 대체

- 후보가 없으면 조건을 차례로 푼다. 같은 예시의 다른 색 허용, 샷 바꾸기, 마지막으로 목적의 기본 컷이다. 마지막 단계는 반복을 허용하고 기록에 이유를 남긴다.
- 상품 사진이 없어 아무것도 만들 수 없으면 작업과 예약을 만들지 않고 거절한다.

### 8. 요청과 응답

```text
POST /v1/projects/{projectId}/editor:generate-image
Idempotency-Key: <uuid>   (필수)
{ "mode": "fill", "slot": { "blockId": "<에디터 블록 id>", "elementId": "<이미지 요소 id>" } }
```

본문의 다른 필드는 읽지 않는다. 화면은 요청 전에 에디터를 저장한다. 상세페이지 생성 중에는 이 요청을 보내지 않는다(그동안의 수정은 서버에 저장되지 않는다).

접수(202):

```json
{
  "jobId": "…",
  "contextFill": {
    "slot": { "blockId": "…", "elementId": "…" },
    "label": "스타일링 · 왼쪽 사진과 같은 장소",
    "path": "similar",
    "cutType": "styling",
    "colorId": "col1"
  }
}
```

- `label`은 생성 중 칸 위에 보이는 한 줄이다. 줄표 없이 공백 포함 20자 이하로 쓴다. 3열 칸은 폭이 약 112px라 두 줄까지만 들어가기 때문이다. 착용 사진은 섹션 이름(첫 장면, 스타일링, 스튜디오), 제품 사진은 샷 이름(고스트샷, 디테일)으로 시작하고 가운뎃점 뒤에 고른 이유나 대상을 짧게 붙인다. 예: "스타일링 · 왼쪽 사진과 같은 장소", "스튜디오 · 옆모습", "디테일 · 소매 끝단", "고스트샷 · 블랙". 디테일 부위 이름이나 색 이름이 길어 20자를 넘으면 부위는 종류 이름(목선, 여밈, 주머니, 허리, 소매 끝, 밑단, 봉제, 표면, 원단, 라벨)으로 바꾸고, 색은 이름을 빼고 면(앞면, 뒷면)만 쓴다.
- `path`는 `new`(새 컷) 또는 `similar`(짝 사진의 비슷한 컷)다.
- 같은 칸의 진행 중 작업에 합류하면 그 작업의 `contextFill`을 돌려준다.

완료(작업 결과): 기존 `{ data, credits, creditsCharged }`이고, `data`에 `contextFill: { slot, label, colorId }`가 붙는다.

거절(작업과 예약을 만들지 않는다). 기존 오류 규약대로 `code`와 화면에 그대로 띄울 짧은 한국어 `message`를 함께 돌려준다.

| 상태 | 코드 | 경우 | message |
|---|---|---|---|
| 400 | `fill_slot_invalid` | slot 형식이 틀림 | 이 칸을 찾지 못했어요. |
| 409 | `fill_slot_not_found` | 저장된 에디터에 칸이 없음 | 저장 중이에요. 잠시 뒤 다시 눌러 주세요. |
| 409 | `fill_slot_not_empty` | 칸에 이미 사진이 있음 | 이미 사진이 들어 있는 칸이에요. |
| 400 | `fill_slot_planned` | 계획된 칸(다시 만들기로) | 이 칸은 원래 콘티대로 다시 만들어요. |
| 400 | `fill_slot_unsupported` | 정보 블록, 자동 블록, 숨긴 칸 | 이 칸은 AI로 채울 수 없어요. |
| 400 | `fill_slot_unsupported` | 생성 중인 칸 | 이 칸은 지금 만들고 있어요. |
| 409 | `page_generation_active` | 상세페이지 생성 중 | 상세페이지를 만드는 중이에요. 끝나면 눌러 주세요. |
| 409 | `fill_unavailable` | 만들 수 있는 컷이 없음 | 이 칸에 만들 수 있는 컷이 없어요. |

크레딧 부족(402), 실제 모델 생성 닫힘(409) 같은 기존 거절은 그대로다.

### 9. 칸에 넣기

- 서버는 에디터 블록을 쓰지 않는다. 결과는 의류 탭에 들어가고, 화면이 그 칸에 넣는다.
- 완료 때 그 칸이 아직 있고 이미지 칸이며 비어 있으면 넣는다. 그 사이 칸이 지워졌거나 다른 사진이 들어갔으면 의류 탭에만 둔다.
- 되돌리기는 기존 실행 취소다. 결과 사진은 의류 탭에 남는다.

### 10. 크레딧과 중복 방지

- 에디터 이미지 한 장 값(`credit_cost_editor_image`, 지금 19)이다. 판단에는 값을 받지 않는다. 실패하면 차감하지 않는다.
- 같은 `Idempotency-Key`는 같은 작업이다. 키가 달라도 같은 칸에 진행 중인 AI로 채우기 작업이 있으면 그 작업에 합류하고 새로 예약하지 않는다. 합류한 키는 기존 다시 만들기와 같은 방식으로 기억한다.
- 누른 뒤 2초 취소는 화면에서만 기다린다. 취소하면 요청이 없으므로 서버 취소 처리는 없다.

### 11. 기록

작업(`jobs.payload._contextFill`, `jobs.metadata.contextFill`)과 결과 자산(`assets.metadata.context_fill`)에 같은 판단 기록을 남긴다. 자산에는 `attempt`를 뺀다. 클라이언트가 보낸 `_contextFill`은 버린다.

```json
{
  "version": 1,
  "slot": { "blockId": "…", "elementId": "…" },
  "slotKey": "<blockId>:<elementId>",
  "purpose": "coordination",
  "rule": "pair_similar",
  "label": "스타일링 · 왼쪽 사진과 같은 장소",
  "path": "similar",
  "colorId": "col1",
  "anchorAssetId": "…",
  "attempt": 0
}
```

`rule`은 고른 규칙 코드다: `pair_similar`, `row_direction`, `page_direction`, `ghost_order`, `ghost_other_face`, `detail_unused`, `detail_to_ghost`, `color_compare`, `section_new`, `relax_other_color`, `relax_shot`, `section_default`.

결과 자산에는 생성 설정 `assets.metadata.generation`도 남긴다. 이 모양은 G6의 생성 설정 저장(색상, 열림 정도, 비슷한 컷 도구)과 함께 쓴다. G6는 이 기록으로 "같은 컷을 그 값만 바꿔 다시 만들기"를 하고, 메뉴의 지금 값과 비교, 교체할 원본을 찾는다.

```json
"generation": {
  "version": 1,
  "origin": "context_fill",
  "autoSelected": true,
  "sourceAssetId": null,
  "recipeFrom": "self",
  "recipe": {
    "sectionRole": "styling", "contentRole": "coordination", "cutType": "styling",
    "shot": "full", "direction": "front", "sideStyle": null, "colorId": "col1",
    "faceExposure": "same", "modelId": "mB", "matchIds": ["…"], "matchIdsOrigin": null,
    "refAssetIds": [], "refScope": "all", "exampleId": "…", "exampleSelectionOrigin": "auto",
    "outerClosureState": "open", "detailTargetId": null, "detailTargetOrigin": null,
    "spaceGroupId": null, "spaceVariation": null, "spaceSetMemberOrder": null,
    "horizonBackgroundMode": null
  }
}
```

- **필드 목록은 서버 상수 하나다.** `content_roles.GENERATION_RECIPE_FIELDS`에 위 22개를 둔다. 비슷한 컷 상속 목록(`_SIMILAR_RECIPE_FIELDS`)과 화면의 다시 만들기 목록(`failedCutRetry.js`의 `RETRY_FIELDS`)을 합치고, 화면용 값(`thumb`, `previewThumb`, `baseThumb`, `angle`), 없앤 값(`pose`, ADR-0015), 폐기된 값(`colorIds`), 화면용 사본(`refImages`, 생성에는 `refAssetIds`를 쓴다)을 뺀 것이다. `recipe`는 목록의 모든 키를 담고 값이 없으면 `null`이다. G6 2b와 다시 만들기가 같은 상수를 쓴다.
- **값은 서버가 실제로 생성에 쓴 값이다.** 정규화를 거친 뒤의 값을 작업자가 성공 때 기록한다. 열림은 `outer_closure.effective_state`를 거친 값, 방향은 예시 방향을 적용한 값, 시그니처 예시는 재배정 뒤의 값이다.
- **`origin` 값 목록.** `page`(상세페이지 생성), `editor_new`(새 이미지 추가), `editor_retry`(계획된 칸 다시 만들기), `editor_similar`(비슷한 컷), `editor_reshoot`(디테일 같은 부위 다시 촬영), `editor_color`, `editor_closure`(G6 2b), `context_fill`(AI로 채우기), `upload`(직접 올린 사진, `recipe`는 `null`).
- **`sourceAssetId`.** 변주의 원본 자산이다. 비슷한 컷과 다시 촬영은 고른 사진, AI로 채우기의 비슷한 컷은 짝 사진이고, 새 컷은 `null`이다.
- **`recipeFrom`.** 새 컷은 `self`다. 비슷한 컷은 원본 사진의 설정을 서버가 찾을 수 있으면 그 값을 넣고 `anchor`로 표시한다. 찾지 못하면 `recipe`는 `null`이다. 비슷한 컷의 원본 계보는 기존 `similar_cut` 기록이 맡는다.
- **누가 쓰나.** G11은 에디터 이미지 작업의 성공 경로 전부(`editor_new`, `editor_retry`, `editor_similar`, `editor_reshoot`, `context_fill`)에 쓴다. 같은 성공 처리 코드라 나눠 고치면 충돌한다. G6 2b는 `editor_color`, `editor_closure`와 상세페이지 생성 경로의 `page` 기록을 쓴다. G11은 상세페이지 생성 작업(`detail_page_job.py`)을 고치지 않는다. 직접 올린 사진은 `assets.source`가 이미 `upload`라서 기록을 쓰지 않는다.
- **읽는 쪽은 공용 함수 하나다.** `server/app/agents/asset_recipe.py`의 `resolve_asset_recipes(conn, user_id, project_id, asset_ids)`가 자산마다 `{ origin, recipe, recipeFrom, sourceAssetId, cutType, colorId, upload, realDerived }`를 돌려준다. 찾는 순서는 다음과 같다.
  1. 자산의 `generation` 기록.
  2. 페이지 생성 사진: 최근 완료한 상세페이지 작업 결과(`jobs.result.data`)의 블록에서 그 사진의 `sourceBlockId`를 찾고, 저장 콘티의 그 블록을 `canonicalize_storyboard_block`으로 정규화한 값.
  3. 이 기록 전에 만든 에디터 사진: 자산 키에 든 작업의 요청. 다시 만들기는 `retryBlockId`의 콘티 블록, 새 컷은 요청의 레시피 필드, 비슷한 컷은 원본 자산을 같은 순서로 다시 찾는다(한 단계만).
  4. `assets.source`가 `upload`면 레시피 없음.
  5. 그 밖에는 의류 목록의 컷 종류와 색 그룹만.
  
  판단 규칙과 G6 2b가 같은 함수를 쓴다. 이 함수는 읽기만 하고 아무것도 쓰지 않는다.
  
  한계: 2번 값은 콘티에 저장된 요청 값이라, 서버가 생성 때 바꾼 값(열림 보정, 시그니처 예시 재배정, 매칭 대체)과 다를 수 있다. G6 2b가 상세페이지 생성 경로에 `page` 기록을 쓰기 시작하면 그 뒤에 만든 사진은 1번으로 찾는다.
- **비슷한 컷 결과의 색 그룹.** 지금은 비슷한 컷 결과의 색 그룹이 비어 의류 탭 '기타'로 간다(`editor_image_job.py` 383행). 이번에 모든 비슷한 컷 결과가 원본 사진의 의류 색 그룹을 물려받게 고친다. AI로 채우기의 비슷한 컷도 같다.

### 12. 화면과의 경계

- G11은 서버 판단, API, 클라이언트 서비스 함수(`src/lib/api`의 `fillEmptySlot`), 칸 가르기 함수(`src/lib/editorSlotKind.js`의 `editorSlotKind`), 사진 설정을 찾는 공용 함수(`asset_recipe.resolve_asset_recipes`), 에디터 이미지 결과의 생성 설정 기록과 비슷한 컷 색 그룹 수정, 서버와 프론트 단위 시험을 맡는다. 상세페이지 생성 작업은 고치지 않는다.
- 빈 칸 메뉴, 2초 취소, 생성 중 표시, 도착, 칸에 넣기 연결은 G6가 시안 I1~I3대로 만든다. 임시 버튼은 만들지 않는다. 출시 일정에 G6가 늦을 것 같으면 그때 오너에게 다시 묻는다.

## 버린 안

- **마지막 고르기에 AI 판단 한 번 더하기.** 2~5초 늦어지고, 같은 칸에서 답이 달라질 수 있고, 실패 경로가 하나 는다. 얻는 것은 직접 올린 사진 옆 칸의 분위기 맞추기 정도인데, 직접 올린 사진은 짝으로 쓰지 않는다. 후보 만들기와 고르기를 나눠 두어 나중에 고르기만 바꿀 수 있다.
- **짝 칸도 늘 새 예시로 만들기.** 장소가 달라져 짝이 따로 논다. 새 예시로 같은 장소를 맞추려면 에디터 새 이미지에 장소 세트를 열어야 해서 범위가 커진다.
- **클라이언트가 레시피를 정해 보내기.** 클라이언트가 임의 사실을 생성 근거로 보내지 않는다는 원칙(ADR-0012)과 어긋나고, 접수 단계의 모델 처리 때문에 착용컷 모델이 빠질 수 있다.
- **새 컷이 없으면 거절하기.** 빈 칸이 남는다. 마지막 대체는 목적의 기본 컷으로 채우고 기록에 이유를 남긴다.
- **G6 전까지 의류 탭 안내 띠에 임시 버튼 두기.** 오너가 빈 칸 화면을 고쳐 확정하는 중이라 만들었다 버리는 일이 된다.

## 바꾸지 않는 것

계획된 칸의 다시 만들기(ADR-0017), 비슷한 컷 경로(ADR-0016), 생성 엔진과 검수, 상세페이지 생성 작업, 에디터 이미지 단가, 실패 미차감, 저장 계약(blocks)의 모양, DB 스키마. 새 마이그레이션은 없다.

## 검증

- 서버 단위 시험: 배치별 판단(2열 오른쪽, 3열 가운데, 2×2 아래 줄, 1컷 풀폭, 페이지 맨 위, 디테일 칸, 디테일 대상 없음, 제품 2칸, 컬러 비교, 직접 올린 사진 옆, 여밈 없는 아우터), 칸 가르기, 반복 피하기, 다시 누르면 다음 후보, 대체 순서, 거절 코드별 무예약과 message, label 20자 이하, 같은 칸 합류, 같은 키 재생, 착용 새 컷의 모델 유지, 기록 모양(필드 상수 전부, 정규화 뒤 값, origin과 sourceAssetId), 에디터 이미지 결과 다섯 종류의 origin, 공용 함수의 찾는 순서(기록, 상세페이지 결과, 옛 에디터 작업 요청, 업로드, 의류 목록), 일반 비슷한 컷과 AI로 채우기 비슷한 컷의 색 그룹, 실패 미차감.
- 프론트 단위 시험: 칸 가르기 함수 표, 서비스 함수의 요청 모양(본문은 mode와 slot만, 키 헤더 필수)과 접수 응답 전달, 목 어댑터.
