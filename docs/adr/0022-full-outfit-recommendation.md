# ADR-0022: 실제 아이템으로 전체 코디 추천과 생성 연결

상태: 2026-10-13 사용자 구현 승인. 카탈로그 자료는 오너가 나중에 등록한다. 2026-10-17 화면 확정에 따라 개정(맨 아래 "2026-10-17 개정" 절이 앞 절보다 우선한다). 번호는 main의 ADR-0021(팔레트 C)과 겹쳐 0022로 옮겼다.

## 목적과 범위

분석페이지 최초 진입 때 업로드한 판매 의류에 맞는 전체 코디를 Gemini 3.8 Flash로 추천한다. 사용자는 서버에 등록된 실제 이너, 보완 의류, 신발, 가방, 액세서리 중에서 선택을 수정할 수 있다. 사용자 업로드는 기존 매칭 의류 한 벌만 허용한다. 새 아이템 이미지 제작과 운영 카탈로그 등록, 유료 실측, 배포는 이번 로컬 구현에 포함하지 않는다.

판매 상품의 색, 디테일, 핏이 정본이다. 선택한 실제 코디 아이템은 생성예시보다 우선한다. 예시에만 있는 옷과 소품은 가져오지 않는다. 제품 단독컷에는 코디 참조를 붙이지 않는다.

## 분기

- outer: inner, bottom, footwear, bag, accessory.
- top: bottom, footwear, bag, accessory.
- bottom: top, footwear, bag, accessory.
- dress: footwear, bag, accessory. 기존 원피스의 상하의 미추천을 유지한다.
- 하위 분류는 기존 subCategory와 customCategory를 문맥으로 사용한다. 티셔츠, 맨투맨, 셔츠, 니트와 면바지, 트레이닝 팬츠, 청바지, 슬랙스, 스커트, 아우터 셔츠, 재킷, 가디건, 패딩, 코트를 각각 설명한다. 없는 사용자 속성을 꾸며내지 않는다.
- 각 역할 최대 1개. 후보가 없는 역할은 비운다. 서버 matching_items의 기존 top, bottom에 inner, shoes, bag, accessory 유형을 추가 등록할 수 있다. footwear 역할은 shoes 유형을 사용한다. 새 유형의 사용자 커스텀 업로드는 금지한다.

## 저장 계약

기존 matchClothing과 matchIds는 보완 의류 한 벌의 호환 계약을 유지한다. 새 역할을 이 배열에 섞거나 LIMITS.matchClothingMax를 늘리지 않는다.

```json
{
  "outfitSelections": {
    "version": 1,
    "slots": {
      "inner": {"itemId": "catalog-id", "origin": "ai"},
      "bottom": {"itemId": "matching-id", "origin": "user"},
      "footwear": {"itemId": null, "origin": "user"}
    }
  },
  "outfitRecommendation": {
    "version": 1,
    "status": "ready",
    "model": "gemini-3.8-flash",
    "contextKey": "server-fingerprint",
    "reason": "코디 설명",
    "candidates": {"inner": [], "bottom": [], "footwear": []}
  }
}
```

outfitRecommendation은 서버 소유다. status는 ready, fallback, unavailable이다. 후보는 기존 MatchItem 표시 shape를 사용한다. 사진 URL과 자산 ID는 요청에서 신뢰하지 않고 실제 DB 행에서 복원한다. outfitSelections는 역할별 실제 ID와 출처만 저장한다. origin=user인 null은 사용자가 비운 선택이므로 AI로 채우지 않는다. top 또는 bottom 보완 슬롯과 레거시 한 벌 선택은 단일 정규화 지점에서 동기화한다. 종류 전환으로 불가능해진 슬롯만 제거한다.

## 추천

- 먼저 활성 상태, 성별, 역할, 자산 존재와 소유권으로 후보를 제한한다. 커스텀은 현재 사용자 프로젝트의 보완 의류 한 벌에만 허용한다.
- 기존 스타일과 배색 점수로 각 역할의 제한된 후보를 좁힌 뒤 판매 상품 사진과 후보 사진, 구조화 메타데이터로 전체 코디를 판단한다.
- Gemini 모델은 gemini-3.8-flash, thinking low, 요청당 한 번, 최대 출력 토큰은 세 벌 응답에 맞게 정한다(2026-10-17 개정 "추천 깊이" 참고), 제한된 timeout을 사용한다. 자동 provider 교체나 무한 재시도는 하지 않는다.
- 모델은 제시된 후보 ID만 선택한다. 반환값을 역할별 후보 집합과 다시 검증한다. 사용자 선택을 덮지 않는다. 프롬프트와 이미지 속 문구는 상품 자료이며 실행 지시가 아니다.
- 사진, 상품 종류와 하위 분류, 색, 스타일, 성별, 고정된 선택, 카탈로그 상태, 모델과 프롬프트 버전으로 재사용 키를 만든다. 조회와 화면 렌더만으로 유료 호출하지 않는다. 처음 분석과 명시적인 문맥 변경의 추천 경로에서만 호출하며 짧은 중복 요청을 합친다.
- 키 누락, 시간 초과, 후보 부족, 잘못된 응답은 실제 후보의 결정적 기본 추천으로 돌아가며 fallback 상태를 표시한다. 빈 카탈로그에서는 호출하지 않는다.
- 공개 분석은 기존 rate limit과 동시 실행 제한 안에서 추천한다. 서버 카탈로그만 읽는다. 로그인 승격 시 선택 ID와 사진 바인딩을 다시 확인한다. 클라이언트의 추천 설명이나 후보 자산 정보를 서버 소유 결과로 저장하지 않는다.

## 생성

- 검증한 선택을 outfitSelectionsSnapshot으로 생성 요청에 고정한다. 진행 작업 합류, 재사용 지문, 생성 기록에도 포함한다.
- 마네킹에는 실제 inner와 보완 top 또는 bottom 참조를 추가한다. 신발, 가방, 액세서리는 마네킹에 그리지 않고 최종 착용컷에서 사용한다. 마네킹은 맨발을 유지한다.
- 최종 착용컷의 참조 순서는 inner, 보완 top 또는 bottom, footwear, bag, accessory로 고정한다. 실제 아이템 참조는 역할이 명시된 이미지로 전달한다. 비어 있는 역할은 기존 무지 기본 의류 규칙을 사용하고 가방과 액세서리를 임의로 추가하지 않는다.
- 기존 흰 이너 강제와 예시별 fixedInner, fixedFootwear는 해당 실제 참조가 없을 때의 기본값으로만 사용한다.
- confirmed GPT는 실제 역할 참조를 지원하는 명시적 계약으로 확장한다. 기존 v1 무참조 호출을 유지하며 오류를 generic으로 조용히 전환하지 않는다.
- 컷의 matchIds override는 보완 의류 슬롯만 바꾼다. 나머지 선택은 같은 스냅샷을 유지한다. 실패 컷 재시도와 비슷한 컷은 원본 recipe의 실제 착장을 유지한다.
- 이미 선택한 아이템을 읽을 수 없으면 다른 신발이나 가방으로 조용히 바꾸지 않는다. 기존 보완 의류 대체 정책은 그 역할에만 유지하고 실제 대체 ID를 기록한다.

## 화면 기준

(2026-10-17 개정 절의 화면 기준이 이 절을 대체한다.)


주 기준은 현재 AnalysisForm과 DESIGN.md다. 기존 orb, 글래스, 글꼴, 사진 타일 비율, 검정 선택 표시, 알약 버튼을 유지한다. 기존 매칭 의류 영역에 역할별 사진 선택을 추가한다. AI가 먼저 추천하며 등록된 항목만 표시한다. 상품 정보가 바뀌는 동안 도착한 오래된 응답은 새 선택을 덮지 않는다. 모바일과 태블릿은 기존 사진 입력 후 PC 이어하기 정책을 유지한다.

보조 참고는 refero-design의 craft-details.md와 copywriting.md다. 키보드 선택, focus-visible, 이미지 크기 예약, 짧은 상태 문구를 적용한다. 별도 색상 테마나 가상의 신발 샘플은 추가하지 않는다.

## 검증

종류와 하위 분류 분기, 사용자 선택과 비움 보존, 빈 풀 무호출, 허위 ID 거부, 프로젝트 소유권, 초기 공개 분석, 승격과 복원, 오래된 응답, 모든 생성 경로의 참조 순서와 스냅샷, 제품컷 제외를 테스트한다. 유료 API는 모킹한다. 실제 Gemini와 이미지 생성 검증은 건수와 비용을 제시하고 오너 승인 후 수행한다.

## 구현 확인

- 추천 모델은 `gemini-3.8-flash`로 고정한다. `OUTFIT_RECOMMENDATION` 기본값은 `off`이며, 이때 유료 호출 없이 결정적 폴백만 쓴다. 운영에서 `on`으로 켜는 것은 비용 승인 뒤 환경 변수로 한다. `OUTFIT_TIMEOUT_SECONDS` 기본값은 12초이며 설정 허용 범위는 1~30초다. 모델 후보 수는 `OUTFIT_CANDIDATES_PER_ROLE` 기본 6, 허용 2~8이다. 범위 밖 정수는 경계값으로 제한하고 빈 값·잘못된 문자열은 6을 쓴다. 색 묶음 제한 때문에 실제 후보 수는 더 적을 수 있다. 화면의 선택 목록은 전체 유효 후보를 유지한다.
- 신발 역할은 `clothing_type='shoes'`이며 `inner`, `bag`, `accessory`도 같은 서버 카탈로그의 공용 활성 행으로 등록한다. 실제 공개 seed 이미지와 썸네일이 필요하다. 사용자 업로드를 이 유형으로 등록하는 새 API는 만들지 않는다. 현재 카탈로그는 top과 bottom만 있으므로 추가 유형은 자료 등록 전까지 비어 있다.
- 필터와 자동 선택은 옛 AI 선택에 고정되지 않는다. 사용자의 ID와 명시적 null만 고정한다. 가방과 액세서리는 세트에 미리 포함하되 AI가 상품을 가린다고 판단하면 null로 생략할 수 있다. 결정적 폴백도 후보가 있으면 세트에 넣지만 소품 토글 기본값은 false라 생성·미리보기에는 켜기 전까지 포함하지 않는다.
- 추천 키는 사진, 정규화된 상품 종류와 하위 분류, 색, 핏, 소재, 스타일, 성별, 사용자 선택, 카탈로그 상태와 프롬프트 버전을 포함한다. 공개 추천 승격은 같은 사진이라도 알려진 색, 핏, 소재가 달라졌으면 거절한다. 사진 업로드 과정의 ID 재배정과 비어 있던 정보의 자동 채움은 구분한다.
- 실제 추가 아이템의 `{role,itemId,assetId,imageSha256}`를 `outfitReferenceAssets`로 생성 recipe에 기록한다. 과거 사진의 재시도와 열림 편집은 현재 분석 선택이 아닌 원본 기록을 따른다.
- 분류별 모델 지침과 색상, 명도, 채도, 보이는 면적, 질감, 실루엣, 신발의 무게감 기준을 프롬프트에 포함한다. 동색, 블랙과 네이비, 블랙과 브라운을 일률적으로 금지하지 않는다.

## 2026-10-17 개정 (화면 확정 v18 반영)

오너가 분석 페이지 2단계 시안 v13~v18을 거쳐 화면을 확정했다. 화면 정본은 `.scratch/analysis-v12-20261015/UI_SPEC_FINAL_v18.md`(메인 폴더)와 시안 `mockups/analysis_redesign_20261012/v18_edit.html`이다. 이 절은 그중 데이터와 서버에 닿는 결정만 적는다. 앞 절과 다르면 이 절을 따른다.

### 추천 세 벌

- 추천 결과는 완성 코디 최대 3벌이다. `outfitRecommendation.sets`는 길이 1~3의 배열이고, 각 원소는 `{"slots": {역할: itemId 또는 null}, "reason": 짧은 설명}`이다. 역할마다 그 상품 종류의 역할 집합(분기 절)만 쓴다. 모델은 세트에 넣지 않는다(셀러가 고른다).
- Gemini 호출은 지금처럼 요청당 한 번이고, 한 응답에 세 벌을 받는다. 세 벌은 서로 다른 조합이어야 하고, 같은 아이템이 두 세트에 들어가도 된다. 응답 검증(후보 ID만, 역할 집합만)은 세트마다 한다. 세 벌을 다 못 채우면 채운 만큼만 둔다.
- 결정적 폴백도 같은 모양으로 세 벌까지 만든다. 고르는 규칙은 아래 "추천 깊이"의 다양성 추리기다(점수 순만으로 고르지 않는다).
- `candidates`(역할별 화면 목록)는 그대로 둔다. 각 후보에 `inSets` 표시(세 벌 중 하나에 들어 있는지)를 더해, 화면이 "AI 추천" 알약을 그 후보에만 단다.
- 세트 설명(`reason`)은 저장하지만 화면에 쓰지 않는다(오너 10/17, 미리보기 아래 문구 없음).

### 선택 저장

- `outfitSelections`에 `setIndex`(지금 적용한 세트, 0부터)를 더한다. "AI 추천" 버튼은 다음 세트를 적용한다. 세트를 적용하면 셀러가 비운 칸(origin user, itemId null)은 비운 채 두고, 나머지 칸은 그 세트의 것으로 바꾼다(셀러가 직접 고른 옷도 바뀐다, 오너 10/16). 모델 선택은 바꾸지 않는다.
- 가방과 액세서리는 켜고 끄는 소품이다. `outfitSelections.optional`에 `{"bag": false, "accessory": false}`를 둔다. 처음 값은 둘 다 false(꺼짐)다. 켜면 그 칸의 슬롯 값(있으면 셀러가 전에 고른 것, 없으면 지금 세트의 것)을 쓴다. 끄면 슬롯 값은 기억해 두되 생성과 미리보기에서 뺀다. 세트를 적용할 때 꺼진 소품은 꺼진 채 둔다.
- 생성 스냅샷(`outfitSelectionsSnapshot`)과 참조 기록은 켜진 소품만 넣는다.

### 추천 시점과 상태

- 추천은 분석 결과가 저장되는 즉시 서버 뒤에서 시작한다(공개 분석과 로그인 분석 모두). 셀러가 분석 화면을 보는 동안 끝나는 것이 목표다. 재사용 키와 중복 합치기 규칙은 그대로라 화면 진입이나 조회는 유료 호출을 만들지 않는다.
- 상태에 `pending`(진행 중)을 더한다. `pending`인 동안 조회하면 결정적 폴백 세트를 함께 돌려준다(`sets`와 `fallbackReady: true`). 화면은 2단계에 들어왔을 때 아직 `pending`이면 뼈대를 잠깐(최대 1.5초) 보이고, 그때도 아니면 폴백 세트로 채워 바로 고르게 한다. 확정 버튼을 잠그고 기다리게 하지 않는다.
- AI 결과가 나중에 도착하면 셀러 선택을 덮지 않는다. 화면이 "AI 코디 보기"로 알리고, 셀러가 누를 때만 적용한다.
- 시간 제한은 `OUTFIT_TIMEOUT_SECONDS`(기본 12초, 1~30초)를 그대로 쓴다. 넘으면 `fallback`이다.
- `unavailable`은 그 역할의 카탈로그 자료가 없을 때만이다. 자료가 없는 역할의 줄은 화면에서 숨긴다(출시 전 빈 줄 숨김, 오너 10/16).

### 추천 깊이 (2026-10-17 오너 승인, 앞 절의 후보 수와 폴백 규칙을 대체)

- 오너가 10/13 구현의 추천이 얕다는 Claude 점검(역할마다 후보 2개, 규칙 점수가 사실상 선택)을 보고 깊게 하라고 승인했다.
- AI에 보내는 후보 수는 `OUTFIT_CANDIDATES_PER_ROLE`(기본 6, 허용 2~8)이다. 기존 역할별 2개 제한을 이것으로 대체한다. 화면 목록(`candidates`)은 전체 유효 후보다.
- 후보 추리기는 점수 순에 다양성을 섞는다. 같은 색 묶음은 역할마다 최대 2개이고, 스타일 태그가 겹치는 후보는 뒤로 미룬다. 셀러가 고정한 아이템은 언제나 넣는다. 같은 입력이면 같은 결과가 나와야 한다(결정적). pending과 fallback의 결정적 폴백 세 벌도 이 규칙으로 고르고, 세 벌이 서로 다르게 만든다.
- 프롬프트는 v2(`outfit_recommendation_v2.txt`)이고, 버전은 재사용 키에 들어간다. 세 벌은 서로 다른 방향이다. 각 세트는 `slots`, `reason`, `concept`(내부용 짧은 영문 키워드)를 가진다. `concept`은 `outfitRecommendation.sets[].concept`에 저장한다. 화면과 클라이언트 서비스 계약에는 쓰지 않고, 클라이언트는 이 필드가 없어도 동작해야 한다(B가 쓰는 공개 모양 `{slots, reason}`은 그대로).
- 응답 검증에 다양성 검사를 더한다. 후보가 2개 이상인 역할 기준으로 두 세트가 하나도 다르지 않으면 뒤 세트를 버린다.
- 최대 출력 토큰은 4096을 유지한다. 최대 다섯 역할 × 세 벌, 36자 UUID, 세트당 한국어 설명 200자와 concept 48자의 JSON envelope는 공백 없는 직렬화 기준 1,588자/UTF-8 2,788바이트다. 이는 토큰 실측이 아니며, 실제 토크나이저와 thinking 사용량·완료율을 아직 측정하지 않았으므로 한도를 낮출 근거가 없다. 한 요청에서 세 벌을 받고 `reason` 200자, `concept` 48자, `sets` 최대 3개를 스키마와 서버 검증으로 제한한다. 유료 실측 뒤 조정한다.
- 유료 추천 스위치 `OUTFIT_RECOMMENDATION`의 기본값은 off다. off면 결정적 폴백 세 벌만 쓰고 유료 호출은 0이다. 운영에서 켜는 것은 오너가 비용을 승인한 뒤 환경 변수로 한다. 앞 "구현 확인" 절의 설명보다 이 줄이 우선한다.

#### A2 구현 세부 (2026-10-17)

- 후보는 기존 스타일 0.7 + 배색 0.3 점수에서 이미 뽑은 후보와의 최대 스타일 태그 Jaccard 중복도 × 0.25를 빼며 탐욕 선택한다. 동률은 `sort_order`, ID 순이다. 고정 ID를 먼저 넣어 색 묶음 한도에 포함한다. 색 묶음·태그는 공백과 대소문자를 정규화하며, 색 묶음 미상도 하나의 묶음으로 취급해 최대 두 개다. 전체 화면 후보 목록은 추리지 않는다.
- pending, off, 모델 실패, 공개 캐시 소멸의 폴백 모두 같은 추린 후보를 쓴다. 첫 세트는 각 역할 첫 후보, 다음 세트는 앞선 세트들과 달라지는 역할 수의 최솟값을 최대화한다. 동률이면 후보 순번 합과 역할 순번으로 고른다. 사용자 고정 ID와 null을 지킨다. 가능한 조합이 적으면 1~2벌이다.
- 검증은 모델에 실제 보낸 후보가 2개 이상인 역할만으로 조합을 비교해 뒤의 중복을 버린다. 동일 `concept`도 뒤의 세트를 버린다. 한 벌 이상 남으면 ready다. 잘못된 ID·역할·concept 또는 고정 선택 변경은 폴백으로 돌아간다. 과거 저장 세트에 concept이 없어도 조회·승격은 허용한다.
- `sets[].concept`은 서버 저장·캐시 및 서명된 승격용 handoff 내부에 보존하고 화면용 응답의 세트에서는 제거한다. 기존 `{slots, reason}` 공개 계약과 DB 스키마는 바꾸지 않는다.
- 재사용 키에 `outfit_recommendation_v2`, 후보 수 설정, 유료 스위치 상태를 포함한다. off 요청은 on 상태의 진행 캐시에 합류하지 않는다. 조회는 스위치 상태와 무관하게 유료 요청을 만들지 않는다.
- 상품은 원본 `Front`만 최대 변 512px, 후보는 `thumb_key` 정돈 썸네일을 최대 변 256px로 종횡비를 유지해 JPEG로 보낸다. 투명 영역은 흰 배경에 합성한다. Front가 없거나 이미지를 읽을 수 없으면 유료 호출 없이 폴백한다. 원본 상품의 정돈 사진은 판단 입력으로 쓰지 않는다.
- `cd server && .venv/bin/python scripts/outfit_dry_run.py`는 각 역할 24개, 여섯 색 묶음의 합성 메타데이터와 로컬 PNG로 실제 요청 준비 경로를 실행한다. 기본 후보 6개일 때 상의+하의만 7장, 상의+모든 역할 25장, 아우터+모든 역할 31장이다. 상품 fixture는 384×512px, 후보는 256×256px다. user+system 프롬프트는 각각 5,333 / 10,909 / 12,737자이고 응답 스키마는 별도로 778 / 1,507 / 1,800자다. `--candidates-per-role 8`의 아우터 상한은 41장이다. 이 수치는 토큰·가격이나 실제 카탈로그 품질 측정이 아니다.

## 2026-10-19 개정 (소품은 켤 때 따로 추천, 액세서리 여러 개)

오너가 10/19에 정했다. 앞 절과 다르면 이 절을 따른다.

### 처음 추천에서 소품을 뺀다

- 분석 저장 때 시작하는 처음 추천(Gemini와 결정적 폴백 모두)은 inner, 보완 top 또는 bottom, footwear만 고른다. bag과 accessory 후보는 AI 요청에 넣지 않고 `sets[].slots`에도 넣지 않는다. 프롬프트는 v3(`outfit_recommendation_v3.txt`)이고 버전은 재사용 키에 들어간다.
- 화면 후보 목록(`candidates.bag`, `candidates.accessory`)과 자료 없는 줄 숨김(`unavailable`)은 그대로다.
- 예전에 저장된 세트에 bag, accessory가 있어도 읽기는 허용한다. 소품의 정본은 아래 `props`다.
- 처음 추천의 후보 사진은 한꺼번에 받는다. 시간 제한 기본값은 30초다(분석 저장 뒤 뒤에서 돌기 때문). 허용 범위 1~30초는 그대로다.

### 소품 추천은 켤 때 따로 한다

- 셀러가 가방이나 액세서리 줄을 켜면 그 소품만 따로 추천한다. 입력은 판매 상품(원본 Front 사진과 상품 문맥)과 그 소품의 후보뿐이다. 셀러가 고른 옷, 지금 세트, 다른 소품은 보내지 않는다(오너 10/19, 이미 고른 것이 있든 없든 상품 전체를 보고 추천).
- 결과는 서버 소유 `outfitRecommendation.props.<bag|accessory>`에 `{"status": "pending|ready|fallback|unavailable", "picks": [itemId, 최대 3개]}`로 둔다. picks는 서로 다른 아이템이고, 액세서리는 서로 다른 종류(category)를 먼저 고른다.
- i번째 세트를 적용할 때 켜진 소품은 `picks[i % picks.length]`를 쓴다. 처음 켤 때는 지금 `setIndex`의 pick을 쓴다. 세트 적용 규칙은 10/17 절과 같다. 셀러가 비운 칸(origin user, itemId null)만 비운 채 두고, 셀러가 고른 소품도 세트의 것으로 바뀐다. 액세서리는 세트를 적용하면 그 세트의 pick 하나만 남는다.
- 유료 호출은 (상품 문맥 키, 소품 역할)마다 한 번이다. 키는 처음 추천 키에서 사용자 선택을 뺀 것(사진, 상품 종류와 하위 분류, 색, 핏, 소재, 스타일, 성별, 그 역할의 카탈로그 상태, 소품 프롬프트 버전, 유료 스위치 상태)이다. 끄고 다시 켜거나 세트를 넘겨도 다시 부르지 않는다. 조회와 화면 렌더는 유료 호출을 만들지 않는다. 짧은 중복 요청은 합친다.
- `OUTFIT_RECOMMENDATION`이 off면 결정적 규칙으로 바로 picks를 만든다(status fallback, 기다림 없음). on이면 Gemini 3.8 Flash를 한 번 부른다. 프롬프트는 `outfit_props_v1.txt`, 후보 수는 `OUTFIT_CANDIDATES_PER_ROLE`이다. 액세서리 후보 추리기는 같은 종류를 최대 2개로 둔다. 시간 제한은 `OUTFIT_PROPS_TIMEOUT_SECONDS`(기본 10초, 1~30초)다.
- pending 동안 화면은 그 소품 줄의 썸네일과 이름 칸, 미리보기 보드의 그 소품 자리를 회색 로딩 모션으로 보인다. 스위치는 켜진 채다. 확정 버튼은 잠그지 않는다. pending 중에 확정하면 결정적 picks를 쓴다.
- 시간 초과, 실패, 잘못된 응답은 결정적 picks(fallback)로 돌아가고 화면에 오류를 띄우지 않는다.
- pending 동안 셀러가 그 줄에서 직접 고르면 그 선택을 지키고, 도착한 picks는 다음 세트 적용부터 쓴다.

### 액세서리는 여러 개

- 액세서리는 최대 3개, 종류(category)마다 1개다. 가방은 1개 그대로다. 모자는 액세서리의 한 종류(`모자`)이고, 카탈로그에 없으면 보이지 않는다.
- 저장은 `slots.accessory = {"itemId": 첫째, "extraIds": [둘째, 셋째], "origin": ...}`이다. `itemId`만 있는 예전 값은 그대로 읽는다. `extraIds`는 `itemId`가 있을 때만 쓰고, 서버가 중복, 같은 종류, 넷째 이상, 액세서리가 아닌 아이템을 거른다.
- 생성은 켜진 액세서리 전부를 최종 착용컷 참조로 넣고, 아이템마다 accessory 역할 라벨을 붙인다. `outfitReferenceAssets`에도 아이템마다 기록한다. 마네킹에는 그리지 않는 규칙은 그대로다.
- 화면 줄은 하나 그대로다. 썸네일은 첫째 그림, 이름 칸은 "첫째 이름 외 N개"다. 펼친 격자와 전체 보기는 눌러서 넣고 빼는 방식이고, 같은 종류를 누르면 그 종류의 것이 바뀐다. 3개가 찬 상태에서 새 종류를 누르면 한 줄 안내로 알린다. 액세서리 전체 보기에는 색 칩 위에 종류 칩(있는 종류만)을 둔다. 미리보기 보드는 가방을 왼쪽에, 액세서리를 오른쪽에 위에서 아래로 쌓는다.

### 독립 배포 중 선택과 추천 결과를 지킨다

- 프런트는 `GET /v1/public/outfit-capabilities`의 현재 서버 응답으로 소품 요청과 액세서리 여러 개 저장 지원을 확인한다. 이 조회는 AI나 DB를 호출하지 않으며, 유료 추천 스위치와 별개다. 구버전 서버이거나 지원 확인이 안 되면 기존 한 개 선택과 규칙 추천을 사용한다.
- 이미 액세서리를 여러 개 고른 초안은 구버전 서버에 첫째만 저장한 채 확정하지 않는다. 저장과 승격 응답에서도 선택 보존을 확인하고, 누락되면 선택을 유지한 채 다시 시도할 수 있게 한다.
- 서버 교체용 `OUTFIT_PROPS_READY`는 유료 추천 스위치와 별개다. 기본값은 off이며 준비 전 지원 응답은 `props: false, maxAccessories: 1`이다. 준비 전에는 여러 액세서리의 저장과 승격, 생성 요청을 쓰기와 작업 생성 전에 거부한다. 프런트도 여러 개를 저장하기 직전에 캐시되지 않는 지원 상태를 다시 확인한다.
- 첫 도입(#571, 2026-10-19)은 상세 워커를 먼저 반영하고 `OUTFIT_PROPS_READY=off`인 API로 구버전 태스크를 모두 교체한 뒤, 같은 코드에 준비 값만 on으로 바꿔 다시 배포했다. 이후 운영 API와 상세 워커가 모두 여러 액세서리를 지원하므로 2026-10-19부터 배포는 한 번이고 준비 값은 manifest에서 항상 on이다. off는 비상 스위치로만 쓴다. 저장 계약을 다시 바꾸는 변경은 그때 단계 배포를 따로 정한다. 작업 소비자는 준비 값과 무관하게 여러 액세서리를 유지한다.
- 구버전 API는 이후 생성 요청이나 에디터 작업에서도 여러 액세서리를 하나로 줄일 수 있으므로 지원 확인 조회만으로 배포 완료를 대신하지 않는다. 여러 액세서리를 저장한 뒤에는 이를 지원하지 않는 서버로 되돌리지 않는다.
- 공개 분석의 기본 캐시가 만료된 뒤 같은 handoff로 소품을 연달아 요청해도, 다음 handoff와 상태 조회에는 두 역할의 진행 상태와 완료 결과를 함께 보존한다. 조회를 위해 캐시를 복원할 때는 서명된 선택도 함께 보존하며 새 유료 호출을 만들지 않는다.
