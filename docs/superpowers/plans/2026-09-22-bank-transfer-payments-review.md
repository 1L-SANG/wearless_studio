**도달 경로**

**구체적 대안**

2. 이월을 유지하려면 같은 이용권에 속한 기존 활성 버킷의 표시 종료일도 함께 연장한다. 수동 이용권과 각 `credit_source_id`의 명시적 연결을 남겨, 최종 종료 때 그 이용권 소속 버킷만 잠그고 소멸 원장과 잔액을 갱신한다. 사용자 전체를 대상으로 하는 기존 함수를 무조건 호출하지 않는다.
3. 다른 플랜으로 즉시 교체하면서 예전 크레딧을 예전 종료일까지 유지하려면, `status='ended', ended_reason='replaced'`인 이용권의 버킷도 기한에 맞춰 정리해야 한다. `active` 이용권만 훑는 지시서 쿼리로는 빠진다. **추천은 첫 버전에서 다른 플랜의 중도 교체를 거절하고 종료 후 새 신청을 받는 것**이다. 교체를 유지한다면 버킷별 소속과 별도 기한 정리를 구현 범위에 넣어야 한다.
4. 만료 작업 기동은 토스 설정과 분리한다. 현재 `server/app/main.py:195`는 `subscription_billing_enabled`일 때만 청구 워커와 만료 워커를 함께 시작하고, 기본값은 false다(`server/app/config.py:401`). 새 `BankTransferExpirer`를 별도 모듈과 API 수명주기에 두면 기존 청구 로직을 건드리지 않을 수 있다. 신규 판매를 꺼도 기존 이용권과 신청 정리는 계속 실행해야 한다. 다중 인스턴스용 advisory lock과 사용자별 트랜잭션을 둔다.

## 3. [차단] `grant_subscription`은 `payment_history`를 남기지 않음

**근거**

- 반면 `purchase_topup`은 `server/app/repo.py:3316`에서 `payment_history`를 만들고, `:3324`에서 버킷의 `payment_id`에 연결한다. `supabase/migrations/20260620100000_credit_subscription_system.sql:36`은 결제 내역의 `kind='subscription'`을 이미 허용한다.

**도달 경로**

예정된 관리자의 구독 입금 확인. 지시서의 “이미 남기면 중복으로 넣지 않는다”를 실제 동작 확인 없이 생략 조건으로 삼으면 수동 결제 내역이 빠진다. 충전 쪽에 별도 결제 기록을 추가하면 반대로 중복된다.

**구체적 대안**

신규 관리자 확인 서비스의 **같은 DB 트랜잭션 안에서** 구독 결제 내역 한 건을 명시적으로 생성한다. 값은 신청의 `user_id`, 상품 `plan_id`, 스냅샷 `amount`, `kind='subscription'`, `provider='bank_transfer'`, `status='paid'`다. 안정적인 `provider_ref`는 신청 ID로 두고, 입금자명과 입금일은 신청 및 감사 기록에 남긴다. 지급 뒤 반환된 `creditSourceId`에 `payment_id`를 연결한다. 신청에도 결제, 버킷, 수동 이용권 참조를 각각 보관하는 편이 다형적인 `grant_ref text` 하나보다 명확하다.

충전은 `purchase_topup`이 만든 기록을 그대로 사용한다. 결제 기록, 이용권, 버킷, 원장, `profiles.plan`, 신청의 paid 전이, 감사 기록 중 하나라도 실패하면 모두 롤백한다. 메일은 커밋 후 보내고 실패가 지급 결과를 뒤집지 않게 한다. 실제 입금 시각은 별도의 `paid_at`을 조회해 보여준다. `payment_history.created_at`을 입금 시각으로 해석하지 않는다.

## 4. [권고] 종류당 한 건은 유지하되, 3일 만료와 늦은 확인을 구분

**근거**

- `지시서:69`, `:91`은 만료 워커가 상태를 바꾸기 전의 지난 requested 신청을 어떻게 다룰지 정하지 않는다. 부분 유니크는 `expires_at`을 보지 않는다. 기존 워커 간격은 300초이고 오류 뒤에도 다음 tick을 기다린다(`server/app/workers/subscription_biller.py:32`, `:69`).
- `지시서:24`는 “입금이 없으면” 자동 종료라고 안내하지만, 현재 설계에는 은행 입금 조회가 없다. 관리자 입력 전에는 기한 안에 입금한 건도 미입금 건과 구분할 수 없다. `지시서:80`의 requested 전용 확인은 워커가 expired로 바꾼 뒤 정상 입금 확인도 거절한다.

**도달 경로**

사용자가 마감 직전에 입금하고 관리자가 다음 영업일에 확인하는 경우. 또는 만료 워커가 지연된 상태에서 같은 종류를 다시 신청하는 경우다. 단순히 기한을 늘려도 첫 번째 문제는 남는다.

**구체적 대안**

- 종류당 한 건과 3일 입금 기한을 유지한다. 생성 시 같은 사용자와 종류의 기한 지난 requested 행을 먼저 expired로 전환하고 새 행을 삽입한다. 동시 신청의 최종 방어선은 부분 유니크이며 충돌은 409로 변환한다. 열린 신청 조회도 기한을 반영한다.
- 3일은 정확한 만료 일시인지 서울 날짜의 끝인지 명시한다. 현재 DB 세션은 서울 시간으로 설정된다(`server/app/db.py:22`, `:54`). 추천은 생성 후 3일의 정확한 일시를 저장하고 화면에도 시각을 표시하는 것이다.
- 기한 내 실제 입금이 확인된 expired 신청은 관리자만 지급할 수 있게 예외 전이를 명시하고, 실제 `paidAt`과 확인 사유를 필수로 남긴다. 그 뒤 새 신청이 생겼다면 함께 잠그고 중복 입금 여부를 대조한다. canceled와 rejected는 자동 복구하지 않는다.
- 안내는 “3일 뒤 신청이 자동으로 닫힙니다. 기한 안에 입금했다면 확인 후 지급합니다”처럼 실제 시스템이 아는 사실에 맞춘다. 현재 정확한 문구 지정(`지시서:24`)을 바꾸는 결정은 Claude가 받아야 한다.
- 늦은 입금, 금액 부족, 초과 입금, 동명이인, 중복 입금은 관리자 수동 대조와 반환 절차를 정한다. 자동 은행 연동은 이번 범위에 추가하지 않는다. 기존 직접 충전 지급은 신청과 연결되지 않으므로(`server/app/facemarket_admin.py:1204`) 열린 신청을 우회해 지급하는 표준 해결책으로 삼으면 안 된다.

기존 토스 가입자가 구독 관리에서 해지 예약한 다음, 예정된 계좌이체 신청과 관리자 확인을 거치는 경로는 직접 성립한다. 반대 방향은 계좌이체 전용 CTA에서는 바로 노출되지 않지만, 이미 열린 토스 인증의 성공 복귀 화면이 `startSubscription`을 호출한다(`src/features/subscription/Subscription.jsx:71`, `:80`). 향후 계좌이체 플래그를 끄고 토스 CTA를 복원할 때도 성립한다. 운영 환경에서 토스 라우트가 꺼져 있다면 그 기간에는 후자의 서버 경로가 미등록이다(`server/app/main.py:589`).

**구체적 대안**

추천은 두 이용권의 동시 보유 금지다. **구독 종류에 한해** 신청 단계와 관리자 확인 단계 모두 `active`, `past_due`, `canceled`를 거절한다. `canceled`의 기간이 지났어도 아직 기존 만료 정리가 끝나지 않았다면 지급을 보류한다. 먼저 `ended`와 잔액 정리를 완료한 뒤 수동 지급해야 옛 워커가 새 버킷을 지우지 않는다. topup은 토스 구독 유무와 무관하게 허용한다.

토스 시작에도 활성 수동 이용권 거절과 동시 실행 직렬화가 필요하다. 이는 `subscriptions.py` 수정 금지와 충돌한다. Claude가 최소 가드 수정 예외를 승인하거나, 새 마이그레이션에서 양쪽 지급 경로를 막는 DB 상호배제 제약 구현을 선택해야 한다. 단순 조회 후 삽입은 동시 실행을 보장하지 않으므로 공통 잠금과 그 순서까지 검증한다. 토스 재개방 전 해결할 별도 필수 작업으로 분리하려면, 그 전까지 서버의 토스 시작 경로가 실제로 닫혀 있다는 배포 조건을 명시해야 한다.

## 6. [권고] 세금계산서는 대표자 성명을 보완하고, 법정 기재사항과 발급 화면을 구분

**근거**

- `지시서:23`, `:41`, `:70`은 사업자등록번호, 상호, 이메일만 수집한다. 입금자명은 별도 의미이므로 대표자 성명으로 대입할 근거가 없다. 서버 검증 목록에는 이메일 필수 검증도 빠져 있다.
- 현행 [부가가치세법 제32조](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1031739493)는 공급자 식별정보, 공급받는 자의 등록번호, 공급가액과 세액, 작성 연월일을 규정한다. 따라서 “대표자 성명이 법률상 필요적 기재사항이어서 무조건 무효”라고 주장할 수는 없다.
- 그러나 홈택스 입력 업무는 별개다. [국세청의 홈택스 발급 안내](https://v.daum.net/v/cc93y1Nvfu)는 공급받는 자의 상호와 성명을 별도로 입력하도록 설명한다. [2024년 손택스 발급 안내서 공개본](https://gwangjuta.or.kr/uploads/cbkta/common/2024/06/231de139-c237-4086-9895-06b10ea89f5a.pdf)의 공급받는 자 정보 설명에는 등록번호, 상호, 성명이 필수 입력 항목으로 명시되어 있다. 공개 안내를 확인했으며, 2026년 로그인 후 실제 홈택스 화면을 조작해 검증한 것은 아니다.
- 금액과 날짜도 발급에 필요하지만 고객에게 다시 입력받을 정보는 아니다. 신청 amount, 상품 정보, 실제 거래 증빙을 운영자가 사용해야 한다. 현재 화면은 표시가가 부가세 포함이라고 알린다(`src/features/pricing/Pricing.jsx:152`).

**구체적 대안**

사용자 수집 최소안을 `사업자등록번호, 상호, 대표자 성명, 수신 이메일`로 보완한다. 이메일은 체크 시 필수이며 형식을 서버에서 검증한다. 사업자번호는 숫자 10자리 정규화와 기본 유효성 검사를 하되, 그것만으로 실제 사업자 확인이 끝났다고 표시하지 않는다. 주소, 업태, 종목까지 모두 필수로 늘리기보다 실제 발급 화면에서 추가로 필요한 경우 운영자가 보완받는 절차를 둔다. 발급용 성명을 별도로 받지 않는 안을 선택한다면 최초 발급 전 별도 확인이 필요하다는 운영 비용을 명시한다.

관리자 화면에는 총액과 상품, 실제 입금일, 확인일을 구분해 제공하고, 공급가액과 세액의 원 단위 처리 및 작성일 기준은 발급 담당자가 확정한다. 신청 DB에 발급 시스템 전체를 만들 필요는 없다. `admin_note`에 발급일과 승인번호를 남기는 최소 운영 방식부터 가능하다. 공급시기는 단순히 관리자 확인일과 같다고 가정하지 않는다. [국세청 발급절차 안내](https://www.nts.go.kr/nts/cm/cntnts/cntntsView.do?cntntsId=7788&mi=2453)도 법정 발급시기에 맞춘 발급과 이메일 전송을 구분한다.

## 8. [차단] 누락된 지급 계약과 화면 연결, 줄일 수 있는 범위

### 8.1 [차단] 저장한 금액과 크레딧 스냅샷을 지급에 사용하지 않음

**근거 및 도달 경로:** `지시서:39`, `:68`은 신청 시 스냅샷을 약속하지만 `:81`, `:82`의 호출에는 이를 전달하지 않는다. 신청 후 3일 안에 가격이나 지급량을 바꾼 다음 관리자가 확인하면 현재 카탈로그로 지급된다. `server/app/repo.py:3295`는 이미 topup 스냅샷 인자를 지원하며, 구독은 `:3170`에서 활성 플랜을 다시 읽고 `:3177`에서 기본 지급량을 선택한다. 구독에 `credits`를 전달해도 상품 비활성화 시의 404는 남는다.

**구체적 대안:** 충전은 `snapshot={"credits": request.credits, "price": request.amount}`를 넘긴다. 구독도 `credits=request.credits`와 신청 금액을 사용한다. 이미 입금한 신청의 상품 비활성화를 사유로 지급을 막지 않으려면 신뢰된 스냅샷을 처리하는 별도 지급 경로를 두거나 `grant_subscription`에 명시적 내부 인자를 추가한다. `is_active` 검사를 기존 토스 호출 전체에서 제거하면 안 된다. 신청 때 상품 ID와 이름도 저장해 이후 이름 변경과 조회를 안정화한다. 상품을 중단할 때 열린 신청을 어떻게 처리할지도 확정한다.

### 8.2 [차단] 중복 확인 409와 멱등 성공 요구가 충돌

**근거 및 도달 경로:** `지시서:80`은 requested가 아니면 409, `지시서:126`은 중복 확인 멱등을 요구한다. 첫 확인이 커밋된 뒤 응답만 유실되어 재시도하면 지급 함수 전에 409가 난다. topup의 repo 멱등(`server/app/repo.py:3284`)만으로 이 응답 문제는 해결되지 않고 구독 함수에는 자체 멱등 키도 없다(`:3149`).

**구체적 대안:** 신청 ID를 지급의 고정 멱등 식별자로 삼는다. 신청을 잠근 뒤 paid이면 저장된 동일 지급 결과를 200으로 반환하고 재지급, 연장, 메일을 반복하지 않는다. rejected, canceled 등은 409로 구분하며 expired는 4번의 명시적 예외만 허용한다. 헤더를 받는다면 재사용 키에 다른 요청이나 입력을 섞었을 때의 응답까지 정한다. 가장 단순한 안은 요청 ID 기반 멱등을 필수 보장하고 헤더 의존성을 없애는 것이다.

확인, 취소, 거절, 만료 모두 같은 신청 행을 잠그거나 조건부 UPDATE로 경쟁을 해결한다. 서로 다른 신청의 연장과 수동 이용권 만료는 신청 잠금만으로 직렬화되지 않으므로 사용자 단위 공통 잠금도 필요하다. 부분 유니크 활성 이용권, 요청별 지급 참조 유일성, `ends_at > starts_at`, 필수 FK를 새 마이그레이션에 명시한다. 워커 전역 advisory lock은 HTTP 확인 요청까지 보호하지 않는다(`server/app/workers/subscription_biller.py:254`).

### 8.3 [차단] 수동 이용권 조회 API와 계정 갱신 경로가 없음

**근거 및 도달 경로:** `지시서:30`의 수동 이용권 화면을 만들 정보가 `지시서:66`부터 `:75`까지의 API 목록에 없다. 현재 `/v1/subscriptions/me`는 subscriptions가 없으면 none을 반환한다(`server/app/subscriptions.py:195`). 프론트도 이 API만 읽고 none 화면을 바로 반환한다(`src/features/subscription/Subscription.jsx:148`, `:189`).

또한 `지시서:31`의 상단바가 자동 갱신된다는 가정은 맞지 않는다. `src/features/shell/shell.jsx:117`은 DB를 직접 읽지 않고 Zustand의 `account.plan`을 그린다. `src/store/useAppStore.js:205`는 이미 로드했으면 재조회하지 않으며, `:229`의 `syncCredits`는 plan을 바꾸지 않는다. 사용자가 화면을 열어 둔 사이 관리자 지급이 끝나는 경로에서 발생한다.

**구체적 대안:** 새 은행이체 모듈에 `GET /v1/bank-transfer/entitlement`와 대응 서비스, 목 계약을 추가한다. 최소 `planCode`, `startsAt`, `endsAt`, 남은 수동 구독 크레딧, 자동 갱신 없음 정보를 반환한다. Subscription 화면에서 토스 미등록 또는 none 상태와 이 응답을 함께 판단한다. 토스 라우트 자체가 미등록인 경우도 다룬다. 지급 완료나 만료를 감지하고 화면에 다시 들어올 때 `/v1/me/account`를 재조회하여 계정 캐시를 교체한다. 소스 변경 금지 범위를 유지하려면 구독 API 확장은 기존 `subscriptions.py` 대신 신규 모듈에 둔다.

### 8.4 [차단] CTA 문구만 바꾸면 같은 플랜 연장과 키 없는 구매가 막힘

**근거 및 도달 경로:** `src/features/pricing/Pricing.jsx:174`, `:233`은 현재 플랜이거나 토스 키가 없으면 구독 버튼을 비활성화한다. 충전도 `:259`에서 토스 키를 요구한다. 이 조건을 유지하면 계좌이체 전용 환경의 최초 구매와 현재 플랜 연장이 막힌다. 충전 탭은 `:129`뿐 아니라 `:142`에도 조건이 있다. `:152`, `:158`에는 자동 결제와 갱신 실패 유예 문구가 그대로 남아 있다.

**구체적 대안:** 계좌이체 분기의 활성 조건을 서버 info의 사용 가능 여부와 같은 종류의 열린 신청 유무로 정한다. 같은 수동 플랜은 “1개월 연장 신청”을 허용하고 토스 키를 검사하지 않는다. 충전 탭 조건 두 곳을 함께 수정한다. 안내는 수동 확인 후 시작, 자동 갱신 없음, 확정된 이월과 소멸 정책으로 분기한다. 서버 설정이 꺼졌거나 계좌가 비어 있으면 CTA와 안내도 그 상태를 반영한다. 판매 스위치 off가 기존 신청 조회, 취소, 관리자 지급, 만료를 끄는 의미가 되어서는 안 된다.

### 8.5 [권고] 권한, 감사, 알림 계약을 실제 기존 코드에 맞춰 확정

**근거 및 도달 경로:** 새 관리자 목록은 이메일, 연락처, 사업자정보를 노출하고 확인은 유료 지급을 수행한다(`지시서:78`, `:96`). 기존 관리자 가드는 기기 확인 중 커밋 또는 롤백할 수 있다(`server/app/admin_guard.py:125`, `:127`). 지급 트랜잭션 도중에 부르면 원자성이 깨질 수 있다. 감사 함수도 이미 존재한다(`:150`). 기존 관리자 prefix는 `/v1/facemarket/admin`이다(`server/app/facemarket_admin.py:27`).

**구체적 대안:** `require_admin(conn, actor, request)`를 어떤 지급 변경과 잠금보다 먼저 호출한다. 목록과 확인, 거절에 모두 적용하며 `write_audit`는 지급과 같은 트랜잭션에 넣는다. 조회 응답은 사용자용과 관리자용을 나눠 `admin_note`, 관리자 식별정보 등을 사용자에게 통째로 반환하지 않는다. 새 두 테이블 모두 `toss_payment_orders`처럼 RLS 활성화와 직접 접근 정책 없음으로 두고 서버에서 본인 조건을 강제한다(`supabase/migrations/20260727000000_toss_payment_orders.sql:31`, `server/app/db.py:3`).

API의 실제 전체 URL을 `/v1/admin/bank-transfers` 등 하나로 확정하고 서비스 함수와 맞춘다. `지시서:78`의 `/admin/...`만으로 기존 prefix를 추정하지 않는다. `settings.contact_email`은 현재 Settings와 env 로더에 없으므로 새 알림 수신 설정을 명시한다. `_send_email`은 FaceMarket 발신 설정을 쓰므로 Wearless 발신명 재사용 여부도 정한다(`server/app/config.py:314`, `server/app/facemarket_notify.py:338`). 알림은 커밋 후 best-effort로 처리하고, 사용자 입력은 HTML 이스케이프하며 사업자번호 전체를 알림 제목이나 로그에 싣지 않는다.

### 8.6 [권고] 원장 정본, 환불, 충전 보너스의 현재 계약을 구분

**근거:** 지시서가 원장 정본으로 지정한 `documents/credit_system_design.md:16`, `:77`은 여전히 월 리셋을 설명한다. 실제 `server/app/repo.py:3155`와 요금제 화면은 구독 유지 중 이월이다. 현행 가격은 `documents/research/2026-09-07-credit-pricing-plans.md:816`에 별도로 확정되어 있다. 오래된 원장 문서만 따라 월 소멸을 다시 넣으면 회귀다.

또한 `src/features/pricing/Pricing.jsx:159`는 미사용 결제의 환불 문의를 안내하지만, `server/app/repo.py:3367`의 자동 환불 요청은 topup만 허용한다. `:3427`의 승인도 DB 상태 처리이며 실제 은행 송금은 하지 않는다. 이 제한을 새 수동 구독도 자동 환불된다고 안내하면 안 된다. 카드의 “충전할 때마다 5%, 10% 보너스”(`src/features/pricing/Pricing.jsx:41`, `:46`)도 `purchase_topup`의 지급량에는 계산되지 않는다(`server/app/repo.py:3306`, `:3328`).

**구체적 대안:** 이번 구현의 크레딧 정책은 실제 이월 코드와 확정된 수동 이용권 규칙을 기준으로 명시하고, 정본 문서 정리는 Claude의 후속 문서 작업으로 둔다. 수동 구독 환불은 문의 접수, 은행 반환, 이용권과 잔액 회수의 운영 절차를 정하되 자동 환불 시스템까지 이번 범위를 넓히지 않는다. 충전 보너스는 지급할지 문구를 보류할지 결정하고, 지급한다면 신청 시점 플랜을 기준으로 최종 credits에 스냅샷한다. 구현자가 임의로 5%, 10%를 더하지 않는다.

### 8.7 [권고] 통과 기준을 실제 실패 경계에 보강하고 범위를 줄임

**근거:** `지시서:126`의 테스트 목록에는 정상 지급과 순차 중복 확인이 있지만, 위에서 확인한 경쟁과 설정 조합이 빠져 있다. 특히 `supabase/migrations/20260612090000_init.sql:38`의 `reserved <= balance` 제약 때문에 진행 중 생성이 있는 사용자에게 전량 만료를 적용하면 잔액 감소가 실패할 수 있다. `server/app/repo.py:3216`, `:3245`는 예약량을 보존한 채 잔액을 줄인다.

**구체적 대안:** 구현 단계에는 다음 실패 조건을 검증한다. 이번 검토에서는 테스트를 실행하지 않았다.

- 응답 유실 뒤 확인 재시도와 동시 이중 확인에서 결제, 원장, 기간 연장이 정확히 한 번인지.
- 확인과 취소, 거절, 만료가 경쟁할 때 한 결과만 남는지. 연장과 이용권 만료가 경쟁해 plan 또는 크레딧을 잘못 지우지 않는지.
- 신청 후 카탈로그 가격과 credits 변경, 비활성화에도 확정한 거래 조건이 유지되는지.
- 토스 해지 예약, 기한이 지난 미정리 구독, 수동 이용권과 토스 시작의 역방향 충돌을 막는지.
- 토스 기능 off와 키 없음에도 수동 지급, 조회, 만료가 동작하고 판매 off 뒤에도 기존 이용권을 정리하는지.
- 월말 연장, 같은 플랜의 반복 연장, 마감 직전 입금 후 늦은 확인을 처리하는지. 다른 플랜 교체를 채택하면 이전 버킷만 제때 만료되는지.
- 생성 예약 때문에 소멸 트랜잭션이 실패해도 부분 지급이나 부분 만료가 없고, 다른 사용자 처리를 계속하며 다음 tick에 재시도하는지. 기존 예약·정산 모델 전체 개편은 이번 작업에 넣지 않는다.
- 비관리자와 미승인 기기, 타인 신청 접근을 거절하는지. 메일 실패가 지급을 취소하지 않는지. 프론트에서 현재 플랜 연장, 키 없는 CTA, 지급 후 plan 갱신까지 확인하는지.

첫 방문의 세션 스토리지 완료 띠(`지시서:27`)는 생략 가능하다. 신청 상태와 현재 이용권 조회만으로 먼저 완결시키는 편이 단순하다. 토스 테이블 통합, 자동 은행 대사, 자동 세금계산서 발행, 중도 플랜 교체는 첫 버전에 꼭 필요한 범위가 아니다.

## 구현에 들어가기 전에 Claude가 결정해야 할 것

1. **이월과 플랜 교체:** 같은 플랜은 남은 기간에 한 달을 더하고 기존 크레딧도 연장할지 확정한다. 추천은 이를 허용하되 다른 플랜 중도 교체는 첫 버전에서 거절하는 것이다. 교체를 유지하면 버킷 소속과 교체된 이용권의 별도 만료까지 승인한다.
2. **토스와 수동 이용권의 상호배제:** `canceled` 정리 완료 전까지 수동 구독을 막고 topup은 허용한다. 반대 방향의 시작 가드를 위해 토스 소스 수정 금지에 최소 예외를 줄지, DB에서 막을지, 토스 재개방의 필수 선행 작업으로 분리할지 결정한다. 추천은 최소 가드와 공통 직렬화 계약을 함께 확정하는 것이다.
3. **기간과 늦은 입금:** 신규 시작은 관리자 확인 시각, 연장은 기존 종료일, 입금 증빙은 실제 `paid_at`으로 분리할지 결정한다. 추천은 3일 입금 기한을 유지하고 기한 내 입금한 expired 신청의 관리자 예외 확인을 허용하며 안내 문구도 수정하는 것이다.
4. **지급 금액과 크레딧:** 요청 스냅샷을 끝까지 보장하고 지급 전 상품 비활성화도 처리할지 확정한다. 추천은 입금한 요청의 거래 조건 보장이다. 화면의 충전 보너스 5%, 10%를 실제 지급량에 넣을지도 함께 결정한다.
5. **멱등과 결과 참조:** 이미 paid인 신청 재확인은 기존 결과 200으로 통일할지 결정한다. 추천은 신청 ID 기반 멱등과 결제 ID, 버킷 ID, 이용권 ID의 명시적 연결이다. 헤더만으로 지급의 유일성을 정하지 않는다.
6. **필수 구현 범위 보완:** 토스 설정과 독립된 만료 작업, 수동 이용권 조회 API, 계정 캐시 갱신, 현재 플랜 연장 CTA를 지시서에 추가한다. 추천은 신규 모듈을 쓰고 공유 파일 등록부만 최소 수정하는 것이다. 진행 중 예약으로 만료가 보류될 때 재시도하는 운영 기준도 명시한다.
7. **발급과 반환 운영:** 대표자 성명과 유효한 수신 이메일을 추가할지, 공급가액과 세액 및 작성일을 어떻게 기록할지 확정한다. 추천은 대표자 성명까지 수집하고 발급과 은행 반환은 운영자가 처리하며 신청에 처리 근거를 남기는 것이다. 입금자명으로 대표자 성명을 대신하지 않는다.
8. **동시 작업 조율:** 열린 PR 조회를 네트워크 가능한 환경에서 다시 실행하고 `main.py`, `config.py`, `repo.py`, 관리자 메뉴의 수정 담당자를 확정한다. 현재 보고서의 로컬 ref 조사만으로 충돌 검토가 끝났다고 승인하지 않는다.
