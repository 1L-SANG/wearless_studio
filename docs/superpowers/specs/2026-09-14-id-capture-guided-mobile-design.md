# 신분증 촬영 재설계 — 모바일 전용 가이드 촬영 · 자동 마스킹 · 서버 검증

- 작성일: 2026-09-14 (Asia/Seoul)
- 선행: `2026-09-11-facemarket-id-capture-and-admin-review.md` (간편인증 경로 v1, 배포됨)
- 상태: 설계 확정 — 구현 계획 미작성

---

## 1. 왜 다시 설계하나

v1 은 "파일을 골라 올리고, 사용자가 검은 박스를 드래그로 주민번호 위에 맞춘다"였다. 프로덕션에서 두 가지가 드러났다.

**첫째, 파일 선택 경로가 깨진다.** 맥 사진앱 기본 포맷인 HEIC 를 고르면 브라우저가 `<img>` 로 못 그린다. 미리보기가 깨진 띠로 뜨고 제출 버튼이 잠긴 채 안내가 없었다(PR #300 에서 응급 처치).

**둘째, 마스킹이 사용자 손에 달려 있다.** v1 스펙 §7.2 가 스스로 적어 둔 한계다 — *"서버는 마스킹 여부를 검증할 수 없다."* 사용자가 박스를 엉뚱한 데 두면 주민등록번호가 그대로 서버에 올라오고, 관리자 육안이 유일한 방어선이었다.

두 번째가 본질이다. 이건 UX 문제가 아니라 **개인정보보호법 §24(고유식별정보) 노출 위험**이고, 모델과 맺는 계약서 문구와도 직접 얽힌다.

## 2. 핵심 통찰

**신분증은 규격이 고정이다.** 주민등록증은 86×54mm(ISO/IEC 7810 ID-1)이고 주민등록번호의 위치도 카드 안에서 고정이다.

따라서 **카드가 화면의 가이드 박스를 채우도록 찍게 하면, 주민등록번호의 픽셀 좌표가 계산으로 나온다.** 사용자가 맞출 필요가 없고 — 더 중요하게 — **서버가 "그 자리가 실제로 덮였는지" 검사할 수 있다.**

v1 스펙이 인정한 한계가 정상 경로에서는 사실이 아니게 된다. 새 의존성 없이(서버엔 이미 OpenCV 가 SFace/YuNet 용으로 있다).

## 3. 확정된 결정

| # | 결정 | 근거 |
| --- | --- | --- |
| 1 | **간편인증 경로 전체를 모바일 전용** | 간편인증 승인은 어차피 폰 앱으로 온다. PC 로 하면 두 기기를 오가고, 신분증 때문에 또 폰으로 넘어가야 한다. 처음부터 폰이면 한 기기에서 끝나고 유지할 경로가 하나로 준다 |
| 2 | **순서를 뒤집는다: 간편인증 → 신분증 촬영** | 촬영 시점에 인증사가 검증한 이름·생년월일·CI 를 이미 쥐고 있다. 카드는 "정보를 읽는 대상"이 아니라 **"방금 인증된 그 사람 것인가"를 확인하는 물증**이 된다 |
| 3 | **가이드 박스 + 자동 셔터. 라이브러리 0** | 사용자가 정렬만 하면 알아서 찍힌다. OpenCV.js(~8MB)를 끌어오지 않고 캔버스로 직접 구현한다 |
| 4 | **OCR 은 v2** | 브라우저 한글 OCR 은 10MB+ 에 신분증 정확도가 들쭉날쭉하다. 서버 OCR 은 외부 업체 계약·PII 위탁이 붙는다. 그리고 **관리자가 이미 카드와 인증 신원을 나란히 놓고 대조한다** — OCR 은 정확도를 올리는 게 아니라 관리자 몇 초를 아낀다. 심사량이 늘면 그때 |
| 5 | **마스킹 검증 실패 = 거부. 단 2~3회 연속 실패하면 수동 마스킹으로 내려준다** | 정상 경로에서는 §2 의 보장을 지키고, 오판으로 사용자가 갇히지 않는다. v1 의 수동 드래그 UI 를 비상구로 재활용 |

## 4. 흐름

상태 머신이 **오히려 단순해진다.** v1 은 간편인증만 다른 상태에서 시작해 처음부터 갈렸는데, 순서를 바꾸면 두 경로가 같은 자리에서 시작한다.

```
v1
  simple_auth:  id_capture_pending → identity_pending → photos_pending → review_pending
  mid:                               identity_pending → photos_pending

v2
  둘 다:                             identity_pending
                                          ↓
  simple_auth 만:                    id_capture_pending
                                          ↓
  둘 다:                             photos_pending → (simple_auth 면) review_pending
```

화면:
```
동의 → 인증수단 선택 → 간편인증(폰 앱 승인) → 신분증 촬영 → 사진 3장 → 심사 대기
                                              ↑ 여기서만 갈린다
```

`id_capture_pending` 이라는 상태값 자체는 그대로라 **마이그레이션이 필요 없다.** 현재 그 상태인 행은 0건(2026-09-13 prod 실측)이라 전환 리스크도 없다.

## 5. 모바일 게이트를 어디서 강제하나

**서버는 User-Agent 를 보지 않는다.** UA 는 위조가 쉽고 오판이 잦다.

- **프런트**: PC 에서 "간편인증으로 확인" 버튼 비활성 + 안내 + QR(주소만). 이어받기는 기존 `GET /v1/facemarket/enrollments/current` 가 이미 한다 — 폰에서 같은 계정으로 들어오면 등록이 그대로 이어진다. 토큰을 URL 에 싣는 핸드오프 장치를 새로 만들지 않는다
- **서버**: 기기를 묻지 않고 **"마스킹이 규격 위치에 실제로 덮였는가"** 를 검사한다

진짜 통제는 기기 판별이 아니라 **기하 검증**이다. 가이드 촬영을 거치지 않은 사진은 그 검사를 통과하기 어렵고, 통과했다면 주민번호는 가려져 있으니 목적은 달성된 것이다.

## 6. 촬영 컴포넌트

`getUserMedia({ video: { facingMode: 'environment' } })` 로 후면 카메라를 띄우고 카드 비율(1.586:1) 가이드를 겹친다.

**자동 셔터 판정** — 매 프레임을 다 볼 필요 없다. ~10fps 로 다운스케일(장변 320px) 후:

1. 그레이스케일 → Sobel 로 경계 강도
2. 가이드 테두리 **안쪽 밴드**에서 수평·수직 에지 강도 측정
3. 세 조건이 **연속 N프레임**(~0.5초) 유지되면 촬영
   - 카드가 가이드를 충분히 채움(면적비 임계)
   - 기울기가 작음(에지 각도)
   - 흔들림 없음(프레임 간 차분)

**HEIC 문제가 구조적으로 사라진다** — 파일을 고르는 게 아니라 `canvas.toBlob('image/jpeg')` 로 우리가 만든다.

**비상구 3겹** (사용자가 갇히지 않게 — v1 리뷰가 잡은 I7 의 교훈):

| 상황 | 대응 |
| --- | --- |
| 자동 셔터가 안 잡힘 | 수동 셔터 버튼을 항상 노출. ~15초 지나면 "수동으로 찍어도 괜찮아요" 안내 |
| 카메라 권한 거부 · `getUserMedia` 실패 | 파일 선택으로 폴백(`accept` 는 PR #300 의 좁힌 집합) |
| 기하 검증 2~3회 실패 | 수동 마스킹 드래그 UI(v1 것)로 내려주고 관리자 카드에 `수동 마스킹` 배지 |

## 7. 마스킹과 서버 검증

**클라이언트**: 카드가 가이드를 채웠으므로 주민번호 위치가 규격 상대좌표로 나온다. 사용자가 끌 필요 없이 캔버스에 바로 덮어쓴다. v1 과 같이 **픽셀을 실제로 태우고 그 blob 만** 올린다 — 원본 File 은 브라우저를 떠나지 않는다(v1 최종 리뷰가 경로별로 확인한 속성, 그대로 유지).

**서버** (기존 cv2, 새 의존성 0):

```
업로드 → 규격 상대좌표로 주민번호 영역 산출
      → 그 영역의 분산·평균밝기 검사 (단색으로 덮였는가)
      → 통과: 저장 / 실패: 거부 + 재촬영 (2~3회 후 수동 경로)
```

임계값은 골든셋으로 캘리브해야 한다 — v1 의 SFace 임계가 캘리브 없이 들어갔다가 오탈락으로 고생한 선례가 있다. **shadow 모드(판정만 기록, 차단 안 함)로 먼저 켜고 실측 후 enforce 로 올린다.**

## 8. 관리자 심사

v1 화면을 유지하되 둘만 바꾼다.

- **인증된 신원(이름·생년월일)을 카드 사진 바로 옆에** — 대조가 한눈에 되게. v1 은 별도 블록이라 눈이 왔다갔다 한다
- **`수동 마스킹` 배지** — 기하 검증을 못 거친 건은 눈에 띄게

## 9. 비범위

- **OCR** (§3-4)
- **신분증 진위확인 API**(행안부·경찰청) — v1 스펙 §11 그대로
- **주민등록증 외 신분증** — v1 이 `rrc` 로 좁혔고 그대로 둔다. 운전면허증·여권은 규격이 달라 상대좌표와 가이드 비율을 따로 잡아야 한다
- **데스크톱 촬영 경로** — 결정 1 로 제거

## 10. 열린 위험

| 위험 | 완화 |
| --- | --- |
| 자동 셔터가 조명·배경에 따라 안 잡힘 | 수동 셔터 상시 노출. 자동은 편의이지 관문이 아니다 |
| 기하 검증 오판으로 정상 사용자 차단 | shadow 먼저 → 실측 후 enforce. 2~3회 실패 시 수동 경로 |
| 카드를 가이드에 안 맞추고 멀리서 찍음 | 면적비 임계가 거른다. 그래도 통과하면 마스크가 어긋나고 서버 검증이 잡는다 |
| 규격 상대좌표가 카드 개정으로 바뀜 | 좌표를 상수 한 곳에 두고 테스트로 고정. 개정 시 한 곳만 |
