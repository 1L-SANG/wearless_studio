# 움직이는 썸네일(GIF) 설계 (2026-10-13, 오너 승인: 1차 범위 A+B, 썸네일 우선, AI 영상은 X)

## 1. 목적
스타일링컷 여러 장을 모아 돌아가는 대표이미지(썸네일) GIF를 에디터에서 바로 만들어 내려받는다. 셀러가 찍은 짧은 영상도 같은 규격의 GIF로 바꿔 준다. 모든 처리는 브라우저 안에서 하고 서버·크레딧·DB를 건드리지 않는다.

근거: 카톡방 썸네일 GIF 고통(용량, 색 빠짐, 화질, 목록 로딩), 에이블리 공식 권장(대표이미지 GIF, 640×768, 전환 1.7초, 5장 이상), 카페24 썸네일 GIF 5MB 한도. 조사 정본 `.scratch/gif-20261013/PLAN.md`.

## 2. 범위
- 포함: 의류 안 이미지와 GIF 밑줄 탭, 사진 2~8장 또는 영상 1~4초의 GIF 제작, 원본 비율과 고정 규격 3종, 저장과 캔버스 삽입, GIF 인스펙터, 정지 이미지와 GIF 원본 내보내기.
- 제외: AI 영상 생성, 크레딧, 서버와 DB 변경, 글자 얹기, 손실 압축.

## 3. 화면 (의류 패널, 라운드 3 확정)
별도 GIF 툴바 탭을 없애고 의류 패널에 기존 `UnderlineTabs`로 **이미지 | GIF**를 둔다. 기본은 이미지다.

1. 이미지 탭은 기존 의류 패널의 업로드 버튼, 색상 묶음, 타일 클릭과 드래그 삽입, 삭제를 유지한다. 만든 GIF는 제외한다. 점선 업로드 타일은 쓰지 않는다.
2. GIF 탭 상단은 `.modal-actions`의 같은 알약 두 개 **사진으로 | 영상으로**다. 기본은 사진이다.
3. 사진은 기존 색상 묶음과 타일 비율을 유지하고 각 묶음에서 스타일링컷을 먼저 보여 준다. 클릭은 선택 토글이며 선택 순서 번호를 표시한다. 2~8장, 삭제와 드래그는 제공하지 않는다. 안내는 “선택한 순서대로 돌아가요 · 3/8” 형태다. GIF는 사진 재료에서 제외한다.
4. 영상은 사진 타일을 숨기고 “영상 파일 고르기”, 시작 지점과 길이 슬라이더를 보여 준다. 기존 코덱 오류 안내와 1~4초 범위를 유지한다.
5. 규격은 S1 시안의 비율 틀 아이콘 네 개다. 원본 비율이 기본이며 5:6, 3:4, 1:1이 뒤따른다. 원본은 첫 선택 사진 또는 영상 기준 폭 640px, 높이는 짝수 반올림, 최대 1200px다. 고정 규격은 기존 640×768, 800×1067, 800×800을 유지한다. `coverCrop`의 `anchorY: 0.08`로 세로 초과분의 8%를 위에서 잘라내고, 가로 초과분은 가운데 기준으로 자른다.
6. 사진은 장당 1.5초 고정, 하드컷이다. 시간 칩은 제거한다.
7. “GIF 만들기” 뒤 미리보기와 크기, 장수, 용량을 표시한다. 첫 줄에 primary “의류에 저장”, 다음 줄에 “GIF 받기”, “첫 컷 JPG 받기”를 같은 알약 규칙으로 둔다. 저장 중 중복 실행을 막고 성공하면 “저장됨”으로 바꾼다. 설정 변경은 기존 결과를 지운다.
8. 맨 아래 “만든 GIF”는 최근 저장 순이다. 기본 poster, 호버와 키보드 초점 때 GIF 재생, GIF 배지와 용량, 우측 위 X를 둔다. 클릭은 기존 캔버스 삽입 경로를 쓴다. 사용 중 삭제는 기존 안내로 막는다.

한국어 단어 중간 줄바꿈 금지, 짧은 문구와 제목은 균형 줄바꿈, 입력칸 16px 이상, CSS Modules와 기존 토큰을 쓴다. 브라우저와 폰 폭, WebKit 확인은 지시서에 따라 Claude가 담당한다.

## 4. 인코딩 규칙
- 라이브러리: `gifenc`(npm, MIT). Web Worker(`new Worker(new URL('./gifEncodeWorker.js', import.meta.url), { type: 'module' })`)에서 인코딩. 메인 스레드는 프레임 추출(canvas)만.
- 프레임마다 팔레트: `quantize(rgba, maxColors, { format: 'rgb565' })`로 프레임별 256색. 전역 팔레트 금지(색 빠짐 원인).
- 디더: Floyd–Steinberg(직접 구현, 쇼필공 도구와 같은 식). 켜짐 고정.
- 피부·입술 보정(colorBoost): 양자화 입력 샘플에 피부·붉은 기 픽셀(r>95&&g>40&&b>20&&r>g&&r>b&&|r-g|>15&&r-b>15, 또는 r>110&&r-g>45&&r-b>35&&g<140)을 3배 더 넣어 팔레트 칸을 확보한다. 함수로 분리해 테스트한다.
- GIF: loop 0, delay = 1500ms 고정(사진) 또는 1000/fps(영상). 첫 프레임은 JPG(품질 0.92)로도 만든다.
- 영상 모드: `<video>`를 fps 간격으로 seek해 캔버스에 그린다(쇼필공 방식). 기본 fps 10. HDR 영상은 브라우저가 SDR로 그린 값을 그대로 쓴다.

## 5. 용량 사다리 (순수 함수 `planLadder` + 실행 루프)
- 하드 상한 4.7MB(카페24 5MB 안전 여유), 소프트 목표 1.5MB(목록 로딩).
- 사진 모드 단계: [256색] → [192색] → [폭 ×0.8, 256색] → [폭 ×0.8, 128색] → [폭 ×0.64, 128색].
- 영상 모드 단계: [10fps 256색] → [8fps 256색] → [8fps 128색] → [6fps 128색] → [폭 ×0.8, 8fps, 128색] → [길이를 2초로, 8fps, 128색] → [폭 ×0.8, 2초, 8fps, 128색] → [폭 ×0.64, 2초, 8fps, 128색] → [폭 ×0.64, 2초, 6fps, 128색].
- 소프트 목표는 사진의 256 → 192색, 영상의 처음 두 256색 단계까지만 시도한다. 128색과 폭·길이 축소는 하드 상한을 위해서만 쓴다. 영상의 하드 상한 판정 시작 인덱스는 3으로 유지한다.
- 각 단계마다 실제 바이트를 재고 하드 상한 이하였던 첫 결과를 기억한다. 소프트 목표를 통과하면 그 결과를 쓰고, 소프트 시도가 끝나도 목표에 못 미치면 기억한 첫 통과본을 쓴다. 하드 통과본이 없으면 사다리를 계속 실행하며, 하드 판정에서 멈췄을 때도 소프트 목표를 못 맞췄으면 기억한 첫 통과본을 쓴다. 마지막 단계도 하드 상한을 넘고 기억한 통과본도 없으면 결과를 보여주되 "4.7MB를 넘어 카페24에 올라가지 않을 수 있어요" 안내.
- 결과 객체: `{ blob, width, height, frames, delayMs, bytes, colors, scale, stepIndex }`.

## 8. 테스트 기준(통과해야 함)
1. `planLadder('photo'|'video')` 단계 순서와 종료 조건이 위 표와 같다.
2. cover 크롭: 세로 긴 사진을 5:6, 3:4, 1:1로 자를 때 기본 가운데와 anchorY 0.08의 위쪽 기준 좌표가 맞고 결과 크기가 정확히 640×768, 800×1067(짝수 보정 허용), 800×800이다.
3. 인코더(워커 없이 순수 함수 경로): 합성 프레임 6장(800×1067, 노이즈 포함)을 넣으면 올바른 GIF(헤더 `GIF89a`, 프레임 6, loop 0, delay 150)가 나오고 바이트가 4.7MB 이하다.
4. colorBoost: 피부색 배경에 0.2% 붉은 영역을 가진 합성 프레임에서, boost 적용 팔레트의 붉은 영역 평균 색 오차가 boost 없는 팔레트보다 작거나 같고, 양쪽 모두 256색 기준으로 계산한다(ΔE는 간단한 Lab 변환으로 테스트 안에서 계산).
5. 기존 테스트 전부 통과, `pnpm build` 통과.

## 10. 만든 GIF의 저장·표시·캔버스·인스펙터·내보내기

### 저장 계약과 실패
- GIF와 첫 컷 JPG를 기존 `api.uploadPhoto`의 presigned PUT과 complete 경로로 각각 올린다. 이미 인코딩된 blob은 재인코딩하지 않는다. MIME 허용 목록, 25MB 업로드 한도, 4.7MB GIF 저장 한도를 검사한다.
- 두 업로드가 모두 성공했을 때만 `{ id, src, posterSrc, kind: 'gif', gifMeta: { frames, delayMs, width, height, bytes }, width, height, userUploaded: true, wardrobeGroup: 'misc' }` 항목 하나를 등록한다. 저장 중 오류는 결과를 보존하고 재시도할 수 있다. 부분 업로드 실패 시 미완성 항목을 노출하지 않는다.
- 현재 서버 보관함은 생성컷 조회만 제공한다. 서버 변경 금지 조건에 따라 미삽입 GIF 목록은 프로젝트별 브라우저 저장소에 URL과 메타데이터만 보관한다. HTTP 어댑터의 보관함 조회에 이 목록을 합친다. 저장소 쓰기에 실패하면 성공으로 표시하지 않는다. 목은 프로젝트별 DB 목록과 독립 blob URL을 보관한다.
- 삭제는 목록에서만 제거한다. 서버 asset 삭제 API를 추가하지 않는다. 캔버스에서 GIF 원본 또는 poster를 사용 중이면 삭제를 막는다.

### 캔버스와 인스펙터
- 기존 `type: 'image'`에 `kind: 'gif'`, `posterSrc`, `gifMeta`를 전달한다. 블록 생성, 일반 삽입, 프레임 채우기, drag payload, 캔버스로부터 보관함 복원에 모두 유지한다. 일반 사진으로 교체하거나 빈 슬롯으로 돌릴 때 GIF 필드를 제거한다. 정보 카드의 사진 선택과 순서 변경 뒤에는 src로 이전 요소와 보관함을 찾아 GIF 정보를 복원한다.
- 캔버스의 img는 gif 원본을 쓴다. 내보내기를 위해 img에 poster 주소를 data 속성으로 함께 표시한다. 크롭과 비율 잠금은 그대로다.
- 인스펙터 제목은 GIF, 정보는 “640×960 · 4장 · 0.4MB” 형태다. “GIF 받기”는 원본 바이트를 받고 “정지 컷으로 바꾸기”는 src를 poster로 바꾸고 GIF 필드를 비운다. 기존 Undo 한 단계로 복구한다. 크롭, 크기, 레이어 행은 유지한다.
- GIF에는 AI 오브와 AI 요청을 제공하지 않는다. 사진으로 변환하면 일반 이미지 규칙을 따른다.

### 내보내기
- 실제 캔버스는 건드리지 않고 복제 DOM의 GIF src를 posterSrc로 치환한다. 크롭 위치는 그대로이며 긴 JPG와 PNG, 블록 캡처 모두 첫 컷을 쓴다.
- 다운로드 창에서 GIF를 세고 분할 ZIP이면 “움직이는 GIF n개는 별도 파일로 같이 담아요”를 표시한다. 같은 src를 여러 번 배치한 경우 파일은 한 개만 넣는다. 숨긴 요소는 제외한다.
- 기존 정지 이미지 ZIP을 먼저 공증하고 그 결과 ZIP에 원본 `gif_01.gif` 등을 추가한다. GIF 바이트를 공증에 보내거나 서버 kind를 늘리지 않는다. GIF 바이트 읽기 실패 시 누락된 ZIP을 성공으로 내리지 않는다.
- 단일 이미지 모드에서는 별도 “GIF 따로 받기” 버튼으로 GIF 전용 ZIP을 받는다. 이 ZIP에는 공증을 적용하지 않는다.

### 가정 (미정 부분의 단순한 결정)
1. “상단 8%”는 세로 초과분의 8%를 잘라내는 anchorY 0.08이다. 원본 규격에서도 다른 비율의 후속 사진과 최대 높이 제한에 같은 anchor를 적용한다.
2. 원본이 매우 길면 폭 640을 유지하고 높이를 1200으로 제한하며 크롭한다. 고정 규격의 기존 크기는 유지한다.
3. 스타일링 우선은 색상 묶음 안에서 적용한다. 탭을 떠나면 미저장 제작 상태를 초기화한다. 사진 모드로 돌아오면 영상 리소스를 해제한다.
4. GIF 저장은 캔버스에 자동 삽입하지 않는다. 저장된 타일을 눌러 넣는다. 4.7MB 초과 결과는 경고와 로컬 다운로드는 유지하되 의류 저장은 막는다.
5. 캔버스 미삽입 목록의 기기 간 동기화는 제공하지 않는다. 같은 브라우저에서는 재접속해 복원하고, 캔버스에 저장된 GIF는 다른 기기에서도 문서로부터 복원한다. 목 blob은 현재 브라우저 문서 수명 동안 유효하다.
6. 부분 업로드 후 남은 asset은 기존 서버 정리 정책에 맡긴다. 새 정리 API와 DB 구조를 만들지 않는다.
7. 중복 GIF는 원본 src로 합치고 가장 최근 저장 항목을 먼저 표시한다. 일반 이미지 탭과 GIF 사진 재료에 만든 GIF를 중복 노출하지 않는다.
