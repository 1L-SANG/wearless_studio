# Source-directed wearshot stages and owner length reference

The user approved separating mannequin color from explicitly preferred garment length, requested Flare first generation and Sunburst post-QC correction, and requested measured QC-off/QC-on latency plus honest generation lineage. This extends the existing opt-in pipeline. No Goal restart, merge, production activation, global legacy model switch, or private corpus publication.

## Required behavior

- Color remains owned by each target/matching approved mannequin. Permanent construction/material/details remain seller-owned. An explicitly selected owner-approved worn reference can own only that garment's body-relative length. It cannot replace face/model/scene/color/structure authority. Fit compares width/ease independently and must not reject an approved length indirectly through silhouette/fit.
- New optional `GarmentBinding.approved_length_key` refers to a garment-scoped `approvedLength` BoundReference. Without it, length falls back to mannequin. Old contract metadata/fingerprints and frozen v2 manifests remain compatible when the new optional fields are absent. New references/approval scope are hashed and validated; old failed observations are never relabeled PASS.
- New optional `directing_mode="source_locked_v1"` means the example is the first generation image/primary canvas and sole physical-place/camera/crop authority. Model/seller/mannequin/length references are not location donors. Capture rendering is prompt-only: a full capture photo is rejected in this mode, not silently attached or dropped. Pose may vary slightly; background variation, if chosen, stays in the same physical place. A wholly different cafe/room/location fails the background check even if minimum variation passes.
- Generation/repair/QC share the same explicit authority map. Repair still uses exact generated base + bound references and protects only verified axes. Hidden/partial/cropped scope remains honest; no forced head or trouser hem completion. Owner length approval changes the reference, not a QC PASS bit.
- Production optional request fields: `lengthReferenceAssets` maps selector `target` or a selected matching ID to an owned project image asset UUID; `directingMode` is null/absent or source_locked_v1. Empty/absent new options preserve the old request/snapshot shape. Check owner/project/nondeleted/type and reject seed-only, private-face storage and REAL/FaceMarket-derived assets in this virtual pilot. Normal owner-only DB visibility is not private-face storage: ordinary owned uploads and proven virtual assets on configured public R2 remain eligible. Unknown AI lineage holds; length selection grants neither public visibility nor a license bypass. Record/revalidate selected asset metadata and exact loaded bytes before generation. Approval grants only length. No new upload/UI/DB migration is part of this change.
- Model routing is v2-local. An optional WEARSHOT_GENERATION_MODEL chooses first-stage image model, while existing WEARSHOT_REPAIR_MODEL chooses second stage. Defaults remain unset so legacy and existing deployment settings are not switched. Experiment selects gpt-image-2 vs gpt-image-2.5-flare-2026-09-08 in stage1, and Image2 vs gpt-image-2.5-sunburst-2026-09-08 in conditional stage2. No provider fallback or automatic repeated submission.

## Timing and experiment protocol

Four source-directed cases (dress scene/capture, navy close crop, red cardigan face/color, navy+purple full body) use native 2K, medium quality and the same revised reference packet/prompt within each first-stage model comparison. Full capture photograph is absent; original example is first. Navy's explicit length reference is fr03-v1 in both relevant cases. Separate expression preferences are directions, not blanket approval of an entire generated person/outfit.

Generate each first-stage image once. Its measured completion time is the QC-off/unreviewed-preview path. Then evaluate that exact image through existing full v2 QC and focused visible-face check; only a failed result receives one second-stage correction, followed by final QC. Report measured image request times, QC stage times and their critical-path sum separately; exclude agent pauses/manual review/other-case queue time and label the sum accordingly. Do not claim these sums are stopwatch measurements of a separate no-QC production deployment. No-QC previews are not automatically approved for release.

Compare Image2→Image2 against Flare→Sunburst as workflows, because their stage1 outputs may trigger different repair sets. Do not call the second-stage differences a model-only same-base comparison; the previous paired-edit study already provides such observations. Four cases are a small workload sample, not universal speed/quality proof. Cap at eight new stage1 images plus at most eight conditional stage2 images, no extra repeats. Freeze all manifests/code before live calls; preserve existing history and record durations/provenance/uncertainty without keys or raw provider errors.

## Lineage and disclosure

Version numbers are experiment versions, not necessarily edit depth. Historical built-in backend model is unknown. The previous Sunburst outputs edited pre-existing built-in bases after GPT QC; none was Flare first-stage generation. Review artifacts must distinguish source, historical preferred base, fresh stage1, pre-QC verdict, optional stage2 and final verdict. Explain holds as conflicting references, not missing files or user failure to select.
