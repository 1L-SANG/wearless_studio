# 대표 색상 재현을 공유하는 의류 색상 생성

## 사용자 의도와 확정 범위

대표 색상에는 앞뒤와 디테일 사진이 충분하지만 추가 색상은 사진이 적다. 추가 색상 착용컷도 대표 색상의 풍부한 근거로 옷의 형태, 핏, 봉제선과 디테일을 재현하는 전 과정을 거친 뒤, 마지막에 해당 색상 원본을 적용한다. 단순히 색상별로 서로 다른 사진을 배치하는 과제가 아니다. 2026-11-06 사용자의 정정 설명이 앞선 독립안보다 우선한다.

사용자는 프로듀싱 새 콘티의 인스펙터에서 원하는 색상 하나만 선택한다. 생성 방식을 고르는 설정은 추가하지 않는다. 기존 업로드 개수 제한, 템플릿과 섹션 배치, 매칭 의류, 사용자 과금 정책은 유지한다.

## 최종 동작

1. 입력: 대표 색상의 사진은 공통 형태와 핏의 근거다. 추가 색상의 정면 사진은 그 색의 실제 색감과 배색 근거다. 스와치 이름이나 HEX로 실제 사진을 덮어쓰지 않는다.
2. 콘티: 한 칸의 `colorId`는 최종적으로 원하는 색이다. 인스펙터에서 색상 이름과 그 색에 첨부한 원본을 확인한다. 사진 없는 색은 이유와 함께 사용할 수 없게 한다. 제품컷의 원본 면 보정과 디테일의 기준색 제한을 유지한다.
3. 대표 색상 착용컷: 현재 전체 생성 파이프라인을 그대로 실행한다.
4. 추가 색상 착용컷: 같은 컷 설정으로 대표 색상 생성 파이프라인을 실행한다. 대표 색상의 사진, 분석, 마네킹과 기존 검수 규칙을 그대로 사용한다. 이 완성 이미지를 master로 삼고, 선택한 색상의 실사진으로 판매 의류의 색과 관찰 가능한 배색만 한 번 바꾼다. 인물, 자세, 핏, 봉제 구조, 주머니와 여밈, 코디, 장소, 빛의 방향을 유지한다.
5. 제품 단독컷: 선택한 색상의 실제 원본에서 직접 만든다. 없는 뒷면을 다른 색상의 뒷면 사진으로 묵시 대체하지 않는다. 디테일 촬영 대상의 현재 근거 제한은 유지한다.
6. 결과: 목표색 완성본만 페이지와 의류 탭에 넣는다. 중간 master는 사용자 사진 수나 크레딧 계산에 포함하지 않는다. 색상 적용 실패 시 대표색을 목표색으로 표시하거나 출고하지 않는다. 다른 성공 컷은 기존 부분 완료 정책에 따라 유지한다.
7. 추가 색상으로 다시 변경: 가능한 경우 보관한 대표색 master에서 다시 출발한다. 이전에 색을 바꾼 결과에 재차 덧입히는 연쇄 편집을 피한다. 기존 사진은 사용자가 교체하거나 추가를 선택하기 전까지 유지한다.
8. 비슷한 컷: 콘티의 후속 컷과 에디터의 비슷한 컷도 내부 대표색 원본에서 새 자세를 만든 뒤 목표색을 적용한다. 후속 컷은 새 자세의 대표색 원본을 따로 보관한다. 열림 정도처럼 의류 상태를 바꾼 옛 결과에는 이전 상태의 원본을 억지로 물려주지 않으며, 현재 상태의 사진을 새 시작점으로 삼는다.

## 좁은 생성 계약

클라이언트 저장 계약은 `block.colorId` 그대로다. 서버가 색상 그룹과 원본 자산 소유권을 해석한다. 클라이언트의 master, 내부 실행색, 근거 이미지 지정은 신뢰하지 않는다.

서버에서 목표색과 실행색을 구분한 계획을 만든다. `mode`는 `direct` 또는 `base_then_color`, `targetColorId`, `baseColorId`, `renderColorId`, 목표색 근거 자산 ID를 포함한다. 기준색을 의미하는 암묵값은 옛 요청의 색상 미지정에만 허용한다. 명시적으로 삭제된 색상은 실패한다.

완성 자산의 서버 메타데이터에는 실행 방식, 목표색, 대표색, 실제 색 근거 자산, 대표색 master 연결과 원본 해시를 기록한다. 자동 색 정확도 검사를 하지 않았다면 검사 통과로 기록하지 않는다. master는 같은 사용자와 프로젝트의 내부 자산으로 저장하며 의류 목록에는 추가하지 않는다. 기존 자산 테이블과 JSON 메타데이터를 사용하고 DB 마이그레이션은 추가하지 않는다.

목표색 전용 검수는 기존 검수가 `off`이면 실행하지 않는다. 그 밖의 설정에서는 구조, 질감, 인물과 장면, 목표색, 명백한 상품 불일치를 비교하고 명시적 불일치를 실패 처리한다. 기준색 단계의 shadow 판정을 목표색 출고 근거로 사용하지 않는다. 검수한 이미지의 해시와 범위를 기록하며, 이후 얼굴 목선 보정은 필요할 때 한 번만 실행한다.

최종컷 파이프라인의 출력 경계는 대표색 이미지, 해당 컷의 생성 설정과 근거다. 색상 적용은 이 출력 뒤의 별도 단계라서 최종컷 엔진을 바꿔도 동일하게 붙인다. 기존 확정 GPT 프롬프트의 hash와 기준색 권한을 변경하지 않는다.

## 비용, 실패와 재시도

- 추가색 착용컷에는 내부 색상 편집 호출이 한 번 추가된다. 사용자가 선택한 완성컷 수를 기준으로 기존 크레딧 정책을 유지하며, 중간 단계의 숨은 사용자 차감은 없다.
- 처음부터 모든 색을 자동 생성하지 않는다. 콘티가 요청한 컷만 생성한다.
- 최적화보다 정확성을 우선한다. 서로 다른 구도나 코디가 같은 master를 공유하지 않는다. 동일성 증명 없이 색을 제외한 키만으로 기존 중복 판정을 합치지 않는다.
- 목표색 근거가 없어지거나 바뀌면 실패 이유를 보존한다. 색상 적용 실패를 기준색 성공으로 바꾸지 않는다.
- 체크포인트는 목표색과 목표색 근거가 달라지면 이전 최종 결과를 재사용하지 않는다. 대표색 중간 이미지와 목표색 완성 이미지의 단계를 혼동하지 않는다.
- 원본 옷과 추가색 사진의 디자인 자체가 다르면 동일 상품 색상 변형으로 정확히 처리할 수 있다는 보장은 하지 않는다. 색상 단계는 옷 재설계 요청을 만들지 않는다.

## 검증과 완료 기준

- 대표색과 추가색의 입력 근거가 올바르고 저장 색상은 항상 목표색이다.
- 추가색 착용컷에서 대표색 전체 생성이 먼저, 색 적용이 그 뒤에 정확히 한 번 실행된다.
- 확정 GPT 추가색 컷이 기준색 전용 오류로 건너뛰어지지 않으면서 기존 기준색 계약을 보존한다.
- 제품컷은 목표색 원본에서 직접 만들고 색상 단계를 거치지 않는다.
- 색 적용 실패, 삭제된 색, 자산 변경, 재시도, 취소 및 체크포인트에서 잘못된 색을 출고하지 않는다.
- 내부 master가 사용자 의류 목록, 최종 장수, 중복 차감에 들어가지 않는다.
- 새 콘티의 색상 선택과 저장, 에디터 색상 확장이 연결된다.
- 기존 프론트와 서버 테스트, 빌드 및 가능한 브라우저 검사를 실행한다.
- GPT 이미지 검증을 할 경우 사용자 승인 상한은 합계 5달러다. 호출 수와 실제 사용량을 기록한다. 운영 배포, 커밋과 푸시는 이번 요청에 포함하지 않는다.
