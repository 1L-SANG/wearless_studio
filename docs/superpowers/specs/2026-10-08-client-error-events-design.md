# 오류 상황 자동 기록과 슬랙 알림 설계 (초안, 2026-10-08)

오너 요청(2026-10-08): 사용자 화면에 "서버 연결이 불안정해요"가 뜨면 그때 사용자의 상황을 알아서 문제를 확실히 파악할 수 있어야 한다. 자동으로 모으고, 슬랙으로 알린다.

## 1. 지금 상태

- AI 작업(마네킹, 상세페이지, 에디터 이미지) 실패는 `jobs` 표에 오류 문구가 남는다. 서버 4xx·5xx는 CloudWatch에 한 줄씩 남고(main.py 요청 로그 미들웨어), 5xx는 로그 알림(copilot/environments/addons/log-slack-alerts.yml)이 운영 슬랙으로 건별 전송한다.
- 요청마다 붙는 추적 번호가 없다. 로그의 `trace=`는 ALB 헤더였는데 10/2 ALB 철거로 지금은 비어 있다. 그래서 사용자가 본 오류와 서버 로그 한 줄을 이어 붙일 수 없다.
- 브라우저에서만 난 오류(연결 끊김, 시간 초과, CORS, 화면 오류로 흰 화면)는 어디에도 남지 않는다.
- 처리방침(documents/legal/11_wearless_privacy_policy_v1.md 66행)은 수집 항목에 "서비스 이용 기록, 오류 로그"를 이미 적고 있다.

## 2. 목표

오류가 사용자에게 보인 순간을 한 건의 기록으로 남기고, 그 기록 하나로 다음을 답할 수 있어야 한다.

1. 누가(사용자 id, 로그인 여부), 언제, 어떤 기기와 브라우저와 네트워크 상태에서
2. 어느 화면, 어느 단계, 어느 상품(프로젝트 id), 어느 작업(job id)에서
3. 어떤 동작을 하다가(사진 올리기, 분석, 마네킹 생성, 저장, 다운로드 등)
4. 직전에 무엇을 했는지(최근 동작과 요청 30개)
5. 서버의 어느 요청과 어느 로그 줄이 같은 일인지(추적 번호)
6. 사용자에게 무슨 문구가 보였는지

## 3. 구성

### 3-1. 추적 번호
- 브라우저가 API 요청마다 추적 번호를 만들어 `X-Client-Request-Id` 헤더로 보낸다. 요청이 서버에 닿지 못해도 브라우저 기록에는 번호가 남는다.
- 서버는 받은 번호(없으면 새로 만든 번호)를 요청 로그 두 줄(`http error`, `http request`)과 에러 봉투 응답 헤더 `X-Request-Id`에 싣는다. CORS `allow_headers`에 `X-Client-Request-Id`, `expose_headers`에 `X-Request-Id`를 더한다.
- AI 작업을 만든 요청의 번호를 작업 메타에 남겨, 작업 실패와 그 요청을 잇는다.

### 3-2. 브라우저 발자취(최근 30개, 메모리에만)
- 화면 이동(경로는 id를 `:id`로 바꾼 틀), 주요 동작(아래 목록), API 요청(방법, 경로 틀, 상태, 걸린 시간, 추적 번호, 오류 코드), 온라인과 오프라인 전환, 화면 숨김과 보임.
- 주요 동작: 사진 올리기, 사진 지우기, AI 분석, 의류 정보 확정, 콘티 진입, 마네킹 생성과 재생성, 상세페이지 생성, 에디터 저장, AI 이미지 생성과 수정, 다운로드, 폰 저장, 보관함 다시 열기.
- 넣지 않는 것: 입력한 글자(상품명, 문구), 사진 내용과 파일 이름, 이메일, 결제 정보, 토큰.

### 3-3. 오류 기록 한 건
- 언제 남기나: 사용자에게 오류 문구(토스트, 띠, 모달, 상태 화면)가 보일 때, 화면 전체 오류(오류 경계, `window.onerror`, `unhandledrejection`), AI 작업이 오류로 끝난 것을 화면이 알게 됐을 때.
- 담는 것: 발생 시각, 화면 빌드 번호, 화면 경로 틀과 단계, 프로젝트 id와 작업 id, 기기 종류(폰, 태블릿, PC)와 브라우저와 OS와 화면 크기, 온라인 여부와 네트워크 품질(가능할 때), 화면이 보이는 중이었는지, 페이지를 연 뒤 지난 시간, 동작 이름, API 정보(방법, 경로 틀, 상태, 오류 코드, 추적 번호, 걸린 시간, 실패 단계), 사용자에게 보인 문구, 기술 메시지(500자), 화면 오류면 스택(2,000자), 발자취 30개.
- 보내기: `POST /v1/client-events`. 로그인 중이면 인증을 같이 보내 서버가 사용자 id를 붙인다. 로그아웃 상태도 받되 IP 기준 속도 제한. 화면을 닫는 중이면 `sendBeacon` 또는 `keepalive`.
- 브라우저 쪽 절제: 같은 종류(서명)는 30초에 한 번, 한 세션에 최대 30건. 보내기 실패는 localStorage에 최대 20건 보관했다가 다시 연결되면 보낸다.

### 3-4. 서버 저장
- 새 표 `client_error_events`(새 전진 마이그레이션): id, 받은 시각, 사용자 id(없을 수 있음), 서명, 종류, 화면 경로 틀, 동작, 상태, 오류 코드, 추적 번호, 프로젝트 id, 작업 id, 기기 종류, 원문 jsonb(32KB 상한), IP는 해시로만. RLS로 일반 사용자 접근 차단, 서버만 쓴다.
- 받을 때 서버 로그에도 한 줄 남긴다(`client event ...`, INFO라 5xx 알림 필터에 안 걸림).
- 보관 30일, 매일 지난 기록을 지운다.

### 3-5. 슬랙 알림(운영 채널, 기존 `SLACK_ALERT_WEBHOOK_URL`)
- 몰림 알림: 같은 서명이 10분 안에 5건 이상이고 사용자 3명 이상이면 즉시 한 번. 같은 서명은 1시간에 한 번만. 화면 전체 오류(흰 화면)는 사용자 2명 이상이면 즉시.
- 하루 요약: 매일 오전 9시(한국 시간). 서명별 건수와 영향 사용자 수, 전날 대비, 대표 사례 3개(사용자 id, 추적 번호, 화면, 동작), AI 작업 실패를 종류와 오류 코드별로.
- 어디서 돌리나: API 서버 안의 주기 작업(draft_asset_reclaimer와 같은 방식), DB 잠금으로 여러 서버 인스턴스가 겹쳐 보내지 않게 한다.
- 기존 5xx 건별 알림은 그대로 둔다.

### 3-6. 조사
- 사용자 id나 추적 번호 하나로 그 사람의 오류 기록, 발자취, 같은 번호의 서버 로그 줄, 관련 작업을 시간순으로 뽑는 서버 스크립트(관리자 전용)와 사용법 문서.

## 4. 배포 순서

서버가 `X-Client-Request-Id` 헤더를 CORS에서 허용하기 전에 화면이 그 헤더를 보내면 모든 API 요청이 사전 요청에서 막힌다. 그래서 서버 PR(헤더 허용, 표, 받는 곳, 알림)을 먼저 머지하고 배포한 뒤 화면 PR을 머지한다. 화면은 서버 응답 헤더로 허용 여부를 확인하지 않고 순서로 보장한다.

## 6. 설계 검토 반영 (2판, 2026-10-08, Codex gpt-6.1-sol xhigh). 앞 절과 다르면 이 절이 정본이다

**추적 번호**
- 서버: 요청 로그 미들웨어(main.py 497행 근처) 시작에서 `X-Client-Request-Id`를 UUID로 검증하고, 없거나 잘못됐으면 새로 만들어 `request.state.request_id`에 둔다. `http error`의 `trace=`를 이 번호로 바꾸고 `http request`와 예외 로그에도 넣는다. 모든 응답(성공, 204, 401, 422, 봉투 500)에 `X-Request-Id`를 붙인다. CORS `allow_headers`에 `X-Client-Request-Id`, `expose_headers`에 `X-Request-Id`. 기존 허용 헤더는 그대로.
- 새 작업(job) 메타에 만든 요청의 번호를 남기고, 기존 작업에 합류하면 원래 번호를 지킨다.
- 브라우저: 자체 API로 가는 요청(httpAdapter `http`, `httpBlob`, `publicHttp`, personalization과 facemarket의 직접 요청, 목적지가 자체 API인 바이트 요청)에만 붙인다. Supabase 인증, blob과 data 주소, 정적 파일, CDN, R2 업로드와 다운로드, 외부로 넘기는 리다이렉트에는 붙이지 않는다.

**받는 곳 `POST /v1/client-events`**
- `optional_user`(auth.py 69행) 사용, 사용자 id는 검증된 토큰에서만. 브라우저가 보낸 프로젝트 id와 작업 id는 확인 안 된 값으로 저장한다.
- 제한: IP(HMAC)별, 사용자별, 전체 한도를 Postgres 원자 카운터로(facemarket.py 2240행 패턴). IP 제한은 토큰 확인보다 먼저. 한도 초과는 조용히 202로 버린다.
- 본문은 파싱 전에 실제 수신 바이트 32KiB 상한(Content-Length 없는 chunked 포함). 필드 허용 목록, 문자열 길이 상한, 발자취 30개, 서명은 서버가 계산(종류, 동작, 경로 틀, 상태, 오류 코드).
- 같은 `event_id`는 한 번만 저장(재전송 중복 제거).

**저장**
- 새 전진 마이그레이션: `client_error_events`(event_id UUID unique, schema_version, occurred_at, received_at, user_id null 가능, build_sha, signature, kind, route, action, status, error_code, request_id, project_id, job_id, device, blocking bool, ip_hmac, payload jsonb 정제본). 인덱스: (received_at), (signature, received_at) include (user_id), (user_id, received_at), (request_id). RLS 켬, 일반 역할 권한 회수, 허용 정책 없음.
- `client_alert_ledger`(종류 'burst' 또는 'digest', 키(서명 또는 KST 날짜), sent_at, 상태): 같은 알림을 두 번 보내지 않기 위한 영속 이력.
- 보관 30일, 회원 탈퇴 때 그 사용자의 기록 삭제.

**알림(API 서버 안 주기 작업, detail-worker에서는 돌지 않음)**
- `pg_try_advisory_lock`으로 한 인스턴스만 실행하고, 발송 전후로 원장을 확인해 순차 중복도 막는다(bank_transfer_expirer.py 24행 패턴 + 원장).
- 즉시 알림: 진행을 막는 오류(blocking: 화면 전체 오류, 저장·업로드·생성·분석 불가)는 같은 서명의 첫 건에 바로, 이후 같은 서명은 1시간에 한 번. 그 외 오류는 10분 안에 같은 서명 5건 이상일 때.
- 하루 요약: 매일 오전 9시 KST, 전날 KST 0~24시 구간. 서명별 건수, 영향 사용자 수(로그인 사용자만), 대표 사례 3개(event id, 추적 번호, 화면, 동작). 서버 재시작으로 놓친 요약은 다음 실행에 보낸다.
- 슬랙 메시지에는 사용자 id와 문구 원문을 싣지 않고 event id와 추적 번호만 싣는다. 조사는 DB에서 한다.
- 웹훅: API 매니페스트 `secrets`에 기존 SSM `/copilot/${COPILOT_APPLICATION_NAME}/${COPILOT_ENVIRONMENT_NAME}/secrets/SLACK_ALERT_WEBHOOK_URL`을 `SLACK_ALERT_WEBHOOK_URL`로 매핑하고 Settings에서 읽는다. 값이 없으면 알림만 건너뛴다. **이 SSM 파라미터에는 copilot 태그가 없다(10/8 실측).** 머지 전에 오너가 태그 두 개를 붙여야 배포가 멈추지 않는다(wearless-aws C-1).

**브라우저 수집**
- 공통 수집기 하나. 사용자에게 오류가 보이는 곳에서 확정한다: `ToastProvider.push`의 오류 변형(오류 객체를 함께 받는다), `ErrorState`, 콘티와 에디터의 저장 띠, 에디터 생성 띠, 사진 복원 모달, 내 옷 업로드 모달, 폰 저장 실패 모달, HandoffStatusPage 오류. 핵심 실패 호출은 문구만이 아니라 Error 객체를 넘겨 추적 번호를 잇는다. 일반 Modal 내용이나 DOM 텍스트는 수집하지 않는다.
- 루트 오류 경계(AppProviders)와 `window.onerror`, `unhandledrejection`을 앱 시작 때 설치한다.
- API 어댑터는 발자취만 쌓는다. 폴링 반복 GET은 한 줄로 압축(횟수, 마지막 상태). 동작은 허용된 이름으로만.
- 보내는 것: 문구 원문 대신 문구 코드(종류)와 서버 오류 코드. 기술 메시지와 스택은 정제(주소의 query와 hash, 파일 이름, 이메일 모양 제거). 입력값, DOM, store 전체, 파일 이름은 보내지 않는다. 상황 값: 사진 대기 수, 임시저장 작업권 상태, 로컬 백업 여부, 온라인 여부, 화면 보임 여부.
- 화면 빌드 번호: Vite `define`으로 Vercel 커밋 SHA(`VERCEL_GIT_COMMIT_SHA`)를 넣는다.
- 보내기: 작은 `fetch(..., {keepalive:true})`. 실패는 localStorage 큐(최대 20건, 24시간 TTL, event id)에 두고 다시 연결되면 보낸다. 로그아웃이나 계정 전환 때 큐를 비운다. 수집기 자신의 전송 실패는 기록하지 않는다. 같은 서명은 30초에 한 번, 세션당 30건.

**뺀 것**: 전날 대비, 별도 AI 작업 실패 집계(사용자에게 보이면 화면 기록으로 잡힌다), JSONB GIN 인덱스, 모든 클릭 자동 수집, 취소와 입력 안내의 장애 알림.

**처리방침**: 수집 항목은 이미 "서비스 이용 기록, 오류 로그"에 들어 있다. 화면 이동과 동작 순서, 30일 보관을 다음 개정 때 명시한다(오너 결정). 슬랙에는 개인정보를 보내지 않으므로 위탁 목록 추가는 필요 없다.

**검증**: preflight와 401·422·500 응답 헤더, 무효 토큰, chunked 초과 본문, RLS, 원장으로 중복 발송 방지(두 워커 동시), 계정 전환 때 큐 폐기.
