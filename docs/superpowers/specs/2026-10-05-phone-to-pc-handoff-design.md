- 상태: 오너 결정 반영(태블릿 B안), Codex 설계 검토 2라운드 반영(9장). 구현 대기.

- 검토 원문(gpt-6-astra, effort high): `.scratch/phone-handoff-20261005/codex-design-review.md`(1라운드), `codex-design-review-r2.md`(2라운드)

## 1. 목표

셀러는 상품 사진을 대부분 폰으로 찍는다. 그래서 역할을 이렇게 나눈다.
- **모바일 기기(폰과 태블릿):** 사진 담기까지만 한다.
- **PC:** AI 분석부터 상세페이지 완성까지 한다.

모바일에서 크레딧이 나가는 단계로 넘어가 PC용 화면(콘티, 마네킹, 에디터)에 갇히는 일을 없앤다.

**성공 기준**
1. 로그인한 모바일 사용자가 사진을 담고 버튼을 누르면, 사진이 서버에 **실제로 다 올라간 뒤에만** "저장했어요" 안내가 뜬다.
2. 같은 계정으로 PC에 로그인하면 그 상품이 첫 화면 카드로 뜬다. 열면 사진이 **한 장도 빠짐없이** 있고, PC에서 "AI 분석하기"와 확정이 동작한다.
3. 모바일에서는 AI 분석, 의류정보 확정, 콘티 이후 화면에 들어갈 수 없다.
4. 다른 기기가 담은 사진을 **지우거나 다른 내용으로 덮는 모든 선택**은 지워질 장수를 보여주고 한 번 더 확인받는다.
5. 사진 일부를 확보하지 못한 상태로는, 사용자가 명시적으로 동의하기 전까지 확정이 진행되지 않는다.

## 2. 오너 확정 사항 (2026-10-05)

| 항목 | 결정 |
|---|---|
| 모바일의 범위 | 사진 담기까지. 버튼을 누르면 PC에서 이어하라는 안내창을 띄우고 사진이 저장됐다고 알려준다 |

| 나머지 문제 | Claude가 해결책을 세운다 |

## 4. 기기 구분

새 파일 `src/lib/deviceClass.js`를 만든다. 순수 함수로 `'phone' | 'tablet' | 'desktop'`을 돌려준다. **사용자 에이전트(UA) 정보만으로 판정한다.** 터치 여부나 화면 크기만으로 판정하는 보조 규칙은 두지 않는다. 터치 화면 윈도우 PC를 모바일로 잘못 막을 수 있기 때문이다.

**폰**
- UA에 `iPhone`이나 `iPod`이 있다.
- UA에 `Android`와 `Mobile`이 함께 있다.
- `navigator.userAgentData.mobile === true`이다.

**태블릿**
- UA에 `iPad`가 있다.
- UA는 `Macintosh`인데 `navigator.maxTouchPoints > 1`이다.
  - 아이패드 사파리는 기본으로 자기를 맥이라고 소개하고, 실제 맥에는 터치 화면이 없다.
  - 아이폰에서 "데스크톱 웹사이트 요청"을 켠 경우도 여기에 걸린다. 결과는 같다(모바일 정책).
- UA에 `Android`는 있는데 `Mobile`은 없다.
- UA가 `Linux`(크롬북 `CrOS` 제외)이고 `navigator.maxTouchPoints > 1`이다. 갤럭시 탭 삼성 인터넷의 기본 데스크톱 모드와 안드로이드 폰의 "데스크톱 사이트 보기"가 여기에 걸린다(10/5 모바일 QA에서 발견).

**그 밖**은 데스크톱이다. 윈도우, 리눅스, 터치 없는 맥이 여기에 해당한다.

**판정과 정책**
- 페이지를 처음 열 때 한 번만 판정한다. 화면을 돌리거나 창 크기가 바뀌어도 도중에 모드를 바꾸지 않는다.
- 기기별 정책은 한 곳의 표에서만 정한다: `HANDOFF_POLICY = { phone: 'handoff', tablet: 'handoff', desktop: 'full' }`. 나중에 태블릿을 풀어주려면 이 표 한 줄만 바꾼다.
- 이 문서에서 **"모바일"은 정책이 `handoff`인 기기**를 뜻한다.

**기기 라벨 (카드 문구용)**
- `getDraftSlotDeviceLabel`([draftSlot.js:43-51](../../../src/lib/draftSlot.js))을 `deviceClass`와 맞춘다.
  - 맥 UA에 터치가 있으면 `iPad`로 적는다.
  - UA에 `Android`만 있고 `Mobile`이 없으면 `Android 태블릿`으로 적는다.
- 카드 제목은 라벨로 정한다(오너 10/5 확정). 아래에서는 이 제목을 **"{기기} 작업 이어가기"**로 적는다. "만들던 상세페이지" 카드는 진한 회색 테두리, "{기기} 작업 이어가기" 카드는 파란색(`--link`) 테두리로 구분한다.
  - iPhone, Android: "스마트폰 작업 이어가기" (명사 "스마트폰")
  - iPad, Android 태블릿: "태블릿 작업 이어가기" (명사 "태블릿")
  - 그 밖: 지금 문구 그대로

## 5. 화면과 동작

### 5-1. 모바일

**M1. 로그인 먼저**
- **대상:** `/create/input`에 들어온 비로그인 모바일 사용자. ai.wearless.kr 루트로 들어와도 이 화면으로 온다.
- **가드 위치:** `ProductInputRoute`에서 `ProductInput`을 그리기 **전**에 둔다. 그래야 입력 화면의 복원, 동기화, 자동 저장 effect가 아예 돌지 않는다.
- **화면:** 사진 칸 대신 짧은 소개를 보여준다.
  - 문구: "상품 사진을 여기서 담아두면, PC에서 바로 이어서 만들 수 있어요."
  - 버튼: "로그인하고 사진 담기". 누르면 기존 로그인 창이 열린다. 로그인 후 돌아올 곳은 `/create/input`이다.
- **앱 안 브라우저 안내를 셀러 쪽에서도 켠다.** [Login.jsx:212](../../../src/features/auth/Login.jsx)의 `IS_FACEMARKET` 조건을 넓힌다.
  - 카카오 버튼을 먼저 보여준다.
  - 구글 로그인이 막힌다고 안내한다.
  - 카카오톡이면 "다른 브라우저로 열기"를 준다.
  - 다른 브라우저로 옮긴 경우 로그인은 그 브라우저에서 처음부터 다시 시작한다. 카카오 로그인은 시작한 탭의 sessionStorage에 의존하므로 콜백 주소만 옮기면 실패한다. [kakaoOidc.js:70, 113](../../../src/lib/kakaoOidc.js)
- **모바일 `RootRedirect`:** 로그인 복귀 목표가 콘티이고 로컬 초안이 있어도, 프로젝트를 자동으로 만들지(승격하지) 않는다. 항상 `/create/input`으로 보낸다. [App.jsx:509-548](../../../src/apps/seller/App.jsx)
- **이미 남아 있던 게스트 초안:** 배포 전부터 열려 있던 탭에 IndexedDB 초안이 남은 경우다. 로그인 뒤 기존 진입 창에서 "이 기기" 카드로 고를 수 있게 둔다. 서버 칸을 자동으로 덮지 않는다.
- **로그인 뒤 진입 판정을 다시 한다.** 지금은 비로그인 상태에서 진입 판정이 `continue`로 끝나면 다시 조회하지 않는다. 이메일 로그인은 페이지를 새로 열지 않으므로 그대로면 진입 창이 뜨지 않는다. [App.jsx:244-252](../../../src/apps/seller/App.jsx), [Login.jsx:165](../../../src/features/auth/Login.jsx)
  - 모바일에서는 로그인 전에 진입 판정을 시작하지 않는다.
  - 로그인한 사용자가 바뀌면 판정을 `checking`으로 되돌린다.
- **PC는 지금과 똑같다.** 로그인 없이 분석까지 체험할 수 있다.

**M2. 사진 담기**
- 지금의 입력 화면(색상, 사진 칸, 상품명)을 쓰되 폰 폭에 맞춘다(5-4).
- **주 버튼 문구:** PC는 "AI 분석하기", 모바일은 **"저장하고 PC에서 이어하기"**다.
- **누를 수 있는 조건**
  - 기본 색상의 앞면과 뒷면 사진이 있어야 한다. PC 분석과 같다. [ProductInput.jsx:1203-1207](../../../src/features/product-input/ProductInput.jsx)
  - 사진을 불러오는(HEIC 변환) 중인 것이 없어야 한다. 변환 중이면 버튼을 막고 "사진을 불러오는 중이에요"를 보여준다. [ProductInput.jsx:227-268](../../../src/features/product-input/ProductInput.jsx)
- 모바일에서는 AI 분석을 호출하지 않는다. 분석 결과 화면(AnalysisForm)도 그리지 않는다.

**M2-1. 분석까지 된 상품을 모바일에서 열었을 때**
- 발생 경로: PC에서 분석만 하고 확정하지 않은 상품을 모바일에서 연 경우.
- 지금 코드는 이 상품을 `phase='done'`으로 복원해서, 주 버튼이 사라진다. [ProductInput.jsx:930-940, 1428](../../../src/features/product-input/ProductInput.jsx)
- 모바일에서는 사진을 **읽기 전용**으로 보여준다. 안내 문구: "이 상품은 PC에서 분석까지 마쳤어요. PC에서 이어서 진행해 주세요."
- 사진 편집과 주 버튼은 보여주지 않는다. 분석 결과는 건드리지 않고 칸에 그대로 둔다.
- 할 수 있는 일은 "지우고 새 상품 담기"(M4의 확인 규칙 적용)뿐이다.

**M3. 안내창 (버튼을 누른 뒤)**

| 상태 | 제목 | 본문 | 버튼 |
|---|---|---|---|
| 저장 중 | 사진을 저장하고 있어요 | 다 저장될 때까지 이 화면을 닫지 말아 주세요. | 없음(진행 표시) |
| 완료 | 사진 N장을 저장했어요 | PC에서 같은 계정으로 로그인하면 바로 이어져요. (위에 옷 태그 그림, 아래에 주소 복사 칩) | 확인 |
| 실패 | 사진을 다 저장하지 못했어요 | 인터넷 연결을 확인하고 다시 시도해 주세요. | 다시 시도, 닫기 |
| 작업권 없음 | 다른 곳에서 이 상품을 이어서 작업하고 있어요 | 지금 화면의 저장을 멈췄어요. | 확인 |

- **"완료" 판정은 서비스 계층의 새 함수 하나가 맡는다.** `draftSlot.saveAll(snapshot)`이 결과 `{ status: 'saved' | 'failed' | 'locked', photoCount }`를 돌려준다. `saved`의 조건은 셋이다.
  1. 스냅샷에 든 모든 사진의 업로드가 성공했다(업로드 대기는 `waitForUploads`, [draftSlot.js:516](../../../src/lib/draftSlot.js)).
  2. 그 사진 전부를 참조하는 마지막 저장(PUT)이 성공했다.
  3. 남은 대기 사진이 0장이다(`photosPending=false`).
- **지금의 `flush()`는 저장 대기열만 기다리고 업로드는 기다리지 않는다.** [draftSlot.js:546](../../../src/lib/draftSlot.js) 그래서 `flush()`만으로 "완료"를 판정하면 안 된다.
- **오래된 업로드 기록은 다시 올린다.** 사진 업로드가 성공한 뒤 그 사진을 참조하는 저장(PUT)이 24시간 넘게 성공하지 못했으면, 그 업로드 기록을 버리고 다시 올린다.
  - 이유: 서버 정리 작업은 업로드 후 7일이 지나고 어느 칸에서도 참조하지 않는 사진을 지운다(8-1). 탭이 오래 살아 있다가 저장이 늦게 성공하면, 이미 지워진 사진을 가리키는 칸이 생길 수 있다.
  - 24시간이면 정리 작업까지 6일의 여유가 남는다.
- 저장 중에는 사진 편집을 막는다.
- "완료" 뒤 사진을 고치면, 상태 카드를 회색 새로고침 아이콘과 "사진이 바뀌었어요" / "아래 버튼을 다시 눌러 저장해 주세요."로 바꾼다. 버튼을 누르면 다시 `saveAll`을 거친다.
- 장수 진행률(4/6장)은 MVP에서 뺀다. 지금 업로드 정보는 "대기 중인가"만 알려주기 때문이다. [draftSlot.js:304, 576](../../../src/lib/draftSlot.js)
- **완료 안내창 디자인(오너 10/5 2차):** 404 페이지와 같은 옷 태그 그림을 가운데에 둔다. 태그에는 사진 장수를 가격표처럼 크게, 그 아래 "PHOTOS SAVED", 세탁 기호 자리에 "KEEP 7 DAYS"를 새긴다(보관 기간을 문장 대신 태그에). 태그 틀은 `HangTag.jsx` 하나로 PC 안내 화면과 함께 쓴다.
- **주소 복사 칩:** `ai.wearless.kr` 옆에 복사 아이콘, 누르면 사이트 주소를 복사하고 "주소를 복사했어요" 토스트. 복사가 막히면 "PC에서 ai.wearless.kr로 접속해 주세요". 높이 40px 이상. 상품 정보는 링크가 아니라 계정에 담겨 전달되므로 링크 공유 기능은 두지 않는다(오너 10/5).
- **"확인"을 누른 뒤:** 사진 화면 위에 저장 상태 카드를 남긴다. 초록 체크 원과 두 줄("사진 N장을 저장했어요" / "PC에서 ai.wearless.kr에 같은 계정으로 로그인하면 이어서 만들 수 있어요.").

### 5-2. PC

**C1. 카드 문구**
- 다른 기기 카드의 라벨이 모바일이면, 카드 제목을 "{기기} 작업 이어가기"으로 바꾼다.

**C2. 확정한 작업이 있어도 모바일 상품을 보여준다**
- **문제:** PC에 확정까지 간 작업이 있으면, 진입할 때 임시저장 확인을 아예 건너뛰고 콘티로 보낸다. 이 판정은 초기값과 후속 effect 두 곳에 있다. [App.jsx:227-231, 325-354](../../../src/apps/seller/App.jsx)
- **해결:** 이 경우에도 서버 칸을 조회한다. 다른 기기가 쓴 칸이 있으면 진입 창에 카드 두 장을 보여준다.
  - "만들던 상세페이지": 지금의 이어하기와 같다.
  - "{기기} 작업 이어가기": 카드 아래에 "지금 만들던 상세페이지 대신 이 상품으로 시작해요"라고 적는다.
- **"{기기} 작업 이어가기"을 고르면 이 순서를 지킨다.**
  1. 넘겨받기로 원격 내용을 먼저 확보한다.
  2. 확보에 성공한 뒤에만 이 브라우저의 진행 흐름을 초기화한다(`beginProject`).
  3. 확보한 내용을 stage한다.
  4. 입력 화면으로 간다.

  기존의 원격 카드 선택 순서와 같다. [App.jsx:395-418](../../../src/apps/seller/App.jsx) 서버 칸부터 지우는 `startNew`([App.jsx:381-392](../../../src/apps/seller/App.jsx))는 재사용하지 않는다. 넘겨받기에 실패하면 기존 진행 상태를 그대로 둔다.
- **바꾸지 않는 것:** 원격 칸이 없을 때의 기존 동작은 그대로 둔다. 확정 입력 잠금과, 7초 안 재진입 시 새로 시작하는 분기가 여기에 해당한다. [flowSession.js:48, 68](../../../src/lib/flowSession.js), `tests/frontend/confirmed-input-lock.test.mjs`

**C3. 상단 "새로 시작하기"가 모바일 상품을 조용히 지우지 않게 한다**
- **문제:** 상단 "상세페이지 제작"을 누르면 나오는 이어하기 창에서 "새로 시작하기"를 누르면, 모바일 상품이 보이지도 않은 채 칸이 지워진다. [shell.jsx:40-51](../../../src/features/shell/shell.jsx)
- **해결:**
  - 창을 열 때 서버 칸을 조회한다.
  - 다른 기기가 쓴 칸이 있으면 `ResumeChoiceModal`의 `sources`로 "{기기} 작업 이어가기" 카드를 함께 보여준다.
  - 카드 선택은 C2와 같은 서비스 함수와 같은 순서로 처리한다. C2와 C3를 두 벌로 구현하지 않는다.

**C4. 덮어쓰기와 삭제의 공통 규칙**
- **확인 대상:** 다른 기기가 마지막으로 쓴 칸을 **지우거나 다른 내용으로 대체하는 모든 선택**은 확인창을 거친다. 해당하는 선택은 셋이다.
  - 진입 창의 "새로 시작하기" [App.jsx:381-392](../../../src/apps/seller/App.jsx)
  - 상단 이어하기 창의 "새로 시작하기" [shell.jsx:40-51](../../../src/features/shell/shell.jsx)
  - 원격 카드가 함께 보일 때 **"이 기기에서 입력하던 내용" 카드를 고르는 것**. 이 기기 내용으로 원격 칸을 덮는다. [App.jsx:419](../../../src/apps/seller/App.jsx)
- **확인 문구:** "{기기}에서 담아둔 사진 N장이 지워져요."
- **실행 직전 재확인:** 확인 후 실제로 실행하기 직전에 서버 칸을 다시 조회한다. 사용자가 본 칸과 같은지 `updatedAt`으로 비교하고, 그사이 바뀌었으면 실행하지 않고 창을 새 내용으로 다시 보여준다.
- **조회 실패:** 서버 칸 조회가 실패하면 "원격 내용 없음"으로 간주하지 않는다. 지우거나 덮는 선택을 막고 "잠시 후 다시 시도해 주세요"를 보여준다.
- **남는 위험 (MVP에서 감수):** 재조회와 실제 변경은 별도 요청이라, 그 사이 수백 밀리초 안에 다른 기기가 저장하면 그 최신 내용이 지워질 수 있다. 막으려면 서버의 넘겨받기에 "예상 버전" 조건을 넣어야 한다(서버 계약 변경). 틈이 네트워크 왕복 한 번뿐이라 MVP에서는 감수하고, 실제 신고가 생기면 서버 조건을 넣는다. [routes.py:1956-1982](../../../server/app/routes.py)
- **그대로 두는 것**
  - 잠금 화면의 "지우고 새로 시작"([ProductInput.jsx:991-1000](../../../src/features/product-input/ProductInput.jsx))은 잠금 상태에서 사용자가 직접 고르는 명시적 선택이라 그대로 둔다.
  - 잠금 화면의 "어느 내용으로 이어갈까요?" 선택([ProductInput.jsx:942-960, 1338-1350](../../../src/features/product-input/ProductInput.jsx))도 그대로 둔다. 두 내용의 저장 시각을 보여주고 "고르지 않은 쪽은 덮어써요"라고 이미 알리는 명시적 선택이다.
  - 로그아웃은 서버 칸을 지우지 않는다. 이 기기의 토큰, 동기화 상태, 로컬 초안만 정리한다. 지금 동작 그대로다. [draftSlot.js:705-719](../../../src/lib/draftSlot.js)

**C5. 업로드가 덜 끝난 상품 카드**
- 카드에 사진 저장이 덜 끝났다는 표시(`photosPending`)가 있으면, 지금은 경고만 띄우고 넘겨받기를 허용한다. [shell.jsx:139](../../../src/features/shell/shell.jsx) 그런데 넘겨받으면 모바일에 남은 업로드는 버려진다. [draftSlot.js:339](../../../src/lib/draftSlot.js)
- 이 경우 카드를 바로 열지 않는다. 이렇게 안내한다.
  - 문구: "{기기}에서 아직 사진을 올리고 있어요. 잠시 후 다시 확인해 주세요."
  - 버튼: "다시 확인"(서버 칸을 다시 조회한다), "지금 있는 사진 N장으로 열기"
- 두 번째 버튼은 모바일 탭이 닫혀 영원히 기다리는 일을 막기 위한 탈출구다. 누르면 C4 확인창을 거친다. 문구: "아직 올라오지 않은 사진은 빠져요."

**C6. PC가 원격 사진을 확실히 확보한다 (검토 1번, 치명)**
- **바이트 경로:** 원격 사진(주소가 `/v1/assets/{id}/file`인 사진)의 바이트는 `/v1/assets/{id}/bytes`로 받는다. 적용할 곳은 두 군데다.
  - 로컬 초안 저장: [draftStore.js:80-89](../../../src/lib/draftStore.js)
  - 공개 분석: [httpAdapter.js:464](../../../src/lib/api/httpAdapter.js)
- **바이트 경로를 바꾸는 이유:** 지금의 `/file`은 R2 공개 주소로 넘겨준다(302). 화면의 `<img>`가 그 주소를 먼저 받아 두면, 허가 헤더가 없는 사본이 브라우저 캐시에 1년치로 남는다. 그러면 뒤이은 `fetch`가 CORS로 막힌다. 2026-08-26 실서버에서 재현된 문제다. [draftStore.js:67-80](../../../src/lib/draftStore.js)
  - 로컬 초안 저장에는 한 번 더 받는 우회가 있지만, 공개 분석에는 없다.
  - `/bytes`는 `Vary: Origin`이 붙어 이 문제가 없다. 초안 자산도 서빙하며 원본 바이트를 재인코딩 없이 보낸다(Codex 2라운드 확인). [repo.py:1208](../../../server/app/repo.py), [r2.py:234](../../../server/app/r2.py)
  - 확정 때 서버의 원본 대조(SHA-256, MIME, 바이트 길이)는 **사진 목록, 순서, 슬롯, MIME이 분석 때와 같고 분석 결과가 유효할 때** 통과한다. [product_evidence_contract.py:150, 868](../../../server/app/agents/product_evidence_contract.py)
- **응답 검증:** 바이트를 받을 때 세 가지를 확인하고, 하나라도 아니면 실패로 던진다. 기존 사진 정보의 MIME으로 오류 응답을 사진처럼 다루면 안 된다. 지금은 HTTP 상태를 보지 않는다. [draftStore.js:83, 98](../../../src/lib/draftStore.js), [httpAdapter.js:464](../../../src/lib/api/httpAdapter.js)
  - HTTP 성공(`response.ok`)
  - 응답 MIME이 이미지
  - 본문이 비어 있지 않음
- **원격 사진은 내려받기에 실패해도 상품에서 빼지 않는다.** 지금의 로컬 초안 저장은 받지 못한 사진을 상품에서 빼고 저장한다. [draftStore.js:114-134](../../../src/lib/draftStore.js) 그러면 그 로컬 사본이 나중에 복원되고 자동 저장으로 서버 칸까지 덮여, 사진이 영구히 사라질 수 있다(Codex 2라운드 치명).
  - 주소가 원격 자산(`/v1/assets/{id}/file`)인 사진은 받기에 실패해도 상품에 원격 주소 그대로 남긴다. 로컬 바이트만 없는 상태로 둔다.
  - 그 바이트는 다음 저장이나 확정 때 다시 받는다.
  - `blob:` 사진(이 기기에서 고른 사진)의 기존 처리는 그대로 둔다.
- **확정 차단:** 확정(`goToStoryboard`) 중 사진 수집에 실패한 장수가 1 이상이면, 칸 삭제(`draftSlot.remove()`) **전에** 멈춘다. [ProductInput.jsx:737-746](../../../src/features/product-input/ProductInput.jsx)
  - 지금은 안내 토스트만 띄우고 진행한다. 이 토스트는 없앤다.
  - 창 문구: "사진 N장을 불러오지 못했어요."
  - 기본 버튼은 "다시 시도"다.
  - **"이 사진을 빼고 계속"은 실패한 사진이 모두 분석에 쓰지 않은 사진일 때만 보여준다.**
    - 분석에 쓴 사진은 기본 색상에서 앞면과 뒷면을 우선해 최대 4장이다. 프론트는 `selectPublicAnalysisPhotos`, 서버는 같은 규칙을 쓴다. [publicAnalysisPhotos.js:7-23](../../../src/lib/publicAnalysisPhotos.js), [detail_recommendations.py:76](../../../server/app/agents/detail_recommendations.py)
    - 분석에 쓴 사진을 빼면 서버 원본 대조에서 거절된다. 그래서 이 경우에는 "분석에 쓴 사진이라 빼고 진행할 수 없어요. 다시 시도해 주세요."를 덧붙이고 "다시 시도"만 준다.
  - "이 사진을 빼고 계속"을 눌렀을 때만 해당 사진을 상품에서 빼고 진행한다.
  - 이 규칙은 같은 기기에서 확정할 때도 똑같이 적용한다.

## 8. 서버 변경과 범위 밖

**8-1. 서버 변경 (한 줄)**
- 임시저장 사진 정리 작업은 업로드 후 60분이 지나고 어느 칸에서도 참조하지 않는 사진을 지운다. [repo.py:332-377](../../../server/app/repo.py), [draft_asset_reclaimer.py:45](../../../server/app/workers/draft_asset_reclaimer.py)
- 문제: 모바일에서 업로드는 끝났는데 마지막 저장(PUT)이 한 시간 넘게 늦어지면, 이 사진들이 먼저 지워진다. 화면을 잠그거나 앱을 바꾸면 흔히 생기는 일이다. 그 뒤 PUT이 성공하면 지워진 사진을 가리키는 칸이 남는다.
- 해결은 두 겹이다.
  1. 서버: 정리 작업 호출에 `older_than_minutes=7*24*60`을 넘긴다.
  2. 브라우저: 24시간 넘게 저장에 반영되지 못한 업로드 기록은 다시 올린다(M3).
- 두 기간은 기준이 다르다. 정리 작업은 자산 생성 시각부터, 칸 보관은 마지막 PUT부터 센다. 그래서 같은 7일이라도 하나의 수명 계약이 아니다. 2번 규칙이 그 차이를 메운다.
- Codex는 서버에서 PUT 때 사진 존재를 검증하는 방법도 제안했다. 위 두 겹으로 같은 효과를 서버 계약 변경 없이 얻으므로 택하지 않는다. 그래도 남는 경우는 C6 확정 차단이 PC에서 막는다.

## 10. 기기 간 상황 정책 (2026-10-05, 오너 질문 "폰으로 또 올릴 경우")

분석 에이전트 3개(기기 순서와 작업권, 확정 뒤와 계정, 실패와 시간)가 코드로 상황 40여 개를 추적했고, Claude가 근본 원인을 코드로 확인했다.

### 10-1. 근본 원인

1. **서버가 사진을 즉시 지운다.** 칸을 지우거나 덮어쓰면 빠진 사진을 바로 삭제한다. [routes.py:468-475, 1925-1938, 2016](../../../server/app/routes.py) 다른 기기 화면에는 지워진 사진 주소가 남아 분석과 확정이 404로 막힌다.
2. **브라우저가 업로드 기록을 계속 믿는다.** 칸이 사라진 뒤에도 업로드 기록(synced)을 그대로 쓴다. [draftSlot.js:701-709, 383-401](../../../src/lib/draftSlot.js) 그래서 "이 사진으로 다시 업로드"가 지워진 사진을 가리키는 칸을 만들고 "저장했어요"가 뜬다. 성공 기준 1 위반이다.
3. **폰에 "PC가 열었어요", "PC가 마무리했어요" 상태가 없다.** 넘겨주기 성공도 잠금 화면으로 보이고, 폰이 PC의 작업을 되찾거나 지울 수 있다.
4. **저장 완료 뒤 폰에서 사진을 바꾸면, 확인 없이 저장된 상품이 바뀐다.** 다음 상품을 올리려는 가장 자연스러운 조작이 이렇다.
5. **PC는 확정 뒤 미완성 작업을 다시 열 길이 없다.** 보관함은 완성본만 보여준다. [repo.py:773](../../../server/app/repo.py)
6. **폰 보관함에서 완성본을 열면 PC ONLY 화면과 입력 화면을 끝없이 오간다.** [Library.jsx:20-23](../../../src/features/library/Library.jsx), shell.jsx `useDoneGuard`
7. **PC 입력 화면을 먼저 열어 두면, 폰 상품 카드가 새로고침 전까지 뜨지 않는다.**
8. **이미 쓴 토큰으로 지우기를 요청해도, 칸이 없으면 204를 돌려준다.** [routes.py:2004-2022](../../../server/app/routes.py)

| 7 | 폰 진입 카드가 PC가 쓴 칸 | 카드 제목 "PC에서 만드는 중인 상품". 누르면 넘겨받지 않고 읽기 전용으로 보여준다 |
| 8 | PC 입력 화면이 비어 있고 작업권이 없는 채로 창에 돌아옴 | 서버 칸을 다시 확인해서 폰 상품 카드를 띄운다 |
| 9 | PC에 확정한 작업이 있는데 폰 카드를 고름 | 확인창 "만들던 상세페이지(콘티 단계)는 다시 열 수 없어요. 이미 쓴 크레딧은 돌아오지 않아요.", 기본 버튼 "만들던 것 이어서 하기". 상단 "새로 시작하기" 확인에도 같은 문장을 넣는다 (결정 D2에 따라 바뀜) |
| 10 | 폰 보관함 | 완성본을 누르면 열지 않고 "완성본은 PC에서 열어 주세요"를 안내한다. 폰 입력 화면은 저장된 PC 흐름을 무시한다 |
| 11 | 서버 | 칸을 지우거나 덮어쓸 때 사진을 즉시 지우지 않고 7일 정리 작업에 맡긴다. 이미 쓴 토큰의 DELETE는 칸이 없어도 409 |
| 12 | 브라우저 | 칸이 사라졌거나 넘겨받기가 204면 업로드 기록을 비우고 이 기기 사진을 다시 올린다. `saveAll`은 `gone`을 `locked`와 따로 돌려준다 |
| 13 | 폰 저장 중 창 | 2분 넘게 끝나지 않으면 실패로 바꾼다. 화면이 다시 보이면(visibilitychange) 재시도와 작업권 확인을 한다. 실패 창이 떠 있는 동안 배경 재시도가 성공하면 완료로 바꾼다 |
| 14 | 사진 올리는 중 카드(PC) | 마지막 저장 시각을 보여준다. 탈출 확인 버튼은 "이대로 열기" |
| 15 | 카드 | 상품명과 첫 사진 썸네일을 보여준다(서버 meta만 추가, 마이그레이션 없음). "방금 저장"으로 문법을 고친다. 넘겨받기 때 기기 라벨도 갱신한다 |
| 16 | 폰 저장 완료 창 | 로그인 방법을 안내한다. 예: "카카오 계정에 저장했어요. PC에서도 카카오로 로그인해 주세요." (결정 D4) |
| 17 | PC 확정 중 사진 받기 실패 | 404와 일시 오류를 나눈다. 받기에 실패해도 이미 받아 둔 바이트는 지우지 않는다. 진입 조회에 실패하면 "저장된 상품을 확인하지 못했어요"와 "다시 확인"을 보여준다(조용히 덮어쓰지 않게) |

### 10-3. 오너 결정 (2026-10-05 확정)

- **D1. 물어본다.** 폰에 이미 저장된 상품이 있으면, 어떤 상품인지(사진, 이름, 장수, 저장 시각) 보여 주고 "그대로 두기"와 "버리고 새로 올리기" 중에서 고르게 한다. PC가 만드는 중이면 버리면 PC 작업도 사라진다고 알린다. 상세는 10-5.
- **D2. 다음 PR로 따로 한다.** 콘티와 마네킹 단계의 작업을 보관함에 "만드는 중"으로 보이고 그 단계로 다시 연다. 다른 브라우저와 엉키는 경우 등 생길 일을 먼저 조사해, 꼭 막을 것과 감수할 것을 나눈 뒤 구현한다. 이번 PR에서는 그 작업을 버리게 되는 순간에 경고만 띄운다(10-5의 E).
- **D3. 그렇게 한다.** 저장 완료 뒤 사진 칸을 잠그고 "사진 고치기"와 "다음 상품 올리기"를 둔다.
- **D4. 계정을 알려 준다.** 저장 완료 창에 어느 계정에 저장됐는지(예: "카카오 · 홍길동", "구글 · name@gmail.com")와 "PC에서도 이 계정으로 로그인해 주세요"를 보여 준다.

### 10-4. 범위 밖 (기록만)

- 카카오와 구글 계정 연결

### 10-5. 결정 반영 화면 (D1, D3, D4, 경고)

"작성 기기"는 칸 meta의 `deviceLabel`로 가른다. `getDraftDeviceNoun`이 스마트폰이나 태블릿을 돌려주면 폰이 쓴 칸, 아니면 PC가 쓴 칸이다(넘겨받기 때 라벨이 갱신되므로 PC가 열면 PC가 쓴 칸이 된다).

**A. 편집.** 지금의 폰 입력 화면. 아래 버튼 "저장하고 PC에서 이어하기".

**B. 저장됨 (D3).** 저장 완료 창을 닫았을 때, 또는 진입 때 폰이 쓴 칸을 "그대로 두기"로 열었을 때. 상품명, 색상, 사진 칸이 모두 잠긴다(추가, 삭제, 이름 수정 불가). 위에 저장 상태 배너, 아래 버튼 자리에 알약 두 개 [사진 고치기] [다음 상품 올리기].
- 사진 고치기: 같은 상품으로 A에 돌아간다. 고치는 동안 배너는 "사진이 바뀌었어요, 아래 버튼을 다시 눌러 저장해 주세요"를 보여 준다(지금 동작). 다시 저장하면 B로 돌아온다.
- 다음 상품 올리기: 칸이 보이면 D1 창, 칸이 없으면(PC 확정, 만료) 확인 없이 빈 A.

**C. PC가 만드는 중.** 진입 때 PC가 쓴 칸을 "그대로 두기"로 골랐을 때, 또는 이 탭이 작업권을 잃었는데 가져간 쪽이 PC일 때. 입력 영역 대신 상태 카드 하나: 상품 줄(썸네일, 이름, 사진 장수, 저장 시각), "PC에서 이 상품을 이어서 만들고 있어요", [다음 상품 올리기]. 되찾기 버튼은 없다. 이 상태에서는 칸에 쓰지도 넘겨받지도 않는다. 가져간 쪽이 폰이나 태블릿이면 지금의 잠금 화면(이 화면에서 이어서 하기)을 그대로 쓴다.

**D. 정리됨.** 칸이 사라졌을 때(PC 확정, 만료, 다른 곳에서 버림). 상태 카드 "이 상품은 PC에서 마무리됐거나 정리됐어요"와 [다음 상품 올리기](확인 없이 빈 A).

**D1 창 "저장된 상품이 있어요".** 폰 진입 때 보이는 원격 칸이 하나 있고 사진 올리는 중이 아니면 고르기 창 대신 바로 띄운다. B와 C의 "다음 상품 올리기"에서도 띄운다.
- 상품 줄: 썸네일 56px(없으면 생략), 이름(없으면 "이름 없는 상품"), "사진 N장 · 3분 전 저장".
- 상태 줄: 폰이 쓴 칸 "PC에서 아직 열지 않았어요." PC가 쓴 칸 "PC에서 만드는 중이에요. 버리면 PC 화면의 작업도 사라져요."
- 보조 줄: "한 번에 한 상품만 저장할 수 있어요."
- 버튼(알약 한 쌍): [그대로 두기] 기본, [버리고 새로 올리기] 위험.
- 그대로 두기: 진입 때는 폰이 쓴 칸이면 열어서 B, PC가 쓴 칸이면 넘겨받지 않고 C. B와 C에서 띄운 창이면 닫기만 한다.
- 버리고 새로 올리기: 칸을 다시 읽어 창을 띄운 뒤 바뀌었으면 새 내용으로 창을 다시 보여 준다(지금의 확인 재검사 규칙). 같으면 칸을 버리고 빈 A.
- 폰 고르기 창이 여전히 뜨는 경우(이 기기 내용과 원격 칸이 둘 다 있을 때)에도 PC가 쓴 원격 카드의 제목은 "PC에서 만드는 중인 상품"이고, 누르면 넘겨받지 않고 D1 창을 띄운다. 폰의 "지우고 새 상품 업로드" 확인도 D1 창으로 바꾼다.

**저장 완료 창 (D4).** 제목 "사진 N장을 저장했어요" 아래에 계정 알약(로그인 방법 · 이름이나 이메일)과 "PC에서도 이 계정으로 로그인해 주세요."를 둔다. 로그인 방법은 `app_metadata.provider`로 카카오, 구글, 이메일. 카카오는 이름을, 구글과 이메일은 이메일 주소를 보인다. 알 수 없으면 알약 없이 "PC에서도 같은 계정으로 로그인해 주세요."

**E. 만들던 상세페이지 버림 경고 (D2의 이번 PR 몫).** PC에서 콘티나 마네킹 단계까지 간 작업(확정한 흐름)을 두고 다른 것을 시작하려는 순간 확인창을 띄운다. 해당 조작은 진입 창에서 폰 상품 카드를 고를 때, 그리고 이어서/새로 고르기 창(상단 메뉴, 흐름 화면 진입, 입력 화면 진입)의 "새로 시작하기"다. 제목 "만들던 상세페이지는 다시 열 수 없어요", 본문 "{콘티 화면}까지 만든 작업이 사라지고, 이미 쓴 크레딧은 돌아오지 않아요." 버튼 [만들던 것 이어서 하기] 기본, [이 상품으로 시작] 또는 [새로 시작하기] 위험. 입력 단계와 생성 이후 단계(상세페이지 생성이 끝나면 보관함에 남음)에는 띄우지 않는다. 근거: 콘티 화면에 들어가는 순간 마네킹 생성이 자동으로 시작돼 크레딧(기본 45)이 예약되고 성공하면 차감된다(Storyboard.jsx:2396, routes.py:2320-2343). 보관함은 상세페이지 생성 성공 때만 `status=done`이 된다(repo.py:3277-3282).
