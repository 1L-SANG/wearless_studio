# 보관함 "만드는 중" 카드와 단계별 다시 열기 설계 (정본, 2026-10-06)

오너 결정 D2(2026-10-05): 콘티나 마네킹 단계까지 간 작업을 보관함에 "만드는 중"으로 보이고, 누르면 그 단계로 다시 연다. 다른 브라우저와 엉키는 경우 등 생길 일을 먼저 조사해, 꼭 막을 것과 감수할 것을 나눈 뒤 구현한다. 브랜치 `feat/library-in-progress`는 PR #471(폰 사진 업로드, PC 이어 만들기) 위에 쌓고, #471이 머지되면 main 위로 옮긴다.

오너 확정(2026-10-06): 5장의 추천안 그대로 진행한다. "여러 상황을 고려해서 작업해야 한다."

근거: 위험 조사 3갈래(단계 판정과 복원, 여러 브라우저 동시 사용, 크레딧과 정리). 줄 번호는 HEAD 970ab868 기준.

## 1. 지금 구조에서 확인한 사실

- 보관함은 `projects.status = 'done'`만 보여 준다(repo.py:773). `done`은 상세페이지 생성 성공 때 한 곳에서만 쓴다(repo.py:3277-3282). `generating` 값은 쓰는 코드가 없어 보관함의 "생성 중" 표시(Library.jsx:36-38)는 실행되지 않는다.
- 서버에는 "확정" 컬럼이 없다. 확정 표식은 브라우저 sessionStorage와 `wl_flow` localStorage에만 있다(flowSession.js:34-46, useAppStore.js:39-75). 그래서 다른 브라우저에서 열면 확정 봉인이 풀린 상태로 시작한다.
- 콘티에 들어가면 바로 마네킹 생성이 걸리고 크레딧(기본 45)이 예약된다(Storyboard.jsx:2394-2396, routes.py:2320-2343). 컷이 이미 있으면 차감 없이 돌려주고, 진행 중 잡이 있으면 합류한다. 같은 프로젝트에서 동시에 두 번 예약되지 않는다(부분 유니크 인덱스, init.sql:200-201).
- 다른 프로젝트를 여는 `adoptProject`는 서버 값을 읽지 않고 초기값으로 덮는다(useAppStore.js:355-388). 선택 마네킹은 null, 사진 양은 기본, 카피 여부는 true, 확정은 false가 된다.
- 품질 실패 뒤 자동 재생성을 막는 표식, 첫 생성 멱등키, 생성 대기 표식은 그 브라우저 저장소에만 있다(initialGenerationAttempts.js:33-58, detailPageJobPersistence.js:1).
- 프로젝트별로 진행 중 잡을 찾는 API가 없다(GET /jobs/{id}만 있음, routes.py:3581).
- 콘티 저장(PUT storyboard)은 리비전 검사 없이 나중에 저장한 쪽이 이긴다(repo.py:3161-3170). 에디터 저장은 리비전 검사가 있다(repo.py:3199-3214). analysis 저장은 전문 교체다(repo.py:972).
- 프로젝트 삭제 API가 없다. 잡이 도는 중에 지우면 예약 크레딧이 묶이거나 숨긴 뒤에 차감된다(repo.py:2473-2492, 3278-3290).
- 상품 사진과 마네킹 컷을 지우는 정리 작업은 없다. 24시간 TTL은 실패 보관본과 컷 체크포인트뿐이다(재시도 실비만 늘어남).

## 2. 목록에 넣을 조건과 단계 판정

- 조건: `status <> 'done'`, `deleted_at is null`, 기준 색상 정면 사진이 있음, 그리고 다음 중 하나: 콘티가 비어 있지 않음, mannequin 잡이 있음, mannequin_cuts가 있음, detail_page 잡이 있음. 빈 초안, 분석만 한 초안, 업로드가 끝나지 않은 행이 저절로 빠진다. 새 마이그레이션은 필요 없다(기존 인덱스로 충분).
- API: 지금 안 쓰는 `view` 파라미터로 `GET /v1/projects?view=in_progress`를 따로 받는다(routes.py:901-912, httpAdapter.js:791). 새 응답 모델과 별도 Query 키. 기준 색상은 `isBase`, 없으면 첫 색상이고, 비삭제 자산이 실제로 있는지까지 본다. 최신 잡 정렬은 인덱스가 없어 페이지 제한과 lateral 조회로 하고, 비용은 구현 때 EXPLAIN으로 확인한다. 크레딧 내역 제목 매핑 등 기존 사용처는 그대로 둔다.
- 행마다 내려줄 것: id, 제목(없으면 "새 상품"), 커버(기존 커버 조인 재사용, 컷이 없으면 정면 상품 사진), 갱신 시각, 재개 단계, 최신 mannequin 잡과 최신 detail_page 잡의 id, status, errorCode.
- 재개 단계:
  - detail_page 잡이 진행 중: 생성 중(에디터 대기 화면으로 합류)
  - detail_page 잡이 실패: 생성 실패(자동 재생성 없음, 버튼으로만)
  - 유효한 selected_mannequin_id가 있음: 마네킹 단계
  - 나머지(컷만 있고 선택이 없는 경우 포함, 콘티에서 배경 생성으로 컷이 생기기 때문): 콘티 단계
  - `/create/generating`은 재개 목적지로 쓰지 않는다(done이 아니면 무조건 새 생성을 POST한다, Generating.jsx:27).

## 5. 오너 결정 (2026-10-06 확정, 추천안대로)

- **Q1. 콘티 동시 편집 보호(M6): 넣는다.** 기존 `editor_revision`을 같이 써서 마이그레이션 없이 막는다. 에디터 저장이나 생성 완료 직후 콘티 저장이 한 번 충돌로 튕길 수 있으나, 작업본을 보관하고 최신본을 다시 불러오므로 잃는 건 없다.
- **Q2. "만드는 중" 카드 지우기: 이번에는 넣지 않는다.** 나중에 넣으면 소프트 삭제만 쓰고 잡이 도는 중에는 막는다.
- **Q3. 보관함 배치: "만드는 중" 줄을 위에 따로 둔다.** 카드에 단계 칩(콘티 단계, 마네킹 단계, 생성 중, 생성 실패)을 붙이고, 완성본 목록은 그대로 둔다.

## 7. 화면

- 보관함 맨 위 "만드는 중" 줄: 최근 활동 순(프로젝트 갱신 시각과 최신 잡 시각 중 늦은 것) 최대 20개. 카드는 완성본과 같은 틀에 커버, 제목(없으면 "새 상품"), 단계 칩, 시각. 만드는 중이 없으면 줄 자체를 숨긴다.
- PC에서 카드를 누르면 6장의 복원(M1, M2, M3, M5) 뒤 그 단계 화면으로 바로 간다. "이어서 할까요" 창은 뜨지 않는다.
- 폰과 태블릿에서는 줄을 보여 주되 누르면 "PC에서 열어 주세요" 안내(M8).
- 생성 실패 카드는 에디터의 기존 실패 띠와 "다시 만들기" 버튼으로 열린다. 클릭 전에는 예약이 없다(M4).

## 8. 구현 단위와 검증

Codex 모델은 gpt-6.1-sol, 모든 단위 effort xhigh(크레딧, 동시성, 저장 계약).

1. **U1 서버.** `GET /v1/projects?view=in_progress`(2장 조건, 단계, 최신 잡), 프로젝트 응답에 최신 mannequin·detail_page 잡 요약(M5가 모든 에디터 진입에서 씀), 콘티 저장 리비전 검사(M6, editor_revision 공유, 409에 최신본과 리비전), analysis 최상위 키 부분 병합(M7, 서버 내부 저장 호출 전부 점검), 마네킹 생성·재생성의 견적 검증(M9, 409 quote_changed와 새 견적). 마이그레이션 없음. pytest 전부 통과.
2. **U2 화면 핵심.** 보관함 만드는 중 줄과 카드(7장, M8, M14), 다시 열기 복원(M1, M2, M3 종결 상태 심기, M5 잡 합류), M3 자동 요청 규칙(공유 러너와 initialGenerationAttempts), M5 에디터 진입 서버 잡 확인, M10 탭별 프로젝트 id, M12, M13.
3. **U3 화면 동시성.** M6 콘티 409 처리(작업본 보관, 최신본 다시 불러오기, 안내), M7 어댑터는 바뀐 키만, M9 견적 바뀜 처리(새 견적 보여 주고 다시 확인), M11 에디터 충돌 작업본 보존.
4. **검증.** 단위마다 Claude가 diff 리뷰, `pnpm test:frontend`, `pnpm build`, `cd server && .venv/bin/pytest -q`를 직접 돌린다. 마지막에 오너 시점 QA: 폰 폭과 태블릿과 PC 스크린샷 비평, 줄바꿈 검사, 4장의 상황(두 브라우저, 두 탭, 계정 전환, 실패 잡, 품질 실패, 생성 중, 크레딧 견적 변경)을 시나리오로 직접 돌린다. 서버 변경이 실서버에 없으므로 실서버 E2E는 서버 실행 방법을 정한 뒤에 한다(운영 DB에 쓰는 실행은 오너 승인 필요).

## 9. 배포 순서와 호환 (U1 리뷰 반영)

서버는 머지 뒤 CI로 약 10분, 화면은 Vercel로 약 2분 걸리고, 열려 있는 탭은 몇 시간씩 옛 코드로 돈다. 그래서 이 기능은 PR 두 개로 나눈다.

1. **서버 PR을 먼저 머지하고 배포한다.** 지금 화면과 그대로 맞물려야 한다. 콘티 조회는 기본 응답(블록 배열)을 바꾸지 않고 `withRevision=1`일 때만 `{blocks, revision}`을 준다. analysis 저장은 기본이 지금과 같은 전문 교체이고 `merge=1`일 때만 최상위 키 병합(키를 null로 보내면 삭제)이다. 콘티 `baseRevision`, 마네킹 `expectedQuote`는 보낼 때만 검사한다.
2. **화면 PR은 서버 배포가 끝난 뒤 머지한다.** 새 화면은 위 플래그를 항상 보낸다. 서버가 먼저 나가 있으므로 새 화면이 옛 서버를 만나는 순간이 없다.
