# FaceMarket 외부 계약·생체정보 법무 선행 게이트

- 조사 기준일: 2026-08-20 (Asia/Seoul)
- 범위: RAON/OmniOne CX(OACX)의 정부 신분증 사진·셀피·liveness·1:1 얼굴 대조 제공 범위와, 이를 FaceMarket 가입에 사용할 때의 한국 개인정보 보호법상 선행 조건
- 결론: **현재 상태는 파기·동결 및 운영용 재등록 구현에 대해 No-Go**다. 정부 모바일 신분증 생태계가 `신분증사진`을 선택 제공할 수 있다는 점은 확인되지만, 해커톤용 OACX 계약/응답이 그 사진 바이트를 실제로 제공한다는 필드 수준 보장과 신규 셀피·liveness·1:1 대조 제공 여부는 확인되지 않았다. 법무·동의·보존 설계도 아직 확정되지 않았다.
- 한계: 이 문서는 기술·규제 사전검토이며 법률 의견서가 아니다. 실제 운영 전 개인정보 전문 변호사 또는 개인정보 보호책임자 검토가 필요하다.

## 1. 외부 계약 조사 결과

### 1.1 로컬 제공 자료에서 확인된 것

검토한 로컬 파일:

- `/Users/nojeong-un/Downloads/hackerton/index.html`
- `/Users/nojeong-un/Downloads/hackerton/index_auth.html`

두 샘플에서 확인되는 계약은 매우 좁다.

- `index.html`은 `signType: "ENT_MID"`로 OACX 인증창을 열고 성공 콜백의 `res.token`만 읽은 뒤 `GET /oacx/api/v1.0/trans/{token}`을 호출한다.
- `index_auth.html`도 같은 형태이며 `signType: "ENT_SIMPLE_AUTH"`다.
- 샘플은 `compareCI: false`, `isBirth: true`를 지정하지만, `/trans` 성공 응답의 JSON 스키마를 정의하거나 검증하지 않는다.
- 두 파일 어디에도 정부 신분증 사진의 필드명·인코딩·크기, 신규 셀피 촬영, liveness 판정, 1:1 얼굴 대조 호출 또는 점수/판정 규격이 없다.

제공됐다고 언급된 `모바일신분증API 샘플.zip`과 `OmniOne CX_VC-Verifier_v1.0API 매뉴얼해커톤_20250709` 원문은 위 폴더에서 발견되지 않아 검토하지 못했다. 따라서 응답 스키마를 샘플 HTML이나 기억에 의존해 구현하면 안 된다.

팀이 전달한 RAON 지원 답변 사본은 다음을 말한다.

- 해커톤 테스트 환경은 별도 신청 없이 기간 중 유지된다.
- 토큰 검증 결과로 사용자가 제출한 신분증 데이터, CI, 전화번호가 전달된다.
- 단계별 JWT 유효기간은 5분이다.
- 실제 모바일 신분증이 필요하고, 운영 전환 시 별도 협의가 필요하다.

이 답변은 RAON 담당자의 1차 답변이라는 가치는 있지만, `신분증사진` 포함 여부·바이트 형식·필드명·선택제출 설정·liveness·얼굴 대조를 명시하지 않는다. 또한 계약서나 버전 고정 API 명세가 아니므로 운영 보장으로 취급할 수 없다.

[행정안전부 모바일 신분증 — 신원확인자](https://www.mobileid.go.kr/mip/hps/svcIntrcn/svcIntrcnIdnty.do)

## 2. 한국 개인정보 보호법/PIPC 선행 조건

### 2.1 정보 분류 — “얼굴 파일 전부가 자동으로 민감정보”라고 단정하지 않는다

현행 개인정보 보호법 시행령 제18조는 개인을 알아볼 목적으로 신체적·생리적·행동적 특징에서 기술적으로 **생성한 정보**를 민감정보 범위에 둔다. FaceMarket의 얼굴 embedding/template처럼 얼굴 특징을 추출해 신분증 사진과 본인 여부를 대조하는 정보는 이 정의에 직접 해당한다. [개인정보 보호법 시행령 제18조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0018&lsiSeq=286175&urlMode=lsScJoRltInfoR)

PIPC의 2021년 생체정보 보호 가이드라인은 얼굴 사진·영상을 인증/식별에 넣는 경우 이를 `생체인식 원본정보`, 그로부터 생성한 특징정보를 `생체인식 특징정보(민감정보)`로 구분했다. 현재 PIPC 사이트에서 이 문서는 **과거 안내서**로 분류되므로 현행 구속적 규범처럼 인용하면 안 되지만, 원본·특징정보의 위험과 수명주기 설계에는 유용하다. [PIPC 생체정보 보호 가이드라인 게시 페이지](https://www.pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS217&mCode=D010030000&nttId=7529)

| 데이터 | 최소 법적 분류/취급 | FaceMarket 결론 |
| --- | --- | --- |
| 정부 신분증 얼굴 사진, 셀피, liveness 영상 | 식별 가능한 개인정보. 1:1 인증을 위해 입력되면 생체인식 원본정보로 고위험 처리 | 별도 생체 처리 고지에 포함하고 판정 직후 즉시 파기 |
| 얼굴 embedding/template/특징점 | 시행령 제18조의 민감정보 | 다른 개인정보 동의와 분리된 명시 동의 또는 별도 법적 근거가 필수 |
| match/liveness 원점수, 점수 버킷, pass/fail | 개인과 연결되면 개인정보. 산출 방식과 목적에 따라 생체인식정보로 평가될 수 있음 | 버킷화만으로 익명/비민감이 되지 않음. 필요한 최소 항목과 기간만 보존 |
| CI, 전화번호, 이름, 생년월일 | 개인정보 | 필요한 것만 요청. 성인 여부만 필요하면 전체 생년 대신 성인 claim 선호 |
| 주민등록번호·운전면허번호 | 고유식별정보로 별도 제한 대상 | FaceMarket 목적에 불필요하므로 요청·저장 금지 |

### 2.2 Phase 0에서 확정해야 하는 의무

1. **수집·이용 근거와 최소수집**: 동의를 근거로 할 경우 목적, 항목, 보유기간, 거부권과 불이익을 알려야 하며, 목적에 필요한 최소 정보만 수집했다는 입증책임은 처리자에게 있다(법 제15조·제16조). [개인정보 보호법 제15조~제16조](https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsId=011357&lsJoLnkSeq=900078586&print=print)

2. **민감정보 별도 동의**: 얼굴 특징정보를 처리하려면 법령상 별도 근거가 없는 FaceMarket은 다른 개인정보 처리 동의와 구분된 동의를 받아야 한다(법 제23조). 동의 화면은 원본 사진/셀피·liveness/특징정보, 1:1 대조 목적, 제공자, 즉시 파기와 예외 보존기간, 거부 시 FaceMarket 실물모델 등록 불가를 명확히 표시해야 한다. [개인정보 보호법 제22조·제23조](https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsId=011357&lsJoLnkSeq=900078586&print=print)

3. **목적 제한과 원본 즉시 파기**: 처리 목적을 달성해 정보가 불필요해지면 지체 없이 복구·재생 불가능하게 파기해야 한다(법 제21조). 이 흐름에서는 정부 사진·셀피·liveness 프레임의 목적이 match/liveness 판정 완료로 달성되므로, 별도 보존 필요성과 법적 근거를 승인받지 않은 한 **판정 직후 원본을 앱, 임시파일, 객체저장소, 큐 payload, 로그, 백업 및 공급자 측에서 삭제**하는 것을 hard requirement로 둔다. 2021 PIPC 가이드도 특징정보 생성 시 원본의 지체 없는 파기를 원칙으로 설명했다. [개인정보 보호법 제21조](https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsId=011357&lsJoLnkSeq=900078586&print=print)

4. **보존 결과도 최소화**: `provider`, 거래/evidence 식별자, 검증시각, 판정, 정책/임계값 버전 정도로 시작한다. 원점수나 점수 버킷은 분쟁·재현에 반드시 필요하다는 근거와 보존기간이 승인될 때만 추가한다. Face embedding/template, 정부 사진, 셀피, 영상, OACX live token은 보존하지 않는다. 파기 이벤트에는 원본 자체가 아니라 대상 유형·처리 단계·시각·결과만 기록한다.

5. **암호화와 접근통제**: 저장 또는 네트워크 송수신되는 생체인식정보와 이용자 생체인식정보 저장본에는 안전한 암호화가 요구된다. 즉시 파기 설계라도 처리 중 TLS, 임시 저장 암호화, 최소권한, 비밀값 로그 금지와 감사기록은 필요하다. [개인정보의 안전성 확보조치 기준 제7조](https://www.law.go.kr/LSW/admRulSideInfoP.do?admRulSeq=2100000281400&chrClsCd=010201&dashNo=&docCls=jo&joBrNo=00&joNo=0007&urlMode=admRulScJoRltInfoR)

6. **처리위탁/제3자 제공 구분**: liveness·matcher가 FaceMarket의 지시만 받아 처리하면 법 제26조상 위탁 문서에 목적 외 처리 금지와 보호조치를 넣고, 수탁자/재수탁자를 공개하며, 교육·점검·감독해야 한다. 제공자가 자체 학습·상품개선 등 독립 목적으로 쓰면 단순 수탁자가 아닐 수 있으므로 제3자 제공의 별도 법적 근거를 검토해야 한다. 계약은 학습·2차 이용을 기본 금지해야 한다. [개인정보 보호법 제26조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1029331867)

7. **국외 이전**: 해외 API/리전에서 사진·영상·특징정보를 조회, 처리 또는 보관하면 법 제28조의8의 국외 이전에 해당할 수 있다. 이전 국가, 수령자, 목적, 항목, 시점/방법, 보유기간, 거부방법과 법적 근거를 vendor 선정 전에 확정해야 한다. 국내 리전이라는 마케팅 문구만으로 하위처리자·원격접속까지 국내라고 가정하지 않는다. [개인정보 보호법 제28조의8](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334953)

### 2.3 DPIA는 FaceMarket 민간 서비스에 자동 의무가 아니다

개인정보 보호법 제33조의 의무적 개인정보 영향평가는 `공공기관의 장`을 주체로 하고, 시행령 제35조는 예를 들어 5만 명 이상의 민감정보/고유식별정보를 처리하는 공공기관 개인정보파일 등의 기준을 둔다. FaceMarket이 민간 법인 서비스라는 전제에서는 정부ID 사진과 얼굴 대조를 쓴다는 사실만으로 법 제33조 DPIA가 자동 의무가 된다고 단정할 수 없다. [개인정보 보호법 제33조](https://law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsId=011357&lsJoLnkSeq=900081527&print=print), [개인정보 보호법 시행령 제35조](https://law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1033215557)

다만 PIPC의 2021년 가이드(현재는 과거 안내서)는 민간도 생체인식정보를 서버에서 대량 처리하면 영향평가를 수행하도록 권장했다. 따라서 FaceMarket에는 법 제33조의 의무 DPIA라고 표기하지 말고, **출시 전 내부 생체정보 영향·위험평가와 법무 승인**을 제품 게이트로 두는 것이 정확하다. 공공기관 공동사업으로 전환하거나 처리 규모/구조가 바뀌면 의무 대상 여부를 다시 판정한다.

## 3. Go/No-Go 체크리스트

다음 항목이 모두 `Yes`가 되기 전에는 기존 모델 파기, 전체 모델 동결, 운영 재등록 cutover를 실행하지 않는다.

- [ ] RAON이 대상 신분증별 `신분증사진` 제공 가능 여부와 `/trans` 필드 계약을 서면 확정했다.
- [ ] 해커톤 환경뿐 아니라 운영 환경의 MID/service code, 이용 승인, 비용, SLA와 rate limit이 확정됐다.
- [ ] 등록 시점 fresh 셀피 캡처와 liveness 제공자를 확정했고 nonce/session 결합 및 replay 방지 방식이 문서화됐다.
- [ ] 정부 사진↔셀피 1:1 matcher, 정책 임계값, FAR/FRR, 오류·재시도·수동 검토 흐름이 승인됐다.
- [ ] 각 제공자의 리전, 수탁/재수탁자, 보존·삭제, 학습 금지, 사고통지, 파기 증빙을 DPA/계약에 반영했다.
- [ ] 일반 개인정보 동의와 구분된 생체/민감정보 동의, 처리방침, 보존표, 거부·철회·삭제 절차를 법무/CPO가 승인했다.
- [ ] OACX token, 정부 사진, 셀피, liveness 프레임, 얼굴 특징정보가 판정 후 자사와 공급자에서 삭제됨을 sandbox E2E 테스트와 로그로 입증했다.
- [ ] 보존 DB에는 승인된 최소 evidence만 남고, 원점수/버킷도 승인된 필요성·기간 없이는 저장하지 않는다.
- [ ] 실패·거부·접근성 이슈의 재시도/수동검토 경로와 기존 모델 재등록 UI가 배포 준비 상태다.
- [ ] 그 뒤에만 freeze를 실행하고, 실제 purge는 dry-run 대상 수·영향 확인, 비즈니스/데이터 소유자 서면 승인, cutover·복구 절차를 별도로 통과한다.

## 4. 지금 가능한 안전한 다음 단계

1. 누락된 RAON API 매뉴얼/샘플 ZIP을 확보하고 위 1.4 질문을 포함한 1~2일짜리 contract spike를 먼저 수행한다.
2. 실제 개인정보 없이 schema fixture와 삭제 증빙 요구사항만 작성한다. vendor 응답 전 추측 기반 adapter나 얼굴 matcher 추상화는 만들지 않는다.
3. 법무/CPO와 원본 즉시 파기, 최소 evidence, 위탁/국외 이전 구조를 확정한다.
4. sandbox에서 `정부 사진 claim 수신 → fresh liveness → 1:1 match → 원본/특징정보 삭제`가 한 거래에 결합되는 것을 입증한 뒤 enrollment readiness를 선언한다.
5. enrollment readiness 이후에만 freeze, dry-run 승인 이후에만 purge한다.

현재 stop condition은 명확하다. **RAON 사진 claim 계약, liveness/matcher 계약, 법무 승인, 삭제 증빙이 없으므로 파기·동결 구현은 시작하지 않는다.**
