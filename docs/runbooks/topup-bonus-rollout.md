# 충전 보너스 배포와 활성화

기본 운영 상태는 `TOPUP_BONUS_ENABLED=false`, `SIGNUP_CREDITS=0`이다. 이 변경 자체는 운영 manifest에서 보너스를 켜지 않는다. 보너스 활성화는 아래 확인을 마친 뒤 별도의 운영 승인으로 진행한다.

## 1. 보너스를 끈 채 호환 버전 배포

1. `20261006120000_free_credits_and_topup_bonus.sql` 마이그레이션의 dry-run을 검토한 뒤 승인된 절차로 적용한다. 커밋된 마이그레이션은 수정하거나 되돌려 삭제하지 않는다.
2. 실제 DB에서 두 주문 테이블의 `bonus_credits`, `bonus_percent`, `plan_at_order` 컬럼과 제약을 확인한다. 과거 주문의 보너스량과 비율이 0인지도 확인한다. 무료 버킷을 허용하는 `credit_sources` 제약은 `pg_get_constraintdef`로 확인한다. 마이그레이션 이력만으로 적용 완료를 판단하지 않는다.
3. `TOPUP_BONUS_ENABLED`를 미설정하거나 false로 두고 보너스 스냅샷을 읽는 서버 버전을 전체 배포한다. API의 계좌이체 확인, 토스 승인, 관리자 수동 지급과 크레딧을 소비하거나 환불하는 모든 프로세스가 같은 계약을 읽어야 한다. 관련 워커와 별도 실행 태스크도 포함한다. 가입 지급은 계속 0으로 둔다.
4. 인증된 `GET /v1/me/account`에서 `topupBonusEnabled: false`를 확인한다. Seller와 Pro의 새 계좌이체 신청, 토스 주문, 관리자 수동 충전이 기본량만 저장하거나 지급하는지 검증 환경에서 확인한다. 프론트는 필드가 없는 구버전 API 응답도 false로 처리하므로 보너스 문구가 보이지 않아야 한다.

## 2. 모든 구버전 태스크 종료 확인

활성화 전에 운영자가 다음 증거를 기록한다. 서비스의 배포 완료 표시나 한 번의 API 응답만으로는 충분하지 않다.

- 대상 ECS 서비스마다 모든 실행 중 태스크의 task definition revision과 컨테이너 image digest를 배포한 호환 버전과 대조한다. 여러 API 서비스, 별도 클러스터, 다른 환경이 같은 DB에 연결된다면 전부 확인한다.
- 구버전 deployment의 running count와 pending count가 모두 0이며, 구버전 태스크와 로드밸런서의 draining 대상이 남아 있지 않은지 확인한다. 진행 중 요청도 끝나야 한다.
- 서비스 밖에서 실행한 태스크와 수동 지급 스크립트가 구버전 주문 확인 코드를 실행하지 않는지 확인한다. 구버전 이미지를 다시 띄우는 예약 작업이나 자동 복구 설정도 확인한다.
- 자동 롤백의 대상과 운영 롤백용 이미지가 보너스 스냅샷을 읽는 호환 버전인지 확인한다. 보너스 주문이 하나라도 생긴 뒤에는 스냅샷을 무시하는 과거 이미지로 되돌릴 수 없다.

하나라도 확인되지 않으면 false를 유지한다. 이 단계까지는 보너스를 끈 상태로 운영해도 기존 결제와 충전이 계속 동작한다.

## 3. 나중에 설정만으로 활성화

1. 모든 구버전 태스크 종료와 호환 롤백 이미지가 확인된 뒤, 운영자가 API 설정에 `TOPUP_BONUS_ENABLED=true`를 추가한다. Copilot을 쓰는 환경에서는 `copilot/api/manifest.yml`의 `variables`에 이 값을 추가하는 별도 설정 변경으로 배포한다. 여러 주문 생성 서비스가 있다면 모두 같은 설정을 적용한다. 제품 코드와 DB 마이그레이션을 다시 바꿀 필요는 없다.
2. Settings는 프로세스 시작 때 읽으므로 환경변수 변경을 적용한 새 태스크로 교체한다. 새 배포 도중 남아 있는 false 태스크도 호환 버전이어야 한다. 이 태스크는 true 태스크가 저장한 보너스 주문을 전액 확인할 수 있다.
3. 모든 주문 생성 태스크에 true가 적용된 것을 확인하고, 계정 응답의 `topupBonusEnabled: true`를 확인한다. 프론트의 계정 정보가 갱신되면 Seller와 Pro의 충전 보너스 문구가 표시된다.
4. 검증 환경에서 Seller의 100cr 주문이 기본 100cr와 보너스 5cr, Pro의 500cr 주문이 기본 500cr와 보너스 50cr를 저장하는지 확인한다. 확인 시 합계가 한 버킷과 원장에 한 번만 지급되는지도 확인한다. 운영 결제를 검증에 쓸 때에는 기존 운영 승인 절차를 따른다.

## 4. 중단과 롤백

새 보너스 지급을 중단하려면 `TOPUP_BONUS_ENABLED=false`로 설정을 배포한다. 모든 주문 생성 태스크가 false가 되면 새 주문의 보너스는 0이고 새 계정 응답의 문구도 꺼진다. 이미 받은 주문의 `bonus_credits`와 `bonus_percent`는 수정하지 않는다. 결제 확인과 관리자 지급 재시도는 저장된 보너스를 그대로 지급해야 한다.

보너스 주문을 만든 뒤에는 false 설정만으로 구버전 이미지가 안전해지지 않는다. 주문의 결제 완료, 환불, 재시도까지 보너스 계약을 이해하는 버전을 유지하며, 코드 롤백도 호환 버전으로만 한다.
