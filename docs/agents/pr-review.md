# GitHub PR 전문 리뷰

기본 대상은 `1L-SANG/wearless_studio`다. 사용자가 PR 링크나 번호를 주면 GitHub의 해당 변경을 검토한다. 저장소 규칙은 루트 `CLAUDE.md`가 정본이다. 이 문서는 리뷰 절차를 구체화하며 제품 요구사항을 새로 정하지 않는다.

## 역할과 범위

- 구현의 논리적 결함, 실제 사용자 경로의 오류, 운영 버전과의 호환성, 배포 순서와 데이터 계약을 우선 검토한다. 보안, 결제와 크레딧, AI 실행 비용, 성능과 복구 가능성도 변경 범위에 맞춰 확인한다.
- 기본 결과는 이 대화의 리뷰 보고서다. GitHub 댓글이나 승인 또는 변경 요청 게시, 코드 수정, 커밋과 푸시, 머지, 배포, 운영 DB 변경은 해당 행동을 사용자가 요청했을 때만 진행한다.
- 작업 결과 표시용 Codex 패널이나 탭은 자동으로 열지 않는다. 결과는 대화에서 설명하고 필요한 링크만 제공한다. 사용자가 명시적으로 탭을 요청한 경우에만 연다.
- 기존 CI와 자동배포의 결과를 활용한다. 별도 자동화, 반복 감시, 새 워크플로를 만들거나 기존 배포를 리뷰 목적으로 실행하지 않는다.
- 재현이 필요하면 운영 자격증명을 사용하지 않는 격리된 로컬 테스트 환경을 쓴다. 운영에서 AI 생성, 결제, 데이터 저장, 업로드, 워커 기동을 실행해 확인하지 않는다.
- 설정은 필요한 키명과 존재 여부만 추출한다. 설정 파일 전체, 토큰, 비밀 환경변수, 서명 URL, 개인정보를 출력하지 않는다. 운영 설정 조회도 응답에서 필요한 비밀이 아닌 필드만 선택한다.

## 1. 검토 대상을 고정한다

1. GitHub에서 PR 설명, 전체 변경 파일과 diff, head SHA, base 브랜치와 SHA, 머지 가능 상태, 기존 리뷰 의견을 읽는다. 큰 diff와 파일 목록은 잘림과 페이지 누락 여부를 확인한다.
2. PR 변경은 merge-base와 head 사이에서 확인한다. 최신 대상 브랜치에 추가된 변경과 예상 머지 결과도 구분해서 확인한다. Git 충돌이 없다는 사실은 실행 호환성을 증명하지 않는다.
3. 미커밋 변경이 있는 작업 폴더를 체크아웃하거나 초기화하지 않는다. 코드 실행이 필요하면 적절한 기존 worktree 또는 격리된 PR 스냅샷을 사용한다. 테스트와 코드 근거가 어느 SHA의 결과인지 기록한다.
4. 요구사항은 PR과 관련된 현행 `documents/PRD.md`, `documents/common_data_contract.md`, `CONTEXT.md`, ADR에서 읽는다. 로컬의 미커밋 문서 변경과 PR에 포함된 계약을 섞지 않는다. 별도로 전달된 오너 결정은 출처를 밝히고 적용한다.
5. 보고 직전에 PR head와 base의 변경 여부를 확인한다. 바뀌었다면 영향을 받는 근거를 갱신하고, 이전 SHA의 결과를 최신 결과처럼 보고하지 않는다.

## 2. 기존 자동검사의 결과를 먼저 읽는다

아래 범위는 2026-10-11 GitHub main `4b5249b722cdf8209d6574dd7e495f3e170df01d`에서 확인했다. 영구한 배포 상태로 간주하지 않는다. 실제 리뷰에서는 해당 PR과 현재 대상 브랜치의 워크플로, 경로 필터, 외부 배포 연동을 다시 읽는다.

| 기존 담당 | 이미 수행하는 범위 | 리뷰가 추가로 판단할 부분 |
| --- | --- | --- |
| `.github/workflows/frontend-ci.yml` | 프론트 테스트를 3개 샤드로 실행하고 빌드한다. 서버 조립기와의 계약 대조용 Python 환경도 준비한다. | 테스트가 다루지 않는 사용자 경로, 상태 전이, 저장 계약과 오류 복구 |
| `deploy-server.yml`의 `test`, `test-db` | 서버 단위 테스트와 로컬 Supabase DB를 사용하는 지정 통합 테스트를 실행한다. PR에서는 배포하지 않는다. | 테스트의 가정이 운영 데이터와 맞는지, 권한과 과금 경계, 변경이 실제로 도달 가능한지 |
| `deploy-server.yml`의 운영 배포 | 테스트 후 변경 필터에 따라 DB dry-run과 적용, 파드 코드 묶음, 상세 워커와 API 배포, 준비 상태와 브라우저 API 및 R2 CORS 검사를 수행한다. | 독립 배포 사이의 호환성, 대기 중인 기존 작업, 롤백, 경고만 남기고 넘어간 단계의 영향 |
| `.github/workflows/deploy-sam2.yml` | 해당 경로 변경 시 SAM2 서비스와 API 경계 테스트를 실행하고, main의 런타임 변경에 맞춰 별도로 배포한다. | API와 SAM2 중 어느 쪽이 먼저 배포돼도 내부 HTTP 계약이 유지되는지 |
| 기존 Vercel Git 연동 | 프론트 배포와 프리뷰 결과는 기존 연동에서 조회한다. 실제 배포 SHA와 도메인 연결은 결과에서 확인한다. | 새 UI와 운영 API의 조합, 빌드 시점 환경변수, 오래 열린 브라우저의 호환성 |
| `.github/workflows/vercel-deploy.yml` | 확인한 main에서는 `workflow_dispatch`만 있는 수동 비상 배포다. Sensitive 환경변수의 자리표시 값을 검사하고 빌드와 배포를 수행한다. | Git 자동배포와 비상 배포를 혼동하지 않는지, 실제 도메인이 어느 산출물을 제공하는지 |

얼굴 렌더와 Comfy 각도 교체 등 별도 이미지 빌드 워크플로는 해당 변경이 있을 때 그 결과만 추가로 읽는다.

- CI의 실행 URL, 검사 SHA와 대상 head 및 base의 대응, 작업 상태, 생략된 단계와 경고를 기록한다. GitHub 합성 머지 SHA의 검사는 해당 head와 base 조합을 검사한 결과인지 확인한다.
- 성공, 실패, 대기, 취소, 생략, 검사 미대상을 구분한다. 오래된 성공이나 다른 브랜치의 성공을 재사용하지 않는다. 전체 작업이 초록색이어도 `continue-on-error` 단계의 실패는 해당 기능에 영향을 줄 수 있다.
- 동일 변경에 대한 성공한 빌드와 전체 테스트는 반복 실행하지 않는다. 기존 로그와 테스트 내용을 읽어 검증 범위를 판단한다. 실행 중인 CI는 결과를 기다리며 독립적인 코드 리뷰를 진행한다.
- 추가 실행은 기존 CI가 누락한 재현 시나리오, 실패의 원인 분리, 현재 변경을 검사한 결과가 없는 경우에 한한다. 무엇이 미검증인지와 실행 범위를 먼저 밝히고 필요한 검사만 한다. 테스트 실패가 기존 문제인지 PR에서 생긴 문제인지 구분한다.
- 명령은 해당 SHA의 `package.json`, 서버 설정, CI에서 확인한다. 현재 프론트에는 `test:frontend`와 `test:frontend:files`, `build`가 있다. 전체 검사 명령을 기본 리뷰 단계로 다시 실행하도록 등록하지 않는다.

| 논리와 상태 | 로딩과 실패 상태, 새로고침과 재진입, 중복 클릭, 저장과 복원, 비동기 응답 순서, 동시 실행과 재시도의 실제 처리 |
| 데이터 계약 | 프론트 서비스와 HTTP 및 목 어댑터, 서버 직렬화, nullable 필드와 enum, 콘티보드 blocks 저장 계약, 작업 생산자와 소비자의 payload 일치 |

| 성능과 복구 | 사용자나 데이터 증가에 따른 병목, DB 쿼리, 블로킹 작업, 파일 크기와 브라우저 메모리, 부분 실패, 작업 중단과 복구, 관측 가능한 오류 |

콘티보드와 생성예시 변경은 관련 ADR을 함께 읽고, 이미지 소유 경계를 지킨다. 리뷰 과정에서 이미지 생성, 교체, 업로드를 하지 않는다.

도달 불가능한 가정을 제품 결함으로 보고하지 않는다. 순수 함수 경계에서만 참인 개선을 남길 필요가 있으면 `UI 비도달`과 실제 영향을 명시하고 선택적 보완으로 다룬다. 원래 존재하던 문제를 PR이 새로 만든 결함으로 보고하지 않는다.

## 4. 실서버와 배포 호환성을 판단한다

운영 상태는 main의 최신 커밋과 같다고 가정하지 않는다. 관련 구성요소의 배포 식별자, 관측 시각, 근거를 따로 기록한다. 기존 배포 로그가 해당 상태를 충분히 입증하면 다시 같은 검사를 실행하지 않는다.

| 구성요소 | 필요한 운영 근거 |
| --- | --- |
| 프론트 | 실제 도메인에 연결된 Vercel 배포 식별자와 커밋, API 모드와 주소 등 관련 빌드 설정 |
| API와 상세 워커 | ECS 태스크 정의와 이미지 태그 및 digest, 배포 완료 여부, 관련 플래그와 작업 처리 역할. 비밀 환경변수는 조회하거나 출력하지 않는다. |
| Supabase DB | 관련 마이그레이션 이력과 실제 테이블, 제약, 인덱스, RLS와 트리거 정의. 이력의 최신 상태만으로 물리 스키마 일치를 판단하지 않는다. |
| SAM2와 파드 코드 | 해당 서비스 버전과 내부 HTTP 계약, 서버가 지목하는 코드 묶음과 기존 업로드 검증 결과 |

현재 서버 워크플로는 Copilot 앱 메타데이터 리전 `ap-northeast-2`와 배포 환경 `use1`의 런타임 리전 `us-east-1`을 구분한다. 오래된 `prod` 매니페스트만으로 현재 운영 대상을 고르지 않는다. 리뷰 시 실제 배포 설정과 조회 결과를 우선한다.

변경이 닿는 조합만 평가하고 근거와 제한을 남긴다.

1. 현재 프론트와 새 API가 함께 동작하는지 확인한다. 캐시되거나 오래 열린 브라우저도 기존 클라이언트다.
2. 새 프론트와 현재 API가 함께 동작하는지 확인한다. 프론트와 서버의 독립 배포에서 먼저 나가는 쪽을 가정하지 않는다.
3. 현재 API와 워커가 새 DB에서 동작하는지 확인한다. DB 변경이 먼저 적용되는 동안 구버전 태스크도 남아 있을 수 있다.
4. 새 API와 워커가 기존 큐의 payload, 상태와 체크포인트를 처리하는지 확인한다. 별도 배포되는 서비스 사이의 중간 상태도 확인한다.
5. 코드 롤백 뒤 이미 전진한 DB와 새로 저장된 데이터가 호환되는지 확인한다. 되돌릴 수 없는 변경은 선행 조건과 복구 방법을 명시한다.

운영 조회는 읽기 전용으로 제한한다. DB는 스키마 메타데이터 중심으로, 조회 범위와 시간을 제한한다. 읽기 전용 트랜잭션에서도 부작용이 있는 함수나 운영 RPC는 호출하지 않는다. 운영 마이그레이션 적용과 인프라 변경은 리뷰에서 실행하지 않는다.

`/healthz` 성공은 프로세스 응답을 뜻한다. `/readyz`는 DB 연결 여부를 확인하지만 API 계약, 과금, 워커, 개별 테이블의 정확성을 증명하지 않는다. 기존 검사 결과가 있으면 활용하며, 커밋 증거가 없는 헬스 응답을 배포 버전의 증거로 사용하지 않는다.

## 5. 보고 기준

- **P0:** 즉시 대응이 필요한 광범위한 장애, 데이터 유출이나 금전 피해. 현실의 발생 조건이 확인된 경우에만 사용한다.
- **P1:** 머지 전에 수정해야 하는 주요 사용자 경로 장애, 권한 우회, 데이터 손실, 잘못된 과금, 배포 중 기능 단절.
- **P2:** 실제 사용 조건에서 발생하는 제한적 오류나 회귀. 조건과 영향 범위를 구체적으로 적는다.
- **선택적 보완:** 현재 결함으로 입증되지 않은 유지보수와 UX 개선. 머지 차단 사유와 구분한다.
- **미확인:** 접근 권한, 관측 데이터, 재현 환경이 없어 검증하지 못한 사항. 결함으로 단정하거나 통과 처리하지 않는다.

각 지적은 하나의 원인과 영향에 집중한다. `[P1] 짧은 문제 제목`, 도달 경로와 발생 조건, 기대 결과와 실제 결과, 사용자 또는 운영 영향, 해당 SHA의 파일과 줄, 실행한 재현이나 코드 추적 근거, 최소 수정 방향을 담는다. 추론인 부분은 밝힌다. 동일 원인을 여러 항목으로 부풀리지 않는다.

각 문제마다 비개발자용 쉬운 설명과 추천 해결 방법을 함께 쓴다. 사용자의 조작과 눈에 보이는 결과로 문제를 설명하고, 추천하는 해결 방법이 무엇을 바로잡는지 짧게 풀어 쓴다. 마지막 공통 요약에만 쉬운 설명을 모으지 않는다.

최종 보고는 중요한 결함부터 제시하고 다음 내용을 포함한다.

```text
검토 대상: PR 링크, head SHA, base SHA와 브랜치, 검토 시각
머지 판단: 수정 필요, 조건부 가능, 발견된 차단 사유 없음 중 하나
운영 호환성: 관련 구성요소별 확인, 조건부, 미확인 중 하나

확인된 결함:
- 우선순위, 도달 경로와 조건, 영향, 코드 근거, 수정 방향

선택적 보완:
- 보완 내용, 실익, 우선순위

검증 근거:
- 기존 CI와 배포 결과의 링크, 검사 SHA, 성공·실패·생략 상태와 범위
- 추가 실행이 있었다면 이유, 명령, 결과
- 운영 버전과 스키마 근거, 필요한 배포 순서와 롤백 조건

미확인과 제한:
- 무엇을 확인하지 못했는지, 판단에 미치는 영향, 필요한 접근이나 자료

쉬운 설명:
- 사용자에게 생기는 문제, 먼저 할 수정, 결정할 것과 추천안, 다음 단계
```

문제가 없으면 `검토 범위에서 확인된 결함 없음`이라고 쓰고 실제 근거와 제한을 남긴다. 미확인인 운영 상태를 근거로 전체 배포가 안전하다고 말하지 않는다. 모델과 effort는 저장소 규칙에 따라 확인 가능한 실제 값만 기록하며 설정값을 실사용 값으로 추정하지 않는다.

이 표는 설정 시점의 진단 기록이며 다음 리뷰에서 연결을 보장하지 않는다. 설정은 현재 로컬 프로젝트의 수동 리뷰에 적용한다. `CLAUDE.md`와 `AGENTS.md`는 기존 `.gitignore`에 따라 Git 추적에서 제외되어 있다. GitHub 자동 리뷰나 새 CI를 설치한 설정이 아니다. PR 작성 양식은 `.github/PULL_REQUEST_TEMPLATE.md`에 있으며 기존 CI 결과를 기록하는 용도로 사용한다.
