# 페이지 글 지시문, 모델마다 다르게 한 곳

2026-11-18, 1판(1회차 시험 전). 카피라이팅 총괄이 씀.

모든 모델이 같이 쓰는 것: `rules_v1.md`(규칙 본문), `examples_v1.json`(고치기 전과 후의 짝), 사실 묶음, 계획표, 칸 목록, 응답 스키마. 모델마다 다른 것은 틀(`gpt_v1.md`, `gemini_v1.md`, `claude_v1.md`)과 설정(`settings_v1.json`)뿐이다.

## 규칙 본문을 이렇게 쓴 까닭 (공통)

- 규칙마다 까닭을 붙이고("사진을 볼 수 없다", "페이지에 이미 적혀 있다") 대문자 강조와 MUST를 쓰지 않았다. 요즘 모델은 지시를 그대로 따르므로 세게 쓰면 과하게 반응한다.
- 우선순위를 먼저 적었다(사실, 할 말이 있을 것, 되읽지 않기, 사람처럼, 칸에 맞추기). 규칙끼리 부딪힐 때 무엇이 먼저인지 모델이 알아야 한다.
- 고정 본문에는 한국어 예문 문장을 넣지 않았다. 1단계 시험에서 지시문 예문의 낱말이 출력에 그대로 베껴졌다. 예문은 호출마다 씨앗으로 골라 넣는 짝으로만 준다.
- 예문은 "이렇게 쓰지 않는다, 이렇게 쓴다, 까닭"의 짝이다(오너 지시). 다른 상품의 예문이라는 것과 문구를 다시 쓰지 말라는 말을 틀에 넣었다.

## 모델마다 다른 곳

| 모델 | 틀 | 설정 | 까닭 |
|---|---|---|---|
| gpt-6.1-terra | 규칙은 developer 글에 마크다운 제목으로, 자료는 user 글에. 끝에 돌려주기 전 확인 목록 넷 | reasoning none | GPT-6 계열 공식 가이드: 늘 같은 규칙은 developer, 호출마다 바뀌는 자료는 user, 평이하고 직접적인 말, 단계별로 생각하라는 말은 쓰지 않음. terra 전환 실험에서 none이 약 40% 빠르고 품질 차이가 잡히지 않았다 |
| gpt-6-luna | terra와 같은 틀 | reasoning 기본값 | 가장 싼 모델이라 확인 목록이 더 필요할 수 있다. 1회차에서 본다 |
| gemini-3.8-flash | 규칙은 시스템 지시에, 자료를 XML 태그로 먼저 놓고 물음을 맨 끝 한 문단으로 | thinking low | Gemini 3 계열 공식 가이드: 긴 자료를 앞에, 물음을 끝에 두고 "위 자료를 바탕으로"로 잇기. 간결하고 직접적인 지시. temperature는 건드리지 않음 |
| gemini-3.1-pro-preview | flash와 같은 틀 | thinking low | 지금 운영 공용 글 모델. 대조용 |
| claude-sonnet-5-5 | 규칙은 시스템에, 자료를 XML 태그로 먼저 놓고 물음을 맨 끝에. 끝에 "손님 눈으로 한 번 읽고 되읽기 문장을 지운 뒤 돌려주기" | effort low, 생각은 adaptive | Anthropic 공식 가이드: XML 태그로 자료를 가르고 긴 자료를 위에, 물음을 아래에. 스스로 점검하게 하는 한 줄이 효과가 있다. 이 모델은 생각을 끌 수 없고 깊이는 effort로만 정한다. 짧은 글이라 low에서 시작한다 |
| claude-opus-5-5 | sonnet과 같은 틀 | effort low(기본이 medium이라 명시) | 위와 같음. 기본 effort가 medium이라 비용과 시간을 줄이려고 low로 적었다 |

## 2026-11-18 공식 가이드 확인 뒤 고친 것

조사 기록은 `.scratch/copywriting-20261113/research/model_guides_1118.md`(각 공급자의 공식 문서를 그날 읽은 것).

- gpt: 예문을 user 글에서 developer 글로 옮겼다. OpenAI 가이드는 예문을 developer 메시지에 두라고 한다. 추론 모델은 예문 없이 먼저 해 보라는 권고도 있지만, 오너가 고치기 전과 후의 짝을 넣으라고 했고 다른 공급자와 예문 내용을 같게 두기로 했으므로 넣는다. 예문이 해가 되는지는 1회차 뒤에 예문 없는 arm으로 본다.
- gemini: 그대로. 가이드가 자료 먼저, 물음은 맨 끝, 예문은 늘 넣기를 권한다. 3.8 flash는 temperature를 무시하므로 보내지 않는다. 3.1 pro는 기본 thinking이 high라 low로 명시했다.
- claude: 그대로. 규칙에 까닭을 붙이고 강한 말을 쓰지 않는 것, XML 태그, 예문 3~5개 권고와 맞는다. Opus 5.5와 Sonnet 5.5는 생각을 끌 수 없고 temperature를 보내면 400이다. 생각을 더 줄이는 손잡이(Opus는 "Answer directly without deliberating." 한 줄, Sonnet은 thinking을 between_tools로)는 1회차 결과의 시간과 비용을 보고 쓴다.
- 길이 규칙은 스키마에 넣지 않는다. 글자 수 한도는 Claude에서 400, Gemini에서는 무시된다. 지시문과 코드 검사로 본다.

| 감성형 소개 본문(셀러 글 없음)은 정확히 두 줄 | 지시문은 "두세 줄"이었는데 코드 검사 `paragraph_count`는 두 줄만 받음. 고쳐 쓰기 9번, 미리보기 3판에서는 감성형 3벌 모두 기본 문장으로 바뀜 |
| 상품 이름과 쇼핑몰이 지은 이름(모리플라워미디스커트 같은)을 글에 쓰지 않고 옷 종류로 부르기 | `reread_name` 4번 |
| 추천 대상은 20자 안 | 디자인 폭에서 두 줄로 넘어가 `wrapped_lines`(16번 가운데 다수) |
| 궁금한 점 답은 한 문장 30자 안, 한 가지만, 두 번째 안내를 붙이지 않기, 모든 질문에 답, 같은 주제 두 번 금지, 레귤러와 슬림은 "평소 사이즈" 없이 실측표만 | 짝 깨짐 `faq_pair_incomplete` 24번(답이 두 줄로 넘거나 겹쳐서 떨어지면 질문까지 함께 떨어짐), `size_advice` 1번 |
| 서버가 막는 말(하루 종일, 구김, 쾌적, 피부 자극, 누구나, 비치지 않아요, 시원해요, 튼튼해요)과, 사실에 없는 몸 부위(발목, 손목 등)를 쓰지 않기 | `unverified_claim` 11번(대부분 "하루 종일"), `body_position` 4번 |
| 없는 소재를 "없다"고도 쓰지 않기(스판이 없어서) | `unknown_material` 3번 |
| 글에서만 쓰는 말에 "살짜기"를 더함 | 미리보기 3판 쇼룸형 디테일에서 나옴 |

함께 고친 데이터(카피 총괄 값):
- `page_copy_trade_terms.json`: 겉감, 덧대, 안감을 더, 절개선, 절개를 넣, 절개를 낸을 더함.
- `page_copy_body_effects.json`: "~해 보이게"(보이게, 보여서)도 보이는 꼴로 받음("허리가 잡혀 날씬해 보이게 입을 수 있어요"가 근거가 있어도 거절됐음).

2.4판 실행 20쪽 가운데 18쪽에서 고쳐 쓰기가 나갔고, 그 76칸의 까닭을 세어 위 표를 만들었다(`.scratch/copywriting-20261113/trial/v24_rewrite_reasons.py`). 2.5판 실제 확인(11/20, 10벌 argon, run4 분석 재사용, 0.7169달러): 308칸 기준 검사 통과 274에서 289, 고쳐 쓴 칸 76에서 44, 빈 칸 8에서 4.

### 2.6 (2026-11-20, 2.5판 실제 확인의 원단 칸 반영, 다시 돌리지 않음)

2.5판 원단 제목 20개 가운데 14개가 "부드러운"으로 시작했고, 폴리에스터가 가장 많은 두 상품에 "부드러운 폴리에스터 혼방"이, 울이 25%인 상품에 "포근하고 잘 늘어나는 폴리에스터 혼방"이 나왔다. 원단 설명은 오너 예문 "피부에 닿는 느낌이 편해요"를 거의 그대로 되풀이했다(`.scratch/copywriting-20261113/trial/v25_fabric_check.py`).

| 바꾼 것 | 까닭 |
|---|---|
| 섬유마다 다른 낱말: 면은 부드러운이나 살에 닿는 느낌이 순한, 레이온은 찰랑이는이나 매끈하고 부드러운, 모달과 텐셀은 부드러운이나 흐르는, 아크릴은 포근한, 울과 캐시미어는 따뜻하고 포근한, 스판은 잘 늘어나는 | 다섯 섬유를 "부드러워요" 하나로 묶어 제목 첫 낱말이 한쪽으로 몰림. 낱말은 운영 데이터 `page_copy_fabric_feel.json`의 allowed에서 고름 |
| 폴리에스터와 나일론은 제 촉감 낱말이 없음. 원단 전체의 사실(기모, 골지, 쭈리, 촘촘한 짜임, 분석에 적힌 촉감, 스판이 있으면 잘 늘어나는)이 있을 때만 제목에 촉감을 쓰고, 없으면 "폴리에스터 혼방 원단"처럼 담백하게 쓰고 소수 섬유의 촉감은 설명으로 | "제목에는 가장 많은 섬유만"(`minority_material`)과 "섬유가 말해 주는 촉감"이 겹쳐 소수 섬유의 촉감이 주 섬유 이름에 붙음. 템플릿 총괄 지시(11/20) |
| 원단의 특징이 드러나는 촉감(기모, 골지, 촘촘한 짜임, 찰랑이는, 포근한)을 "부드러운"보다 먼저 | 제목 첫 낱말 되풀이 |
| 원단 칸 쓰기 조건 줄("소재 목록으로 촉감을 말할 수 있다")에, 폴리에스터나 나일론이 가장 많으면 사실 안에서 쓰고 촉감 사실이 없으면 이름만 담백하게 쓴다고 덧붙임 | 이 표 둘째 줄(폴리에스터와 나일론)과 부딪힘 |
| 보송하다, 폭신하다, 촘촘하다를 사실이 있을 때만 쓰는 낱말에 더함 | 2.5판의 "보송한", "촘촘한"은 분석 근거가 있었으나(aiSuggestedPoints, 사진 이유) 규칙에 적혀 있지 않았음 |
| 원단 설명은 "섬유, 그다음 하는 일"의 꼴만 오너 예문에서 가져오고 섬유마다 낱말을 바꿈(살에 닿는 느낌이 순해요, 몸을 따라 찰랑하게 떨어져요, 앉을 때도 편해요, 쌀쌀한 날 따뜻해요) | "피부에 닿는 느낌이 편해요"와 "편합니다" 되풀이 |

코드와 데이터 값은 바꾸지 않았다. 2.6판은 실제로 돌리지 않았으므로 촉감 쏠림이 얼마나 줄었는지는 첫 운영 생성이나 다음 확인에서 잰다.
