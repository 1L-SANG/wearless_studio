# Product/detail QC implementation and bounded evaluation

Date: 2026-09-25. Final policy: **`detail-output-qc-v4`**. All implementation and new research artifacts are inside `D:/wearless_studio/.worktrees/detail-shot-reliability`. This worker made no commits, image-generation calls, database/storage writes or production deployment changes.

## Final implementation

- `server/app/agents/detail_output_qc.py`: `is_detail(spec)` accepts only exact `cutType=product, shot=detail`; `verdict(settings, sources, candidate, target=..., direction=...)` returns a fail-closed server verdict; `repair_instructions(verdict)` returns fixed server sentences selected only by failed gate codes.
- `server/prompts/detail_output_qc_v1.txt`: separate core and specialist prompt sections. The filename remains stable; the policy version and actual prompt hashes identify the revision.
- `server/tests/test_detail_output_qc.py`: 61 dedicated tests. Combined with the existing vision adapter tests, **77 passed** using `server/.venv/Scripts/python.exe -m pytest tests/test_detail_output_qc.py tests/test_vision_llm.py -q`. One pre-existing Starlette/httpx deprecation warning was emitted.

The detail core and specialist both use the explicitly configured, available OpenAI snapshot **`gpt-5.4-2026-03-05`**, `reasoning_effort=high`, `image_detail=high`, and `max_completion_tokens=7000`. Availability was verified with authenticated read-only `GET /v1/models` before selection; the key was never printed. Root owns the dedicated Settings fields and deployment manifests: `model_detail_core`, `detail_core_timeout_seconds=90`, `model_detail_specialist`, and `detail_specialist_timeout_seconds=90`. General analysis routing is not changed by this module.

The core owns exactly four gates: target/framing, construction/design, color/material, and photographic preparation. The specialist owns permanent markings and temporary artifacts. A definite core FAIL returns FAIL and records specialist **NOT_RUN**, so the controller may spend its single correction without paying for a specialist on an already rejected candidate. A genuine core UNKNOWN returns UNKNOWN with specialist NOT_RUN. Core PASS requires the specialist; an unavailable, malformed or uncertain specialist cannot become PASS. **All six valid gates must PASS before `passed=true`.** There is no provider fallback.

Every attempt records requested/returned models, provider, prompt hashes, exact original source/result/target hashes, actual transmitted-image hashes, raw judge output and usage. Raw evidence never becomes repair instructions. The source is found by its hash, not the old analysis index, because runtime reorders inputs. Optional legacy cross-color detail transfer has separately hash-bound structure and color authorities. Display labels, reasons and seller feature text are not interpolated into judge or repair instructions.

Source and candidate quadrants are deterministic pixel crops used only by the specialist. They do not add evidence or become distinct garments. Permanent-label presence is separate from text readability, and evidence is the union of all authorized originals. Outside-frame labels are not deletion failures. An unclear source label must not become confidently invented text. Temporary cards/fasteners are separate from sewn labels and true yarn/hardware. Steaming, de-wrinkling and attractive re-laying are allowed; intentional lace, openwork, pleats and construction remain protected.

## Frozen controls and label independence

Labels and source/candidate hashes were frozen in `manifest.json` before the first judge call. Calibration uses prior known upload/generation cases only (green pointelle, ivory/red crochet, taupe outer, striped shirt). The control sources are different COOR product IDs: **3990 and 4013**; one negative substitutes a crop from the additional different ID **4002**. Thus control garments are SKU-disjoint from calibration. These COOR files are collected external official product photographs, **not seller uploads and not generated outputs**.

**Labeling provenance correction:** no new human labeler or case-level human validation was involved. Labels and visual inspection were produced by AI agent `/root/detail_evidence_cases`, with AI parent `/root` contributing separate source/target and producer-diagnostic review. The visual review was separate from image production; this QC implementation author also prepared the evaluation labels, so it is not an independently human-validated golden set. User preferences supply the policy, not human verification of each label. Control positives/negatives additionally have deterministic provenance: exact source crops versus known different-SKU swaps. Frozen manifests that mistakenly say human review remain byte-for-byte intact; `provenance-erratum.json` corrects that description without changing labels, inputs or judgments.

Positive controls are direct EXIF-normalized crops of the actual source photos. Negative controls swap in a different garment's actual crop. The controls were visually inspected before calling a judge. The third prepared positive pair was not called after calibration revealed the first policy was unsuitable; uncalled controls are not counted as evaluated.

The same four frozen controls were reused across v3/v4, so the v4 result is a **repeated component evaluation on fixed SKU-disjoint controls**, not a newly blinded unseen set. No control labels or images were changed after their results. The model change was motivated by a separate real-producer false rejection, not by choosing a model that made these four controls look good.

## Real-producer findings prevented overclaiming the easy controls

Root's subsequent producer probe exposed a false core rejection of the pink garment: Gemini called the vertical stitching below the neck label invented. Independent inspection of the actual Detail image shows those stitches already exist. Root's strong GPT core diagnosis correctly accepted that existing seam and still rejected a full-garment negative, motivating the dedicated GPT core. The pink final candidate was not regenerated by this worker.

The new producer crochet view really exposes the full neck-label location and lacks the sewn label, unlike the earlier tighter crop. Its specialist FAIL therefore has visual support. However, the model represented absent lettering as `candidatePresence=absent, candidateReadability=no_text`; v3 treated that semantic alias as invalid and returned UNKNOWN. v3.2 normalized known absence/no_text to not_applicable, preserving a definite missing-label FAIL and allowing the existing correction policy. **Absence+readable remains a contradiction and UNKNOWN.** An outside-frame label still does not fail merely for being absent.

v3.1 additionally blocks unsupported `textMatch=match` claims when readable/unreadable fields disagree. Stored v3 control raw judgments replay unchanged through these validator changes. The crochet producer raw judgment changes from UNKNOWN to FAIL, which is the intended correction of response interpretation, not a new vision judgment. The original v1/v2/v3 snapshots, manifests and receipts remain intact.

## Limits and handoff

This is a small calibration/control study, **not evidence of broad production accuracy**. Clean exact source crops are easier than generated garments. Whole wrong-garment swaps do not measure recall for subtle missing lace, changed motif scale, faint label corruption or ambiguous tiny fasteners. Mobile mixed-light color, adversarial image text, broad categories and production concurrency are not represented. Pixel-perfect microscopic stitch counting and unavailable real-world fiber/color facts are intentionally not claimed.

The module is ready for integration/independent code review. Publication, refund semantics, retry budgets, cache/version binding and actual producer workflows remain root-owned and must be verified at that layer. A local validator replay does not upgrade a weak-model cached PASS into a v4 result; the core model changed, so normal production cache fingerprints must reject old policies. No manual ‘use anyway’ bypass was added.

Owned production files are only the new QC module, prompt and dedicated test file. All owned evaluation changes are under this dated report directory. Existing workers/generator/config/frontend were not edited by this worker. Tests passed on this Windows worktree; root owns the Linux/full-suite/build verification and commit selection.
