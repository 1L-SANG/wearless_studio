# 앞뒤 밑단 혼합과 확인되지 않은 소매선의 진단

실사용 작업 모델은 gpt-6.1-sol, effort는 xhigh다. 오너의 흰 셔츠 앞 직선·뒤 곡선 확인과 핑크 헨리넥 팔 부위 표시를 기준으로 원본, 실제 분석과 생성 입력, QC 코드를 대조했다. 이 문서는 진단과 제안이며 제품 계약 변경이나 이미지 개선 완료 기록이 아니다. 새 유료 호출은 0회다.

## 확인된 문제

흰 셔츠 Front 사진에는 짧은 앞 밑단과 그 뒤로 내려오는 긴 곡선 뒷 밑단이 함께 보인다. Back 사진은 뒷면이다. 오너는 앞이 직선이고 뒤가 곡선인 상품이라고 확인했다. 이전에 두 착장을 올바른 곡선 보존으로 평가한 것은 잘못이다. 원래 API 응답과 사진을 바꾸지 않고 사람 검수와 연구 결과를 정정했다.

실제 AG-01 결과는 `hem_shape={value:curved,evidenceOrdinals:[1,2]}`다. 현재 자료 구조는 전체 밑단 형태 한 값만 담는다. `mannequin_photo_structure.prompt_block`은 앞면 사진 번호가 하나라도 포함되면 혼합값 전체를 통과시켜 `curved`와 `sourceViews=[FRONT,BACK]`를 생성에 전달한다. `confirmed_gpt_runtime._front_seller_facts`도 같은 조건으로 이를 앞 밑단 관찰이라고 투영한다. 앞뒤 차이가 소실된 것은 코드와 저장 결과로 재현됐다. 흰색이라는 원인만으로 설명하지 않는다.

핑크 헨리넥 원본 앞뒤에는 넓게 이어진 어깨 원단과 팔구멍 가장자리 바인딩이 보이며 표시된 위치의 별도 소매 부착선은 명확히 확인되지 않는다. 실제 분석은 `sleeve_structure=cap sleeve cut`를 확정 사실로 저장했고 소매 연결의 불확실성을 기록하지 않았다. 이 사실도 생성에 그대로 전달된다. 첨부 결과에는 그 위치를 별도 소매처럼 나누는 선이 보인다. 이 분류가 생성에 영향을 준 것은 유력한 경로지만 생성 모델의 내부 인과를 확정한 것은 아니다.

현재 분석 지시문에는 이미 넓은 어깨를 붙인 소매로 추정하지 말고 연결을 확인할 수 없으면 불확실로 기록하라는 문장이 있다. 검증 함수는 필드 형식과 사진 번호, usable 여부, 원본 해시를 확인하지만 사진의 실제 솔기를 판독하지 않는다. 지시문이 존재하는 것과 결과가 그 지시를 지켰다는 것은 다르다.

일반 의류 QC는 원본 사진과 생성본을 비교하지만 AG-01의 구조 관찰 자료를 직접 받지 않는다. 앞선 핑크의 가슴 절개 누락 오판처럼 전신만 보고 판단이 흔들릴 수 있다. 전문 구조 QC에는 부위 근거를 다루는 코드가 있으나 현재 운영 설정은 off이며 이번에 켜지 않았다.

## 추천하는 공통 해결안

한 상품의 전체 형태 한 값을 앞뒤와 부위별 관찰로 나누는 것이 핵심이다. 앞 밑단은 직선, 뒤 밑단은 곡선처럼 서로 다른 값을 함께 보존한다. 각 관찰은 사진 번호와 실제 부위, 확인 상태를 가진다. 전체 Front 사진에 뒷자락도 보인다는 이유로 뒷자락의 형태를 앞 밑단 값으로 복사하지 않는다. Detail이 어느 면의 어느 부위를 찍었는지도 독립적으로 기록한다.

소매의 이름과 실제 연결 구조를 분리한다. 팔을 조금 덮는 형태라는 관찰만으로 소매를 따로 붙인 솔기를 확정하지 않는다. 팔구멍 가장자리 마감, 별도 소매 부착 경계, 주름과 그림자, 골지와 평행 스티치 줄을 구분한다. 확인한 구조는 보존하고 연결이 가려지거나 낮은 대비로 읽히지 않으면 unknown으로 둔다. 실제 솔기가 명확히 있는 옷까지 모두 지워서는 안 된다.

원본의 관찰을 생성용 앞면과 뒷면의 적절한 부위에 연결한다. 앞쪽 생성에는 앞 밑단과 앞 팔구멍 근거가 우선하고, 옆에서 보이는 뒷자락은 뒷면 근거로 구현한다. 앞면이라서 Back의 모든 정보를 버리는 것도 올바르지 않다. 같은 부위에 모순되는 관찰이 있으면 한쪽을 사실처럼 채택하지 않고 미확인으로 남긴다.

QC에는 같은 검증된 부위 자료와 원본 사진을 함께 전달한다. 분석 글을 정답으로 믿는 검사로 바꾸지 않는다. 관찰과 원본 픽셀이 어긋나면 원본을 우선하고 분석 오류도 기록한다. 원본과 결과의 해당 부위를 대조해 확인되지 않은 선을 추가한 경우와 실제 선을 삭제한 경우를 모두 검사한다. 초기 생성뿐 아니라 편집 뒤와 untuck 뒤, 최종 결함 보정 뒤에도 같은 원본 근거를 사용한다.

부위 확대는 배치가 다른 원본과 착장본에 같은 좌표를 복사하는 방식으로 만들지 않는다. 어느 뷰의 어느 부위인지와 EXIF 적용 뒤 좌표계를 유지하고, 전체 사진을 함께 제공한다. 같은 픽셀을 확대한 부위와 원본의 출처를 기록한다. 배율이 같거나 물리적인 치수가 같다고 주장하지 않는다. 가려진 부위를 솔기 삭제로 판정하지 않는다.

## 코드와 호환성의 범위

소비자는 `mannequin_photo_structure`뿐 아니라 `confirmed_gpt_runtime`의 앞면 사실 투영, 생성 프롬프트, 초기 및 후속 QC를 함께 다뤄야 한다. 생성 블록의 2400자 제한 때문에 중요한 부위 사실이 잘리지 않는지도 검증한다.

현재 `OBSERVATIONS_VERSION=2`와 엄격한 필드 검증은 새 필드 또는 버전 상수만 바꾸면 기존 저장값을 거절할 수 있다. 구형과 신형을 구분해 읽는 정책이 필요하다. 기존 `curved + FRONT,BACK`를 앞과 뒤의 확정값으로 추측 분해하지 않는다. 기존 해시와 서명을 다시 작성해 새 관찰로 꾸미지 않는다. 구 자료에서 구분할 수 없는 부위는 확인 불가로 두고 원본 사진을 사용한다. 새 버전은 원래 정상 분석이 실행될 때 만들며 기존 상품에 추가 유료 분석을 자동 실행하지 않는다.

기존 상품 분석과 의류 QC 호출 안에서 이 자료를 주고받는 방향을 우선한다. AI를 여러 종류 더 붙이거나 항상 재생성하는 방식이 아니다. 부위 이미지와 구조화 자료가 늘면 입력 토큰과 시간은 증가할 수 있으므로 호출 횟수가 같다는 이유로 비용도 같다고 보장하지 않는다. 운영 specialist를 바로 켜는 설정 변경으로 대신하지 않는다.

## 검증해야 할 반례

| 표본 | 통과해야 할 동작 |
| --- | --- |
| 앞 직선·뒤 곡선 셔츠 | 앞에는 직선, 뒤에는 곡선을 보존한다. |
| 앞뒤 실제 곡선 셔츠 | 곡선을 일괄 금지하지 않는다. |
| 넓은 연장 어깨와 바인딩 | 별도 소매 부착선을 확인하지 못하면 새로 만들지 않는다. |
| 실제 소매 부착선이 보이는 옷 | 실제 솔기를 유지한다. |
| 접힘·그림자·골지 줄 | 새 봉제 경계로 확정하지 않는다. |
| 소매 연결이나 밑단이 가려진 사진 | 보이지 않는 부분을 확정 구조로 추정하지 않는다. |
| 원본에 없던 선 추가와 실제 선 삭제 | QC가 양쪽 오류를 검출하고 부위 근거를 제시한다. |

이번에 무료 대조로 저장된 혼합 밑단의 실제 생성 전달과 소매 분류 확정 전달 두 문제를 확인했다. 제안한 새 계약과 QC를 구현하거나 새 유료 이미지로 개선률을 측정한 것은 아니다. 모든 의류를 완전히 해결했다고 말할 수 없다. 제품 코드 변경과 회귀 검사, 같은 원본으로 실제 생성까지 비교하는 검증이 다음 단계다.

## 공식 문서와 해석

[OpenAI 이미지 지시 공식 안내](https://developers.openai.com/api/docs/guides/image-prompting)는 전체 편집 과정의 상품 보존과 원치 않는 변경을 확인하고 대표 입력에서 일관성을 반복 평가하도록 안내한다. [Google 이미지 생성 공식 안내](https://ai.google.dev/gemini-api/docs/image-generation)는 원하는 상태와 유지할 내용을 구체적으로 기술하도록 안내한다. 이에 맞춰 단순히 라운드나 선을 금지하는 대신 사진에서 확인한 연결과 면별 형태를 지정하는 방향을 제안한다. 공식 문서가 특정 의류 문제의 완전 해결을 보증한다는 뜻은 아니다.

## 쉬운 설명

앞뒤가 다른 옷을 한 가지 형태로 기록했고, 어깨가 넓다는 이유로 붙인 소매라고 확정했다. 생성과 검사까지 어느 사진의 어느 부위에서 확인한 사실인지 유지하는 것이 공통 해결 방향이다. 이 원칙을 코드와 반례 검사에 넣고 실제 사진에서도 개선되는지 검증해야 한다.
