## 0. 두 가지 변경

1. **모델이 고르는 사용 카테고리**를 부위·소재 축(12개)에서 **노출도 축(5개)**으로 바꾼다.
2. **셀러가 고르는 세부 카테고리**를 11개 추가한다.

둘은 독립이지만 같은 화면 계열이라 한 번에 처리한다.

## 1. 모델 사용 카테고리 — 노출도 축으로

### 1.1 확정 목록 (2026-09-10 개정)

```
BRAND_USE_CATEGORIES = ('일반 의류', '액티브웨어', '홈웨어·잠옷')
```

허용 풀 하나뿐이다. 모델은 세 가지 중 허용할 것을 정하고(기본 전부 켜짐), 셀러는 세 가지 중 하나를 선언한다. 여기 없는 품목(속옷·수영복 등)은 실모델을 쓸 수 없다. 선택지 자체가 없다.

> 9/3 초안에는 "제한 (기본 꺼짐) 속옷 · 수영복"이 별도 풀로 있었다. PR #250에서 그대로 구현했다가 리뷰에서 장식임이 지적돼 9/10에 삭제했다. 경위는 §1.7.

### 1.2 현행(v2)과 비교

| | v1 (~2026-08-28) | v2 (현행) | v3 (본 개정) |
|---|---|---|---|
| 축 | 성별·스타일 | 부위·소재·용도 혼재 | **노출도** |
| 개수 | 4 + 비의류 금지 7 | 11 + 금지 2 | **3** (9/3 초안은 3 + 제한 2, §1.7) |

### 1.3 전환 근거

**v2의 문제 — 축이 섞여 있다.**

```
상의 · 하의 · 아우터 · 원피스 · 스커트   → 부위
니트·스웨터 · 데님                      → 소재
셋업·수트 · 트레이닝·애슬레저            → 용도
잡화·액세서리 · 뷰티·화장품              → 품목
속옷·란제리 · 수영복·비키니              → 노출도
```

- 니트 원피스는 '니트·스웨터'인가 '원피스'인가. 데님 자켓은 '데님'인가 '아우터'인가. 분류가 결정 불가능하다.
- 더 근본적으로 **모델은 부위로 판단하지 않는다.** "상의는 되는데 하의는 싫다"는 모델은 없다. 모델이 실제로 거르는 축은 노출도와 맥락이다.
- v1에 있던 '스포츠·애슬레저'는 노출도 축에 가까웠다. v2는 그 점에서 오히려 후퇴했다.

**v3의 이점.**

- 각 항목이 **"내가 이걸 입은 것처럼 보여도 괜찮은가"** 한 질문으로 판단된다.
- 5개라 등록 화면에서 한눈에 들어온다.
- 카탈로그에서 모델 간 비교가 단순해진다(대부분 "일반+액티브+홈웨어 허용"으로 동일).

### 1.4 제외한 것과 이유

| 제외 | 이유 |
|---|---|
| 뷰티·화장품 | **지금 하지 않는다**(오너 결정). 화장품 상세페이지 생성 경로가 없다 |
| 잡화·액세서리 | 의류 종류가 상의·하의·아우터·원피스뿐이라 가방·모자 상세페이지를 만들 수 없다. 뷰티와 같은 논리 |
| 란제리 | '속옷'에 흡수(오너 결정) |
| 리조트·비치웨어 | '수영복'에 흡수(오너 결정) |
| 주류·담배·정치·종교·의료 | PR #194에서 이미 제거. 의류 상세페이지만 만들므로 금지할 대상이 존재하지 않는다 |

향후 뷰티·잡화 생성 경로가 생기면 그때 카테고리를 다시 추가한다.

### 1.5 강제 방식은 그대로

`brandUseCategory`는 **셀러가 명시적으로 선언하는 필드**이며, `clothingType`·`subCategory`에서 추정하지 않는다(2026-08-21 런타임 인가 설계). 이 원칙은 유지한다. 따라서 세부 카테고리 → 사용 카테고리 매핑 테이블은 **만들지 않는다**.

참고 대응(셀러 선언 시 안내용, 강제 아님):

| 사용 카테고리 | 해당 상품 예 |
|---|---|
| 일반 의류 | 티셔츠·니트·셔츠·바지·치마·원피스·코트 등 대부분 |
| 액티브웨어 | 레깅스·트레이닝 팬츠·요가복·스포츠 상의 |
| 홈웨어·잠옷 | 파자마·라운지웨어·홈웨어 |
| 속옷 | 브라·팬티·란제리·보정속옷 |
| 수영복 | 비키니·원피스 수영복·래시가드·비치 커버업 |

### 1.6 마이그레이션

발급된 실사용 라이선스가 없다(테스트만). 기존 값은 하위호환 표시만 하고 신규 발급은 v3 값만 받는다. PR #194가 쓴 방식(`_clean_uses`는 생성 시에만 필터)을 그대로 따른다.

### 1.7 제한 풀 삭제 (2026-09-10, PR #250 후속)

**지적.** PR #250 리뷰에서 다른 에이전트가 짚었다. 제한 풀(속옷·수영복)은 결과에 영향이 없다. `_clean_uses`가 허용 풀 밖 값을 드롭하므로 속옷은 어떤 라이선스로도 허용될 수 없고, 모델이 제한 칩을 체크하든 해제하든 거부 사유 코드만 바뀔 뿐 결과는 같다. 즉 칩이 장식이다. 셀러 측 선택 UI도 5개를 다 보여줘서 속옷을 고르면 항상 실패하는 결함이 있었다.

**대안.** (A) 제한 풀 삭제, 허용 3개만. (B) 제한을 체크 불가한 안내로 남겨 라이선스·QR에 "속옷·수영복 제외"를 명시적으로 기록. 차이는 하나다. 라이선스 기록에 명시적 제외가 남느냐.

**결정(오너).** A. 명시적 기록의 가치보다 단순함을 택했다. 지우는 건 언제든 할 수 있지만, 그 반대(기록에 소급 추가)는 안 된다는 점은 인지하고 내린 결정이다.

**"고를 게 없다"에 대해.** 3개는 부족한 게 아니라 의도한 결과다. 모델의 실질적 결정은 "액티브웨어를 끌까, 홈웨어를 끌까" 둘뿐이고 일반 의류는 사실상 기본값이다. 10초 안에 끝나는 결정이어야 한다. 부위(상의·하의)로 쪼개는 건 v2로 돌아가는 것이라 하지 않는다. 의미 있는 추가 구분은 짧은 기장(미니 치마·미니 원피스) 하나뿐이며, 실제로 거부하는 모델이 있는지 1기에서 관찰한 뒤 판단한다.

**구현.**
- 상수를 `BRAND_USE_CATEGORIES` 하나로. `ALLOWED_`/`FORBIDDEN_` 구분 삭제(프론트·서버 동기).
- 서버 검증에서 `forbidden_use` 분기와 `_clean_uses(forbidden)` 삭제. 셀러 카테고리가 `allowed_use`에 없으면 `license_use_not_allowed`.
- 모델 폼: 제한 칸 삭제. 허용 칸을 토글 3개로("내 얼굴을 쓸 수 있는 옷", 기본 전부 켜짐, 최소 1개 필수).
- 셀러 선택 UI: 상수 참조라 자동으로 3개만 노출. 속옷 선택 결함 해소.
- `forbiddenUse` 렌더링 삭제(모델 폼·셀러 미리보기·QR 검증 2곳·랜딩 상세·모델 허브).

**남기는 것.** `forbidden_use` DB 컬럼(`text[] not null default '{}'`)과 요청·응답·C2PA 매니페스트·admin 필드는 유지하고 항상 `[]`. 출력 이미지에 박히는 매니페스트라 필드 제거는 계약 변경이다. Holder VC는 기존 문자열 계약에 맞춰 `forbiddenUse`를 빈 문자열로 발급한다. 기존 활성 라이선스의 저장 값과 이미 서명된 VC·이미지는 변경하지 않으며, 검증은 기존 `forbidden_use` 값을 읽지 않는다. DB 마이그레이션 없음.

## 2. 세부 카테고리 확장

### 2.1 추가 목록

| 대분류 | 추가 | 비고 |
|---|---|---|
| 상의 | 후드 · 블라우스 | |
| 아우터 | 블레이저 · 바람막이 | |
| 하의 (여성 전용) | 레깅스 · 미니 치마 · 미디 치마 · 롱 치마 | 기존 '치마'는 세 기장으로 분화 |
| 원피스 | 미니 원피스 · 미디 원피스 · 롱 원피스 | 현재 0개 → 3개 |

### 2.2 제외한 것

| 제외 | 이유 |
|---|---|
| 반바지 | 바지 기장 축이 `발목 위/발목/발목 덮음`뿐이라 축을 새로 만들어야 한다. 오너 결정으로 이번 범위에서 제외 |
| 점프수트 · 나시·캐미솔 | 오너 결정 |
| 신발 전체 | 우리는 착용컷 파이프라인이고 신발은 별도 촬영 문법. MirrorMirror는 플랫레이 서비스라 신발이 있는 것 |
| 속옷·수영복 세부 | 모델 제한 카테고리와 충돌. 대분류로만 다룬다 |

### 2.3 유지하는 것

**아우터의 '셔츠'는 그대로 둔다.** PRD에 이미 명문화돼 있다.

> 셔츠는 상의와 아우터의 세부 카테고리에 모두 있을 수 있으며, 셔츠를 열어 입은 사진만으로 아우터로 바꾸지 않는다.

단추를 풀어 겉옷처럼 입는 상품을 위한 의도된 설계다. 중복이 아니다.

### 2.4 추가 비용 (코드 실측)

| 항목 | 영향 | 근거 |
|---|---|---|
| 실측 스키마 | **없음** | `MEASUREMENT_SCHEMA`는 대분류만 본다. subCategory 미참조 |
| 핏 축 카테고리 | **없음** | 축은 top·pants·skirt·dress·outer 5개. `fitProfileCategory`는 대분류 + 이름의 '치마/스커트' 문자열만 본다 |
| 서버 검증 | 한 줄 | `SUBCATEGORY_BY_TYPE` frozenset에 토큰 추가 |
| 소재 프리셋 | 선택 | `MATERIAL_PRESETS[(type, sub)]`가 없으면 대분류 폴백이 자동 적용 |
| 프론트 카탈로그 | 한 줄 | `catalogs.subCategories` |

즉 후드·블라우스·블레이저·바람막이는 **각 2줄**이면 끝난다.

### 2.5 새로 필요한 것

**① 세부 카테고리에 성별 필드**

현재 `catalogs.subCategories`는 대분류로만 나뉘고 성별 분기가 없다(핏 축에는 있음). 여성 전용 항목을 위해 필드를 추가한다.

```js
{ value: 'leggings', label: '레깅스', gender: 'women' }
```

`gender`가 없으면 공용. 대상 성별 선택에 따라 필터한다.

**② 축 초기값 연동**

세부 카테고리가 축의 초기값을 정한다. 예: '미니 치마' 선택 → 치마 기장 축 초기값 `mini`.

**③ 레깅스 축 숨김**

레깅스 선택 시 바지 `cut`·`length` 축을 **화면에서 숨긴다**. 서버는 축 값이 `None`이면 프롬프트에서 조용히 스킵하므로(`build_fit_profile_block`) 별도 서버 변경이 없다.

## 3. 세부 카테고리와 핏 축의 관계 — 축이 최종 진실

미니/미디/롱은 이미 치마·원피스의 **기장 축**에 존재한다. 세부 카테고리에도 넣으면 같은 값을 두 곳에서 정하게 된다. 규칙을 다음으로 확정한다(오너 결정).

> **세부 카테고리는 상품 분류이고 축의 초기값만 준다. 프롬프트가 참조하는 최종 진실은 축이다.**

- 셀러가 '미니 치마'를 고르면 기장 축이 `mini`로 세팅된다.
- 축에서 '롱'으로 바꾸면 그 값이 생성에 반영되고, **세부 카테고리 라벨은 바뀌지 않는다**.
- 이유: 세부는 "무엇을 파는가", 축은 "어떻게 연출하는가"로 역할이 다르다. 미니스커트 상품을 롱으로 뽑아보는 것도 셀러의 자유다.

## 4. 이번에 하지 않는 것

**원피스·아우터의 소매 축 신설 — 건너뛴다(오너 결정).**

현재 소매 축은 상의에만 있고 값이 캡·캡~반팔·반팔·5부로 **전부 짧은 소매**다(긴팔 값 없음). 축의 정체가 "긴팔을 반팔로 재단하기"라, 원피스에 붙이려면 축을 새로 설계해야 한다. 민소매 원피스·롱패딩 소매 조절이 실사용에서 실제로 아쉬운지 확인한 뒤 별도 트랙으로 다룬다.
