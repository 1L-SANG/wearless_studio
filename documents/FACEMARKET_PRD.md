> 등록 흐름은 2026-09-17 작업트리 구현 기준으로 갱신했다. 현재 순서는 [등록 흐름 정본](facemarket_registration_flow.md)과 §5를 따른다. 운영 배포 반영은 별도 확인한다. 그 밖의 인프라 실측과 과거 장애 기록은 2026-09-01 당시 기록이다.

## 1. FaceMarket 이 뭔가

셀러가 AI 컷을 만들 때 쓰는 **모델 얼굴의 공급·권리 계층**이다.

기존 스튜디오는 가상 모델(정적 3명)로 컷을 만들었다. FaceMarket 은 **실존 인물이 자기 얼굴을
등록하고, 사용 조건을 담은 라이선스를 발급받고, 셀러가 그 얼굴로 컷을 만들면 정산되는** 구조를
얹는다. 얼굴은 생체정보라 일반 이미지와 같은 규칙으로 다룰 수 없고, 그 제약이 이 제품의 화면과
플로우 대부분을 결정한다.

권리 증명은 **W3C VC**(Verifiable Credential)로 발급하고 **OmniOne Chain** 에 앵커한다.
QR 하나로 누구나 무인증 검증할 수 있다.

### 도메인이 둘로 나뉜다

| 도메인 | 역할 | 근거 |
|---|---|---|
| `facemarket.wearless.kr` | **모델 등록 전용.** 얼굴을 제공하는 사람이 오는 곳 | `src/lib/host.js` `IS_FACEMARKET` |
| `ai.wearless.kr` | 셀러 스튜디오. 모델 등록 메뉴는 **숨긴다** | `src/features/shell/shell.jsx:190` |

같은 코드베이스·같은 API 를 쓰고 호스트로만 갈린다. 로컬에서는 `?facemarket=1` 로 강제한다.

## 3. 핵심 개념 4개

```
등록(enrollment)  얼굴을 올리고 본인임을 증명하는 1회성 절차. 통과하면 모델이 생긴다.
모델(model)       셀러 카탈로그에 노출되는 사람. 등록 하나에 결속된다.
라이선스(license) 그 얼굴을 어떤 조건으로 쓸 수 있는지. 등록당 1건.
VC                라이선스를 담은 검증 가능한 자격증명. 체인에 앵커된다.
```

**등록 → 모델 → 라이선스 → VC** 가 한 줄로 이어진다. 재등록하면 이 줄이 통째로 새로 생기고,
이전 것은 갈아탄 것으로 정리된다(§7.4).

## 5. 등록 위저드, 현재 4단계

`src/features/model/ModelRegister.jsx`. 지원서 승인 후 시작하며, 상단에는 본인확인·사진·조건·증서가 표시된다. 지원 심사용 프로필과 등록 사진 18장은 별도다.

### 1. 본인확인

필수 약관 및 얼굴 정보 처리 동의를 받고 본인인증을 진행한다. 동의 버전은 서버 `BIOMETRIC_CONSENT_VERSION`과 프론트 `CONSENT_VERSION`을 따른다. 모바일 신분증 또는 활성화된 간편인증을 사용한다. 간편인증 경로는 주민등록증 사진 제출과 담당자 신원 확인이 추가된다. 전체 화면 카메라에서 직접 촬영하거나 앨범 사진을 촬영 틀에 맞춘 뒤, 단말 안에서 주민등록번호 뒤 7자리를 직접 가려야 한다. 가림 박스 위치와 크기를 조절하고 결과 미리보기에서 확인한 경우에만 가려진 사진을 제출한다. 서버는 전달된 가림 영역의 불투명 처리를 검사하며, 번호를 제대로 가렸는지는 담당자가 신원 승인 전에 확인한다. 원본 사진은 서버로 전송하지 않는다.

### 2. 등록 사진 18장

사진 슬롯 정본은 `server/app/facemarket_photos.py`의 `PHOTO_SLOTS`다. 프론트 `registerSlots.js`와 이름·순서를 맞춘다.

- 그늘에서 9장: 정면, 미소, 비스듬한 얼굴, 기준 사진 3장, 좌우 옆모습, 뒷모습.
- 햇빛에서 3장, 오른쪽으로 돌아 3장, 한 번 더 돌아 역광 3장.
- 한 번의 촬영은 약 15분. 같은 날 같은 머리와 옷으로 준비한다.
- 사진 원본을 업로드하고 서버에서 HEIC 해독·회전 정규화와 검사를 수행한다. 촬영 중 실시간 검사는 없다.
- 저장한 사진을 복원해 이어서 등록할 수 있다. 사진 교체와 삭제는 기존 업로드 검증 경계를 따른다.
- 구버전 등록의 완료 판정은 그 등록의 동의 버전을 따른다. 과거 3장·16장 호환 코드를 신규 등록 안내로 쓰지 않는다.

### 3. 사용 조건

사진 18장을 다 올리면 모델 이미지를 만드는 동안에도 바로 이 단계로 온다. 이미지가 준비되기 전에는 발급 버튼만 비활성이다. 허용할 옷 종류를 한 가지 이상 고른다(체형 선택은 2026-09-25에 없앴다). 셀러 이용료와 모델 정산 비율을 확인하고 필수 동의를 받는다. 금액은 가격 상수를 사용한다. 기간 선택 없이 신규 라이선스는 철회 시까지 유효하다.

### 4. 증서 발급

'라이선스 증서 발급하기'는 조건을 제출하고 초상 라이선스 계약에 서명하는 동작이다. 증서(VC)는 신원 확인이 끝난 등록에만 발급된다(§7.2). 모바일 신분증은 이 자리에서 바로 발급되고, 간편인증은 담당자가 신원 확인을 승인하는 순간 발급된다. 어느 경로든 모델에게는 테스트컷을 확정한 뒤에 증서를 보여 주고 완료 메일을 보낸다(2026-09-25 변경). 완료 화면은 테스트컷이 2일 안에 온다고 안내하고 증서 번호를 보여 주지 않는다.

### 등록 후 검수, 본인 확인과 공개

등록을 마친 뒤 기다리는 '검수 중' 화면은 없다. 관리자 순서는 신원 확인(간편인증), 사진 확인, 테스트컷 전송이며 사진 확인은 신원 확인 전에는 막힌다. 모델 본인이 `/model/confirm`에서 확대샷과 전신샷을 확인·확정하면 공개되고, 이때 증서 발급 완료를 함께 알린다.

## 6. 상태 머신

### 등록(enrollment)
```
identity_pending → photos_pending → liveness_pending → processing
                 → asset_building → license_pending → vc_pending → passed
실패 경로: failed(사유 기록) · cancelled(사용자 취소) · expired(24h TTL)
```
- TTL 24시간. 만료 스윕은 **앞 4단계만** 정리한다. `license_pending` 이후는 만료시키지 않는다
- 사용자당 진행 중 등록은 1건(부분 유니크 인덱스)
- 간편인증도 사진을 다 올리면 바로 바인딩(`asset_building`)되고 `review_status='pending'`으로 신원 확인을 기다린다. `review_pending` 상태는 2026-09-25 이전에 들어간 행의 호환용으로만 남는다
- 신원 확인됨은 `coalesce(review_status, 'approved') = 'approved'` 한 가지로 판정한다(`server/app/facemarket.py`의 `IDENTITY_CLEARED_SQL`, `identity_cleared`)

### 모델(model)
```
pending → verified → (재등록 시작) reverification_required → verified
```

### 라이선스(license)
```
pending → active → revoked | expired | reverification_required
```

**전이 규칙 3개가 화면에 직접 드러난다:**
1. 새 등록을 시작하면 기존 `active` 라이선스가 `reverification_required` 로 강등된다
2. 새 라이선스가 활성화되면 같은 모델의 옛 `reverification_required` 라이선스는 `revoked` 가 되고
   그 VC 는 폐기 큐에 들어간다
3. 목록에는 `revoked` 를 보여주지 않는다 — 행은 이력으로 남는다

## 7. 라이선스

### 7.1 조건 항목
| 항목 | 형태 |
|---|---|
| 허용 브랜드 유형 | 다중 선택 |
| 단가 | 셀러가 1회 사용할 때마다 지불하는 금액 |
| 유효기간 | 신규 등록은 철회 시까지, 기간 선택 없음 |

### 7.2 발급
1. 라이선스 행을 `pending` 으로 생성(등록당 1건 유니크)
2. 등록을 `vc_pending` 으로 전이
3. 신원 확인이 끝난 등록만 발급한다. 확인 전(간편인증 심사 대기)이면 pending 라이선스 카드를 201로 돌려주고 끝낸다. 담당자가 승인하면 `FaceVcIssueReconciler`와 `scripts/retry_pending_face_vcs.py`가 같은 발급 함수로 발급한다. 모든 발급 경로가 신원 확인을 다시 검사한다
4. **fm-holder** 에 순서대로: 지갑 생성(`409` 허용=이미 있음) → DID 등록 → VC 발급
   - 멱등키 `fm-license:{license_id}` 를 함께 보낸다
5. 성공하면 같은 트랜잭션에서 라이선스 `active` + 등록 `passed`. 모델은 `pending`으로 남고 테스트컷 확정 때 `verified`가 된다. 발급 순간에는 메일을 보내지 않는다
6. 신원 확인이 거절되거나 기한을 넘기면 발급 안 된 pending 라이선스를 같은 트랜잭션에서 지우고 등록을 정리한다

발급 전 재촬영은 신원 승인 전인 건에만 요청한다. 요청된 사진이 남아 있는 동안 발급과 신원 승인을 막고, 마지막 사진을 받으면 사진 회차를 올려 자산을 다시 준비한다. 준비가 끝나면 선택한 사용 조건을 유지한 채 pending 라이선스의 사진 키와 해시를 갱신한다. 이후 담당자가 변경된 사진의 신원을 승인하면 발급한다. 자산 재준비가 실패하면 미발급 라이선스도 함께 제거해 종료 정리가 사진과 자산을 남기지 않도록 한다. 이미 신원 승인된 발급 대기 건은 발급을 마친 뒤 재촬영을 요청한다.
7. 실패는 `vc_issue_delayed` 로 돌려주고 클라이언트가 **8초 간격 최대 4분** 자동 재시도한다

### 7.3 대기 UX가 인프라 때문에 존재한다
holder 는 평소 **0대**(scale-to-zero)고 콜드부트가 **~2분**(JVM 4개)이다. 그래서:
- 첫 등록 사진 업로드 시점에 holder를 미리 깨운다. 나머지 사진을 올리는 동안 발급을 준비한다
- 그래도 늦으면 발급 버튼이 "발급 준비 중… 최대 3분 걸릴 수 있어요"로 바뀐다
- 유휴 30분이면 다시 0대로 내려간다

### 7.4 VC 카드와 공개 검증
- 앞면: 얼굴 + 마스킹된 신원 + VC ID + 용도 + 단가 + 유효기간 / 뒷면: QR
- QR → `{origin}/verify/{licenseId}`
- **공개 검증 페이지는 얼굴을 렌더하지 않는다.** 서버 응답 화이트리스트에 얼굴·digest·CI·
  생년월일·user_id·model_id 가 애초에 없다

### 7.5 폐기
- 사용자가 폐기하거나, 갈아타서 죽거나, 재검증 배치가 무효화하면 **폐기 큐**에 잡이 쌓인다
- 워커가 holder 에 verify → revoke → verify 순으로 확인하고 종결한다
- 실패는 지수 백오프(최대 5분)로 재시도, **50회를 넘기면 `dead` 로 빼고 경고 로그**를 남긴다

### 얼굴 매칭 임계
| 대상 | 임계 | env |
|---|---|---|

| 업로드 사진 ↔ 앵커 (**측면**) | `0.10` | `FM_SIDE_LIVE_THRESHOLD` |

측면을 따로 두는 이유: 정면 인식기(YuNet+SFace)는 측면에서 유사도가 구조적으로 낮다.
실측 — 같은 사람인데 정면 0.1806 / 45도 0.2605 / **측면 0.14825**. 공통 임계 0.15 를
쓰면 측면만 0.0017 차이로 떨어져 **등록 전체가 실패**했다(2026-09-01, 3회 반복).

검출된 사진은 **전부** 임계를 넘어야 하고, 최소 1장은 매칭돼야 한다(스왑 방지).

## 10. 프라이버시 하드룰

이 규칙들이 화면 설계를 직접 제약한다. 디자인 리뉴얼에서도 깨면 안 된다.

1. **얼굴은 공개 URL 을 갖지 않는다.** 항상 Bearer fetch + objectURL
2. **공개 검증 페이지에 생체정보 0픽셀.** 무인증이라 렌더한 건 전부 공개된다
3. 업로드 사진은 **격리(quarantine)** 상태로 저장되고, 통과 후에만 승인 상태가 된다
4. 신분증 초상은 메모리에만. 저장·로그 금지
5. CI 는 HMAC 해시로만 저장
6. QC 로그에 이미지·파일명·랜드마크 금지 — 판정·사유코드·provider 만
7. 동의문 용어(`생체정보 처리 동의`)는 버전 계약이라 임의로 못 바꾼다

## 13. 디자인 리뉴얼 시 유의점

1. **7단계 진행 레일은 장식이 아니다.** 실제 순차 KYC 라 현재 위치가 늘 보여야 한다
2. **대기 화면이 제품의 일부다.** 콜드부트 2분·자산 생성 수 분이 정상 경로에 있다.
   "기다리면 된다"를 알려주는 상태 표현이 필요하다
3. **얼굴을 보여주는 모든 지점이 게이트를 거친다.** 썸네일 하나도 공개 URL 로 못 바꾼다
4. **선택 단계(체형·대표이미지)는 건너뛰기와 되돌아가기가 있어야 한다.** 이탈에 민감하다
5. **예시 사진과 내 사진이 한 화면에 같이 있다.** 구분 장치가 사라지면 안 된다
6. 법정 고지·동의문 문구는 계약이다. 표기(띄어쓰기) 외에는 건드리지 않는다
