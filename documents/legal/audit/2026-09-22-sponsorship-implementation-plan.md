# 협찬 법무 개정 실행 계획

> 법률 검토 전 초안이에요. 기준 작업지시서는 `documents/facemarket_sponsorship_legal_brief_20260922.md`이고, 지정 워크트리의 기준 커밋은 `8c802365`예요. 실행은 이 세션에서 직접 진행해요.

목표는 제품 사실을 바꾸지 않고 선택 협찬의 동의, 개인정보, 계약 경계를 정하고 검토 가능한 문서와 코드 초안을 만드는 것이에요.

## 작업 단위

1. 문서와 판단 근거를 작성해요. 00 조건표, 01·03·04·06 본문, 02·05 v3 델타, 공개 FAQ를 정리하고 커밋을 시도해요.
2. 동의 유형과 버전은 `DRAFT_` 상수로 분리해요. 자동 적용 디렉터리 밖에 새 SQL 초안을 두고 실제 등록·프로필·VC 배선은 하지 않아요. 테스트가 없는 상수와 발행 동작은 실패를 먼저 확인한 뒤 구현해요.
3. 발행기로 공개 검토본을 만들어요. 02·05 v1과 v2는 보존하고 v3 델타는 별도 공개 검토 파일로 만들어요. 협찬 개정본은 초안 표시, 미확정 시행일, 별도 버전을 유지해요. B-1·B-2 손 이식 공개본은 내용이 바뀌지 않으므로 유지해요.
4. 지정한 pytest로 서버 전체를 검사하고 발행 관련 테스트와 broken_bold 검사를 실행해요. 결과 원문을 마지막 보고서에 넣고 작업 단위별 커밋 결과를 기록해요.

## 설계 판단

- E-2 안에서 참여 토글, 수집·이용 체크, 협찬 프로필 제공 체크, 요청별 배송정보 제공 체크를 구분해요. 마지막 체크는 실제 셀러가 정해지는 후속 요청 단계에서 받아요. 배송 동의는 요청 수락이 아니에요.
- 화면 지시서의 협찬 프로필 노출에도 제3자 제공 근거가 필요해요. 비로그인 대중에게 인스타 계정·팔로워·사이즈를 공개하는 것은 이번 동의에 포함하지 않아요. 화면 트랙과 통합할 때 범위를 확인해요.
- 토글을 끄면 신규 요청이 중단되고 협찬 프로필은 내려가요. 기본 프로필 정보는 파기하며 진행 중 계약 이행에 필요한 최소 정보와 법정 증빙은 구분해요. 화면 지시서의 `off면 저장값 유지`와 충돌하므로 이 법무 초안 기준으로 조정이 필요해요.
- 협찬은 현금이 없지만 게시 의무와 교환되는 현물이에요. 비과세·순수 증여라고 단정하지 않고 세무 검토를 남겨요.
- 광고 표시 근거는 2026년 개정 지침의 Ⅴ.6이에요. 종전 Ⅴ.5를 그대로 인용하지 않아요.
- 소속사 서면 동의를 허용하는 기존 B-6을 협찬 자격으로 원용하지 않아요. 협찬에는 성인·소속 에이전시 없음·본인 참여를 다시 명시해요.
- 협찬 연결만으로 우회 거래 제한을 확대하지 않아요. 반송을 일반적 선택지로 새로 만들지 않고, 토글을 끄기 전 유효 요청은 진행하며 하자·미배송·권리 침해는 별도 구제 대상으로 둬요.

## 진행 기록

- 사전 확인 완료: 브리프 전체, 상위 CLAUDE.md, 00 원칙, 기존 델타, 발행기, 서버 동의 구조를 읽었어요. 기존 미추적 브리프는 사용자 제공 파일이에요.
- 공개본 경계: 기존 8종은 발행기 생성, B-1·B-2는 손 이식이에요. 이번에는 협찬 동의와 계약 델타 공개 검토본을 발행기 대상으로 추가해요. 외부 랜딩 저장소에는 쓰지 않아요.

- 문서 작업 커밋: `aceb099a`. `.git` 쓰기 오류 없이 성공했어요.
- 신규 서버 초안 검사 6건은 상수·공개 파일·SQL 부재 등으로 먼저 실패했고 구현 후 통과했어요. 조건 누락 검사는 내부 검토 절 끝에 넣으면 발행 대상에서 빠지는 것을 확인해 공개 본문에 주입하도록 테스트 위치를 고쳤어요.
- 독립 리뷰가 null 시행일의 실제 법무 화면 렌더 오류를 찾았어요. `/terms`, `/privacy`, `/answers`에서 `.split()` 예외가 재현됐고, 날짜 미정 표시만 추가했어요. 협찬 제품 흐름의 실제 배선은 건드리지 않았어요.
- 형식 판단: 02·05 v3는 기존 v1·v2와 분리한 공개 델타로 생성해요. 01·03·06과 E-2도 초안 상태를 명시하고 시행일을 null로 두므로 개정일을 시행일로 오인하지 않아요.

## 화면 트랙에 넘기는 저장 계약

| 동작 | 저장 원칙 |
|---|---|
| 첫 참여 | 서버가 인증 계정과 현행 고지 해시를 확정해 E-2a·E-2b의 별도 동의 행을 추가해요(E-2c는 E-2b에 합침). 필요한 개별 선택이 빠지면 켬 저장과 협찬 프로필 노출을 하지 않아요 |
| off | 서버가 계정 단위로 잠근 뒤 참여·프로필 정보 수집의 철회 행을 추가하고 협찬 상태와 노출을 같은 트랜잭션에서 꺼요. 이전 동의 행을 수정하지 않아요 |
| 동시에 요청·off | 같은 모델 잠금 아래 접수 시각과 유효 동의를 확인해 선후를 정해요. off가 먼저 확정되면 신규 요청을 받지 않아요 |
| 재시도 | 동작별 idempotency_key를 재사용하고 같은 행위가 중복 저장되거나 뒤집히지 않게 해요. 철회는 철회 대상 동의 버전과 해시를 참조해요 |
| 자동 off | 라이선스 철회·탈퇴는 같은 처리 단위에 상태와 동의 철회를 넣고 reason을 남겨요. 서버 처리 시각과 화면·시스템 식별자를 남기고 존재하지 않는 이용자 IP를 만들지 않아요 |
| 요청별 배송 | 실제 요청과 소유자를 확인한 뒤 E-2d-1·E-2d-2를 각각 저장해요. request_id와 수신자, 표시한 표의 스냅샷이 일치할 때만 그 요청 셀러에게 최소 정보를 제공해요 |
| 기존 모델 | 협찬은 기본 off이고 과거 생체정보·라이선스 동의에서 동의를 추정하거나 백필하지 않아요. 등록·카탈로그 게이트는 기존 경로 그대로예요 |
| 동의 개정 | 비참여자는 협찬 재동의 없음. 참여자는 해당 유형의 최신 버전과 grant·withdraw 이력을 비교하고 새 범위 처리 전에 재동의해요. 기존 진행 건은 접수 당시 조건 스냅샷으로 분리해요 |
| 약관·처리방침 개정 | 04 편집본 버전과 B-1 버전은 달라요. 처리방침은 고지·확인, 실제 변경된 개인정보 처리는 항목별 재동의예요. 약관·계약의 실질 변경은 문서별 명시적 수락 기록을 받아야 하고 현행 생체정보 문자열로 대신하지 않아요 |

`fm_enrollment_consent_events`는 등록 단위이고 비생체 동의에도 biometric_version을 필수로 받아요. 협찬을 여기에 붙이면 두 동의가 결합돼요. 구형 `personalization_consents`도 구형 프로필 FK와 세 유형만 허용해요. 따라서 계정 단위의 `fm_sponsorship_consent_events`를 새로 제안했어요. 프로필 컬럼과 PATCH API는 화면 트랙 소유이며 이번에 추가하지 않았어요.

초안 이벤트 행은 원문 주소·연락처·계정명을 담지 않고 고지 범위만 증빙해요. 이력은 일반 앱 권한으로 수정·삭제하지 않되, 적법한 파기 요구와 보유기간 만료는 분리된 파기 권한으로 처리해요. 데이터 보관 상한 확정과 파기 작업 구현 전에는 실제 수집을 개시하지 않아요.

협찬 프로필 제공 범주를 로그인한 셀러로 제한한 판단이 틀리면 공개 범위와 동의 UI를 다시 설계해야 해요. no-return과 진행 중 이행 유지 판단이 법률 검토에서 수정되면 02·04·05를 함께 고쳐야 해요. 이 비용과 시행일은 마지막 보고서의 오너 결정 항목으로 넘겨요.
