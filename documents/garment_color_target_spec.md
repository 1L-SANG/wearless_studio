# 셀러가 정한 옷 색 반영 명세 (garment-color-v1)

- 날짜: 2026-11-21
- 상태: 1차 구현 정본(11/21 고침: 코디 단계에는 서버 프로젝트가 없어 셀러 입력은 분석 키, 미리보기 누끼는 원본 API). 결정 근거는 ADR-0029.
- 범위: 코디보드에서 셀러가 실물 옷 색을 맞추고, 상세페이지 생성이 끝난 뒤 그 색을 옷 부분에만 반영한다. 에디터에서 다시 맞추기는 2차다.

## 1. 한 줄 규칙

셀러는 올린 상품 사진을 보며 슬라이더로 "실물은 이 색"을 정한다(목표 색 T). 생성은 지금 그대로 하고, 모든 컷이 끝난 뒤 그 색상의 컷들에서 옷의 가운데 색 M을 잰다. M이 T가 되게 하는 보정 한 벌을 구해 그 색상의 모든 컷 옷 부분에 똑같이 건다. AI로 다시 그리지 않는다.

보정은 선형광에서 픽셀마다 곱하는 연산(따뜻함 채널 이득, 밝기 노출 이득)과 그 픽셀 자신의 휘도 둘레 채도 조절뿐이다. 사진의 픽셀은 "빛 × 옷감 색"이므로, 같은 비율을 곱하면 옷감 색만 바뀌고 컷마다 다른 빛의 세기와 색온도는 그대로 남는다.

## 2. 색 연산 `garment-color-v1`

입력은 선형 sRGB 한 픽셀 `(r, g, b)`와 값 `p = {chroma, lightness, warmth}`다. 화면 미리보기(`src/lib/garmentColorTone.js`)와 서버(파이썬)가 같은 식을 쓴다. 상수:

| 이름 | 값 | 뜻 |
|---|---|---|
| `LR, LG, LB` | 0.2126, 0.7152, 0.0722 | Rec.709 휘도 |
| `WARM_END` | 0.10 | 따뜻함 ±100일 때 빨강과 파랑 채널 이득 ±10% |
| `CHROMA_SPAN` | 0.40 | 진하기 ±100일 때 채도 ×0.6~×1.4 |
| `EXPOSURE_SPAN_EV` | 0.50 | 밝기 ±100일 때 ±0.5EV |

순서는 아래와 같다. 값은 실수여도 된다(셀러 슬라이더는 정수, 서버 보정은 실수).

1. 따뜻함: `t = warmth/100 × WARM_END`, `gr = 1+t`, `gb = 1−t`, `n = 1/(LR·gr + LG + LB·gb)`. `r ← r·gr·n`, `g ← g·n`, `b ← b·gb·n`.
2. 진하기: `f = 1 + chroma/100 × CHROMA_SPAN`, `y = LR·r + LG·g + LB·b`, 각 채널 `c ← y + f·(c − y)`.
3. 색역 지키기: 채널이 0 미만이나 1 초과면 휘도 `y`를 유지한 채 채도만 줄인다(`src/lib/toneRender.js`의 `gamutSafe`와 같은 식).
4. 밝기: `gain = 2^(lightness/100 × EXPOSURE_SPAN_EV)`, 세 채널에 곱한다.
5. sRGB로 돌릴 때만 0~1로 자른다.

셀러 슬라이더 범위는 정수 −100~100이다. 화면은 손잡이를 끌 때만 |값| ≤ 3을 0으로 붙이고, 방향키 한 칸 이동은 그대로 둔다. 슬라이더 끝값은 사진에 안전하게 옮길 수 있는 한도(4절 상한)에 맞춘 것이다.

## 3. 원본 누끼와 목표 색 T

새 상품은 코디 단계까지 서버 프로젝트가 없다(확정 버튼에서 프로젝트를 만든다). 그래서 코디 단계의 미리보기 재료는 프로젝트와 무관하게 만들고, 셀러 입력(슬라이더)만 분석에 저장한다. 목표 색은 생성할 때 서버가 다시 계산한다.

- **원본 누끼:** 색상의 첫 Front 원본 사진에서 판매 의류만 오려낸 투명 PNG. 옷 영역은 기존 SAM 3 옷 윤곽(`tone_mask`, `garment_color_tune`과 같은 프롬프트)을 쓴다. 6절 원본 API가 만들어 돌려주고 서버에 저장하지 않는다. 화면은 세션 동안 사진별로 기억한다.
- **원본 색 S:** 누끼에서 알파 200 이상 픽셀의 sRGB 8비트 채널별 중앙값 `S8`, `S = linear(S8)`. 화면 미리보기와 생성 때 서버 계산이 같은 규칙을 쓴다.
- **목표 색:** `T = tone(S, sliders)`. 생성 잡이 끝 단계에서 그 색상의 Front 원본으로 S를 다시 재서 계산한다(색상당 SAM 3 1회). 슬라이더가 모두 0이면 목표가 없다.
- **AI 자동:** 원본 API가 그 사진(배경 포함)으로 기존 조명 추정(`qwen_flatlay._color_target`의 색 방향만, 밝기는 쓰지 않음)을 돌려 목표 a, b를 얻고, `lightness = 0`에서 `chroma`, `warmth` 정수 격자를 훑어 `tone(S, ·)`의 Oklab a, b가 목표에 가장 가까운 값을 `auto`로 돌려준다. 조명을 추정하지 못하면 `auto = null`(화면에서 버튼이 꺼진다).

## 4. 끝 단계 (생성 뒤 반영)

상세페이지 생성 잡에서 모든 컷 생성이 끝난 뒤(`asyncio.gather` 뒤), 결과 저장(`finalize_detail_page_success`) 전에 한 번 돈다.

1. 잡을 시작할 때 읽은 분석의 `garmentColorSliders`에서 0이 아닌 색상만 고른다. 없으면 이 단계는 아무것도 하지 않는다(비용 0). 고른 색상마다 Front 원본으로 S를 재서 `T = tone(S, sliders)`를 만든다(3절).
2. 그 색상의 판매 의류가 보이는 모든 결과 컷(착용컷, 스튜디오컷, 제품 단독컷, 디테일컷)을 모은다. 실존 모델 얼굴이 들어간 컷은 외부 서비스에 보내지 않는 규칙 때문에 `skipped: real_model`로 둔다.
3. 컷마다 옷 윤곽 `m_i`를 따고(코디 겹침 빼기 포함) 가운데 색 `M_i`(3절과 같은 채널별 중앙값)를 잰다. 윤곽 실패 컷은 건너뛴다.
4. `M = 채널별 중앙값(M_i)`. 셀러가 움직인 축만 푼다. 밝기를 움직였으면 `lightness`, 진하기나 따뜻함을 움직였으면 `chroma`와 `warmth`. 움직이지 않은 축은 0으로 고정한다. `tone(M, q)`가 T에 가장 가까운 실수 `q`를 찾는다(밝기는 Oklab L, 색은 Oklab a, b로 잰다).
5. 상한: `tone(M, q)`와 `M`의 차이가 Oklab L 0.10, a·b 거리 0.08을 넘지 않게 `q`를 같은 비율로 줄이고 `capped: true`를 남긴다.
6. 컷마다 윤곽 안 픽셀에 `tone(px, q)`를 건다. 가중치는 `윤곽 알파 × 보호`다. 보호는 **밝기를 뺀 색도 거리**로 잰다: `d = |(a/L, b/L)_px − (a/L, b/L)_{M_i}| × L_{M_i}`(Oklab). `d` 0.04 이하에서 1, 0.08에서 0으로 줄어든다. 그림자는 Oklab에서 (L, a, b)가 같은 비율로 줄어 색도가 그대로라 끝까지 보정되고, 색이 다른 프린트와 머리카락만 빠진다. 밝기를 포함한 거리를 쓰면 깊은 그림자 픽셀의 55~76%가 빠져 주름만 옛 색으로 남는다(11/21 운영 컷 6장 측정, `.scratch/coordi-color-20261111/lighting-demo/check.py`). 0.04~0.08에서 빨간 프린트 글자는 0% 보정, 그림자는 95~100% 보정이었다. 숫자는 로컬 표본 시험으로 조정 가능. 윤곽 밖 픽셀은 원래 바이트 그대로다.
7. 자기 검사: 바꾼 뒤 윤곽 밖이 달라졌거나 결과가 깨졌으면 그 컷만 원본으로 되돌린다.
8. 원본과 윤곽은 내부 자산으로 보관한다(의류 탭, 장수, 크레딧 계산에서 제외. 2차 에디터 다시 맞추기가 비용 0으로 쓴다).
9. 이 단계의 실패는 잡을 실패시키지 않는다. 취소 신호만 그대로 올린다.

추가 색상 컷은 지금처럼 색 입히기, 검사, `garment_color_tune`을 모두 지난 뒤 이 단계를 거친다. 셀러가 그 색상을 손대지 않았으면 이 단계는 그 색상을 건너뛴다.

## 5. 저장 계약

셀러 입력은 분석의 클라이언트 소유 키 `analysis.garmentColorSliders`에 둔다. 손님 초안에서도 같은 키로 저장되고 확정 때 분석과 함께 프로젝트로 옮겨진다. DB 마이그레이션은 없다.

```json
{
  "version": 1,
  "colors": {
    "<colorId>": { "chroma": 0, "lightness": -24, "warmth": 18 }
  }
}
```

- 서버는 분석 저장 때 검증한다. 값은 정수 −100~100, 모두 0인 색상과 상품에 없는 colorId는 빼고 저장한다. 모양이 틀리면 키를 지운다(분석 저장 전체를 실패시키지 않는다).
- 목표 색이나 원본 색을 클라이언트가 보내도 서버는 쓰지 않는다(생성 때 다시 잰다).
- 재분석은 이 키를 보존한다.
- 상세 생성 잡은 시작할 때의 값을 쓴다. 생성 중에 바꾼 값은 다음 생성부터 반영된다.

## 6. API

스위치 `GARMENT_COLOR_TARGET_ENABLED`(기본 꺼짐)가 꺼져 있으면 아래 원본 API는 404, 상태 API는 `{"enabled": false}`이고, 생성 끝 단계도 돌지 않는다.

### GET `/v1/public/garment-color-targets/status`

로그인 없이 부른다. `{"enabled": true, "toneVersion": "garment-color-v1"}`. 화면은 `enabled`일 때만 "내 상품" 줄을 보여 준다.

### POST `/v1/public/garment-color-source`

로그인 없이 부른다(손님 초안). multipart: `image`(그 색상의 Front 사진 파일), `clothingType`, `subCategory`(선택). 사진은 JPEG, PNG, WEBP만 받고(그 밖은 400), multipart가 아닌 요청도 400이다. 요청 수는 비로그인 시간당 40, 하루 120, 로그인 사용자 시간당 60, 하루 200으로 제한한다.

### POST `/v1/projects/{projectId}/garment-color-source`

로그인과 프로젝트 소유 확인. 본문 `{"colorId": "..."}`. 서버가 그 색상의 첫 Front 자산을 읽는다. 없는 색상 404. 요청 수는 위 공개 API의 로그인 사용자 한도(시간당 60, 하루 200)를 같은 사용자 몫으로 함께 센다.

두 원본 API의 응답은 같다.

```json
{
  "status": "ready",
  "reason": null,
  "cutoutPng": "data:image/png;base64,....",
  "sourceSrgb": [226, 217, 196],
  "auto": { "chroma": -8, "lightness": 0, "warmth": -36 }
}
```

- `cutoutPng`는 긴 변 640px 이하로 줄이고 투명 여백을 잘라 낸 누끼다.
- 옷을 못 찾으면 `{"status": "unavailable", "reason": "mask_failed"|"invalid_image", "cutoutPng": null, "sourceSrgb": null, "auto": null}`(200).
- 비용은 호출마다 SAM 3 1~2회다.

## 7. 기록

- 잡 메타데이터 `garmentColorTarget`: 색상마다 `target`, `median`, `params`(q), `capped`, 컷마다 `status`(`applied`, `skipped`, `reverted`), `reason`, 바꾸기 전후 가운데 색.
- 바꾼 결과 자산 메타데이터 `colorTarget`: `originalAssetId`, `maskAssetId`, `params`, `toneVersion`.

## 8. 비용

코디보드에서 판을 열고 색상을 볼 때 색상마다 SAM 3 1~2회(약 0.005~0.01달러). 생성 뒤에는 셀러가 색을 정한 색상에만 색상당 원본 1회와 컷마다 약 2회(약 0.01달러). 15컷 페이지 약 0.15달러. 손대지 않으면 생성 뒤 비용은 0이다.

## 9. 알려진 한계

- 실존 모델 얼굴이 든 컷은 반영하지 않는다.
- 무늬와 배색은 가운데 색만 옮긴다. 길이, 핏, 질감은 바꾸지 못한다.
- 4절 상한을 넘는 큰 차이는 상한까지만 옮긴다.
- 코디에 이너를 고른 착용컷은 반영하지 않는다(`matching_unverified`). 이너와 판매 옷이 같은 자리에 겹쳐 옷 영역을 안전하게 가를 수 없어서, 운영 중인 끝에서 옷 색 맞추기의 규칙을 그대로 따른다. 아우터는 이너 칸이 늘 있어 착용컷 대부분이 여기에 걸린다. 상품컷은 반영한다.
